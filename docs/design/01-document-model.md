# 01. 문서 모델

- 상태: 초안
- 해결 대상: L6, L7, L8 (기반), L1·L2 (구역·개체 표현)

## 1. 요구사항

- R1. 블록 경계를 넘고 서로 겹치는 범위(댓글, 변경 추적, 하이라이트)를 손실 없이 표현한다.
- R2. 문단 분할·병합이 동시 편집 중에도 다른 사용자의 입력을 잃지 않는다.
- R3. 블록(문단, 표, 개체) 이동이 삭제+삽입이 아닌 이동으로 기록된다.
- R4. 모든 위치는 동시 편집 후에도 의미가 유지되는 안정적 식별자로 표현된다.
- R5. 페이지 조판에 필요한 개념(구역, 머리말·꼬리말, 각주, 앵커 개체)을 모델이 직접 가진다.
- R6. 스키마로 허용 구조를 검증하고, 외부 붙여넣기 등은 스키마에 맞게 정규화한다.

## 2. 구조 개요: 스토리(Story) 모델

Word의 모델을 참고해, 문서를 **여러 개의 스토리**로 나눈다.
스토리는 "한 줄로 흘러가는 텍스트 흐름"이다.

```
Document
├─ settings (기본 스타일, 글꼴 목록, 번호 매기기 정의 …)
├─ styles   (문단 스타일, 글자 스타일, 표 스타일)
├─ sections[]  : 구역. 용지 크기, 여백, 단 수, 머리말·꼬리말 스토리 참조
└─ stories
   ├─ body          : 본문
   ├─ header:*      : 머리말 (구역·홀짝·첫쪽 별)
   ├─ footer:*      : 꼬리말
   ├─ footnote:*    : 각주 본문 (본문의 각주 참조 문자가 가리킴)
   ├─ cell:*        : 표 셀 내용
   └─ frame:*       : 글상자 내용
```

스토리 안의 내용은 **문자 열(sequence)** 이며, 다음 요소가 섞여 있다.

| 요소 | 설명 |
|---|---|
| 일반 문자 | 유니코드 코드포인트 1개 = 원소 1개 |
| 문단 표식 `¶` | 문단의 **끝**을 나타내는 특수 원소. 문단 속성(정렬, 들여쓰기, 스타일, 목록 수준)을 가진다 |
| 구역 표식 `§` | 구역의 끝. 구역 속성 참조 |
| 인라인 개체 | 글자처럼 취급되는 이미지, 수식, 각주 참조, 필드(쪽 번호 등) |
| 앵커 | 떠 있는 개체(어울림 이미지, 글상자)가 붙는 위치. 폭 0 |
| 블록 개체 | 표. 원소 1개로 존재하며 셀 스토리들을 참조한다 |
| 구획 표식 | 보이지 않는 원소. 스토리를 구획으로 나누며, 화면 순서는 구획 ID의 순서 목록이 정한다. 구획 ID는 구획을 끝내는 표식의 ID. 문단 이동은 글자를 옮기지 않고 구획 순서만 바꾼다 (ADR-0003, [V4 후속](../spikes/phase0-crdt.md#후속-2-기준anchor-방식-검토와-m4-끝-표식-구획)) |

### 왜 트리가 아니라 문자 열 + 표식인가

- **L6/R2**: 문단 병합은 `¶` 원소 1개 삭제, 분할은 `¶` 1개 삽입이다. 두 문단의 내용은 같은 열에 그대로 남으므로, 동시에 일어난 입력이 다른 컨테이너로 옮겨지다 유실되는 일이 없다. 변경 추적에서도 "문단 표식 삭제 제안"이 문자 삭제 제안과 같은 방식으로 표현된다.
- **L7/R1**: 범위는 열 위의 두 지점이므로 문단, 목록, 제목 경계와 무관하게 연속된다.
- 목록은 별도 중첩 노드 없이 문단 속성(`list: {id, level}`)으로 표현한다. 목록 들여쓰기·내어쓰기가 구조 변경이 아니라 속성 변경이 되어 충돌이 줄어든다.

트리 구조가 꼭 필요한 곳(표 → 행 → 셀)은 **스토리 참조**로 계층을 만든다. 셀 안은 다시 평평한 열이다.

### 대가

- 블록 이동(R3)이 평평한 열에서는 "구간 이동"이 되어 일반 시퀀스 CRDT로는 표현하기 어렵다 → 구획 표식 + 구획 순서로 해결 (05 §3)
- 문단 단위 처리(레이아웃 캐시 등)를 위해 `¶` 위치 인덱스를 유지해야 한다 → §7

## 3. 식별자와 위치

### 3.1 원소 ID

열의 모든 원소는 생성 시 고유 ID를 받는다: `(peerId, counter)`.
문단의 ID는 그 문단을 끝내는 **`¶` 원소의 ID**로 정의한다. 문단이 분할되면 앞쪽은 새 `¶`의 ID를, 뒤쪽은 기존 ID를 유지한다 (뒤쪽 문단이 원래 속성을 가진다).

### 3.2 위치(Position)

```ts
type Position = {
  story: StoryId;
  anchor: ElementId;    // 기준 원소
  side: 'before' | 'after';
};
```

- 원소 사이의 틈은 "어떤 원소의 앞/뒤"로 표현한다. 기준 원소가 삭제되어도 CRDT의 묘비(tombstone) 덕분에 위치를 계속 해석할 수 있다.
- `side`는 커서 친화성(affinity)과 범위의 확장 동작을 결정한다. 예: 댓글 범위 끝이 `before`면 끝에 입력한 글자는 범위 밖.
- 화면 계산용으로는 `Position → (story, offset: number)` 변환을 제공한다 (§7 인덱스 사용).

## 4. 서식과 범위 레이어

두 종류를 구분한다.

| 종류 | 예 | 저장 방식 | 겹침 | 블록 경계 횡단 |
|---|---|---|---|---|
| **글자 서식** | 굵게, 글꼴, 색, 링크 | 원소 열 위의 서식 구간 (Peritext 방식) | 같은 속성끼리는 병합 | 가능 |
| **주석(Annotation)** | 댓글, 변경 추적, 검색 하이라이트, 맞춤법 표시 | 별도 범위 레이어 | 자유롭게 겹침 | 가능 |
| **문단 서식** | 정렬, 들여쓰기, 스타일, 목록 | `¶` 원소의 속성 | - | - |

```ts
type Annotation = {
  id: AnnotationId;
  type: 'comment' | 'suggestion' | 'highlight' | string;
  start: Position;
  end: Position;
  data: Record<string, unknown>;
  persistent: boolean; // false면 문서에 저장 안 함 (검색, 맞춤법)
};
```

- 주석은 문서 구조를 쪼개지 않는다. 렌더러가 레이아웃 결과 위에 겹쳐 그린다.
- 범위 안의 모든 원소가 삭제되면 "빈 주석" 상태가 된다. 댓글은 고아(orphan)로 표시하고 이력에서 복구 가능하게 둔다.

## 5. 연산(Operation)

모든 변경은 아래 연산의 조합이다. 연산은 직렬화 가능하고, 역연산을 만들 수 있어야 한다.

| 연산 | 설명 |
|---|---|
| `insert(pos, elements[])` | 문자, `¶`, 인라인 개체 삽입 |
| `delete(range)` | 구간 삭제 (묘비 처리) |
| `format(range, key, value)` | 글자 서식 설정·해제 |
| `setAttrs(elementId, attrs)` | `¶`, `§`, 개체 속성 변경 |
| `move(range, targetPos)` | 구간(하나 이상의 완전한 문단 또는 블록 개체) 이동 |
| `createStory / deleteStory` | 셀, 각주, 글상자 스토리 생성·삭제 |
| `annotate / unannotate / updateAnnotation` | 주석 레이어 조작 |
| `setStyle / setSection / setSetting` | 문서 수준 정의 변경 |

### 트랜잭션

```ts
type Transaction = {
  ops: Operation[];
  selectionBefore: Selection;
  selectionAfter: Selection;
  origin: { peer: PeerId; kind: 'user' | 'remote' | 'system' | 'undo' };
  meta: { label?: string; mergeKey?: string; time: number };
};
```

- `mergeKey`가 같은 연속 트랜잭션은 실행 취소에서 하나로 묶인다 (연속 타이핑 등).
- `system` 트랜잭션(정규화, 자동 번호 등)은 실행 취소 단위에 포함되지 않는다.

### move의 의미

- 이동 대상은 **완전한 문단 구간** 또는 **블록 개체** 단위로 제한한다 (임의 글자 구간 이동은 잘라내기+붙여넣기로 처리).
- 이동된 구간 안에서 동시에 일어난 편집은 이동 후 위치에 반영되어야 한다. 구현 방식은 05 §3에서 다룬다.

## 6. 스키마와 정규화

- 스키마는 스토리 종류별 허용 원소, 각 개체의 속성 타입, 중첩 제한(예: 각주 안에 각주 금지)을 정의한다.
- 모든 스토리는 `¶`로 끝나야 한다. 빈 스토리 = `¶` 하나.
- 정규화는 `system` 트랜잭션으로 수행한다. 동시 편집으로 생긴 스키마 위반(예: 동시에 표 삭제와 셀 편집)은 수신 측에서 결정적으로 정규화한다. **모든 피어가 같은 규칙으로 같은 결과**를 내야 하므로 정규화 규칙은 순수 함수여야 한다.

## 7. 파생 인덱스

모델은 아래 인덱스를 증분 유지한다.

- 문단 인덱스: 스토리별 `¶` 목록과 각 문단의 오프셋 범위 (균형 트리, 순위 질의 O(log n))
- ID → 오프셋 변환
- 주석 구간 트리: 오프셋 범위로 겹치는 주석 질의

## 8. 직렬화

- 저장 포맷: CRDT 스냅샷 + 증분 업데이트 (05)
- 교환 포맷: 사람이 읽을 수 있는 JSON (`QuireDoc v1`). 묘비와 ID 없이 현재 상태만 담는다. 테스트 픽스처, 가져오기·내보내기의 중간 표현으로 쓴다.

## 9. 열린 질문

- O-1. 평평한 열 + `¶` 표식(현재 제안) vs 문단 리스트. 평평한 열은 분할·병합에 강하고 이동에 약하다. 0단계에서 두 방식으로 동시 편집 시나리오(분할+입력, 병합+입력, 이동+입력)를 시뮬레이션해 결정한다.
- O-4. 표 행·열 이동과 셀 병합의 동시 편집 의미론.
- O-5. 글자 서식 구간의 확장 규칙(굵게 끝에 입력하면 굵게인지)을 속성별로 어떻게 지정할지. Peritext의 `expand` 규칙을 기본으로 검토.
