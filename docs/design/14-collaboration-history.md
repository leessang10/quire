## 2. 주석 레이어 (G1)

### 2.1 모델

01 §4의 주석이다. 문서 구조를 쪼개지 않고 레이아웃 위에 겹쳐 그린다.

```ts
interface Annotation {
  id: string;
  type: 'comment' | 'suggestion' | string;
  /** 범위: 스토리와 시작·끝 위치 (Doc 원소 ID 기준, 01 §3.2) */
  story: StoryId | null;
  start: Position;
  end: Position;
  /** 종류별 데이터 (댓글: 스레드 ID, 제안: 종류·작성자·시각·이전 값) */
  data: Record<string, unknown>;
}
```

- 편집 모델(`Document`)이 주석 표를 가진다: `annotate`·`unannotate`·`updateAnnotation`. 연산 `{ type: 'annotation', id, before, after }`으로 실행 취소가 된다.
- 위치는 그 스토리 Doc의 `Position`(원소 ID + side)이다. 범위 앞뒤에 입력하면 side 규칙(01 §3.2)으로 넓어지거나 그대로다.
  - 댓글: 앞은 `after`, 끝은 `before`. 범위 끝에 입력한 글자는 밖이다.
  - 삽입 제안: 같은 작성자가 이어 입력하면 넓어진다 (§4.2).
- 범위 안 원소가 모두 지워지면 **고아**다. 주석은 남고 화면에는 범위가 없다. 댓글 창에서는 "지워진 글에 단 댓글"로 보인다. 실행 취소로 글이 돌아오면 범위도 돌아온다 (원소 ID 기준이므로).
- 찾기: 그리기는 보이는 문단의 주석만 필요하다. 주석마다 범위의 화면 오프셋을 구하는 것은 O(log n)이다 (`resolve`). 그래서 문서 판마다 스토리별 (시작 오프셋 순) 정렬 목록을 캐시하고, 보이는 문단 범위로 이분 탐색한다. 주석 1,000개에서 입력마다 다시 정렬해도 1 ms 안이 목표이고, 넘으면 구간 트리로 바꾼다.

### 2.2 동기화

- Loro 맵 `annotations` 하나에 키 `<주석 ID>|<키>`를 둔다 (구역 설정과 같은 모양, 12 §3.2). 키는 `type`·`story`·`start`·`end`·`data`이고, 키마다 LWW다.
- 시작·끝은 **Loro 커서**를 인코딩한 바이트열(base64)이다 (09 §7). 받는 쪽은 `resolveCursor`로 자기 Doc의 오프셋을 구하고, 그 자리 `Position`으로 바꿔 편집 모델에 넣는다. 아직 받지 못한 글자를 가리키면 그 주석을 미뤘다가 다음 원격 변경 때 다시 푼다.
- Worker 경로: 주석 맵 변경은 정의 맵(스타일·목록·구역)과 같은 길을 탄다. 메인은 `Position` → 화면 오프셋을 Worker에 보내고, Worker가 커서를 만든다 (Worker만 Loro를 가진다). 로컬 주석 변경이 가는 중이면 그 주석의 원격 값을 미룬다 (끝 ¶ 맵과 같은 규칙, 11 §13).
- 동시성:
  - 같은 주석의 다른 키를 동시에 바꾸면 둘 다 남는다.
  - 지우기는 `type` 키를 지우는 것으로 표시한다. 다른 피어가 같은 때 `data`를 바꿔도 지운 것이 이긴다: `type`이 없으면 주석이 없는 것으로 본다.

### 2.3 저장

- 정본 `annotations` 배열(07)은 `{ id, type, start: { story, offset }, end: { story, offset }, data }`이고, 오프셋은 코드포인트다. 고아는 `start`·`end` 없이 쓴다.
- 압축(새 판)은 정본을 거치므로 커서가 새로 만들어진다. 오프셋에서 새 판의 커서를 만든다.
- 재기반(오프라인 편집을 새 판으로): 주석은 정본 오프셋으로 옮긴다. 그사이 바뀐 글 때문에 어긋나는 범위는 텍스트 차이 대응(재기반의 diff)으로 옮긴다.

### 2.4 그리기

- 줄마다 그 줄에 걸친 주석 범위를 바탕색으로 칠한다. 댓글은 노란색이고, 선택한 스레드는 진하게 칠한다.
- 겹친 범위는 칠을 겹쳐 진해진다.
- 오른쪽 여백에 표시를 둔다 (§3.2 댓글 창과 이어짐).
- 접근성 미러: 범위를 `<mark>`로 감싼다. 댓글은 `aria-describedby`로 스레드 요약을 단다.

## 3. 댓글 (G2)

### 3.1 모델

- 댓글 주석(`type: 'comment'`, `data.thread`)과 스레드는 따로 둔다.
- 스레드는 Loro 맵 `threads`에 키 `<스레드>|resolved`, `<스레드>|anchor`(주석 ID)를 둔다.
- 메시지는 스레드마다 Loro **리스트** `msgs:<스레드>`다. 항목은 `{ id, author, time, text, edited? }`이다. (구현은 평평한 키 맵으로 바꿨다: §12)
  - 답글은 리스트에 넣기만 하므로 동시 답글이 모두 남는다 (LWW가 아님).
  - 고치기는 항목 맵의 `text` LWW다. 지우기는 `deleted` 표시다 (이력·답글 차례를 지킨다).
- 작성자는 `{ id, name, color }`다. 4단계에는 인증이 없으므로 접속할 때의 사용자 정보(프레즌스와 같은 값)를 쓴다. 권한(§7)이 생기면 서버가 넣는다.
- 글은 평문(줄바꿈 포함)이다. 멘션·서식은 4단계 밖이다.

### 3.2 편집기

- 명령:
  - `addComment(text)`: 선택 범위에 주석을 걸고 스레드와 첫 메시지를 만든다. 실행 취소 한 단계.
  - `replyComment(thread, text)`, `resolveThread(thread, on)`, `deleteThread(thread)`: 주석을 지우고, 스레드는 지운 표시만 한다.
- 댓글 창은 편집기 밖의 DOM이다 (플레이그라운드가 그린다). 편집기는 다음을 준다:
  - `threads()`: 스레드 목록, 문서 순서. 각 항목에 범위의 화면 y, 고아 여부, 메시지가 있다.
  - `onChange`.
- 창은 스레드를 범위의 y에 맞추어 놓고, 겹치면 아래로 민다 (Google Docs처럼). 고아·해결한 스레드는 아래 목록에 모은다.
- 셀·머리말·각주 안 범위도 같다. 주석의 `story`로 그 스토리 레이아웃에서 y를 구한다.

## 4. 변경 추적 — 제안 모드 (G3)

### 4.1 원칙

05 §5의 표를 따른다. 제안은 **문서에 바로 들어간 변경 + 그것을 표시하는 제안 주석**이다.

- 삽입은 원소를 넣고 표시한다.
- 삭제는 원소를 지우지 않고 표시한다.
- 서식·문단 속성은 적용하고 이전 값을 남긴다.

그래서 제안 모드 편집도 지금의 연산·동기화·실행 취소를 그대로 쓴다. ¶가 원소이므로(01 §2) 문단 분할·병합 제안은 글자 제안과 같다.

| 편집 (제안 모드) | 기록 | 수락 | 거부 |
|---|---|---|---|
| 글자·¶·개체 넣기 | 넣고 `suggestion` `{ kind: 'insert' }`로 범위 표시 | 주석만 지움 | 범위의 원소 지움 |
| 지우기 | 지우지 않고 `{ kind: 'delete' }`로 범위 표시. 범위 안의 **내 삽입 제안**은 실제로 지운다 (Word와 같다) | 범위의 원소 지움 | 주석만 지움 |
| 글자 서식 | 적용하고 `{ kind: 'format', before: [런별 이전 서식] }` | 주석만 지움 | 이전 서식 복원 |
| 문단 속성 (정렬·스타일·목록 …) | 적용하고 ¶ 하나 범위에 `{ kind: 'para', before: {키: 이전 값} }` | 주석만 지움 | 이전 값 복원 |

- 데이터에는 `author`, `time`이 함께 든다.
- 같은 작성자가 이어서 한 삽입·삭제는 한 제안으로 합친다. 범위를 넓히고, 실행 취소 합치기 키(mergeKey)와 같은 규칙이다.
- 제안 모드는 편집기 상태이고 문서가 아니다 (사용자마다 켬). 문서 설정 "모두 제안으로" 잠금은 4단계 밖이다.

### 4.2 세부

- **삭제 제안 위에 입력하기**: 삭제 제안 범위 안에 입력하면 그 자리에서 범위를 나누고, 새 글자는 삽입 제안이다.
- **다른 사람의 삽입 제안을 지우기**: 삭제 제안이 된다 (그 원소는 두 제안에 걸린다). 이 원소를 수락하면 삽입 수락 → 삭제 수락이므로 지워진다.
- **서식 제안이 겹치기**: 같은 런에 서식 제안이 또 오면 `before`는 처음 값을 유지한다 (거부하면 제안 전으로).
- **수락·거부는 보통 편집이다**: 그 결과도 동기화·실행 취소가 된다. 제안 모드에서 수락해도 새 제안이 되지 않는다.
- **동시성**:
  - A가 제안을 수락하는 동안 B가 그 범위 안에 입력하면, 수락은 그때 범위에 든 원소에만 걸린다. 삭제 수락은 A가 본 원소 ID 목록으로 지우므로, B가 넣은 글자는 남는다.
  - 두 사람이 같은 제안을 동시에 수락하거나 거부하면 결과가 같아야 한다. 지우기는 멱등이고 주석 지우기도 멱등이다.
  - 한 사람은 수락하고 한 사람은 거부한 경우는 시나리오 시험으로 결과를 고정한다. 삭제 제안이라면 "지움"이 이긴다: 원소 삭제와 주석 삭제가 둘 다 일어난다.

### 4.3 보기 모드 (G4)

| 모드 | 화면 | 편집 |
|---|---|---|
| 제안 포함 (기본) | 삽입은 작성자 색 밑줄, 삭제는 취소선, 서식·문단 제안은 여백 표시 | 가능 |
| 최종본 | 모두 수락한 문서 | 읽기 전용 |
| 원본 | 모두 거부한 문서 | 읽기 전용 |

- 최종본·원본은 **파생 문서**로 만든다. 지금 문서를 복제해 모두 수락·거부를 적용하고 따로 조판한다.
- 레이아웃이 원소를 숨기는 필터를 두면 캐럿·위치 대응이 모든 경로에 퍼진다. 그래서 그 방식은 쓰지 않는다.
- 파생 문서는 문서 판이 바뀌면 버리고, 다시 보일 때 만든다. 1,000쪽 복제 + 조판이 1초 안이어야 한다 (지금 처음 조립은 1만 문단 약 0.3초).

### 4.4 제안 창

- 댓글 창(§3.2)에 제안도 놓는다. 항목은 작성자·시각·요약("‘…’ 넣음", "굵게")과 수락·거부 단추다.
- 명령: `acceptSuggestion(id)`·`rejectSuggestion(id)`, `acceptAll(author?)`·`rejectAll(author?)`, `suggestions()`.

### 4.5 블록 이동·표 구조 (4-8)

- 블록 이동 제안: 이동은 바로 하되 (구획 순서 연산, 09 §6), 옮긴 범위에 `{ kind: 'move', from }`을 표시한다. `from`은 원래 자리 문단 첫 원소의 `Position`이다. 거부하면 되돌려 옮기고 (실행 취소의 이동 연산과 같다), 원래 자리에는 "옮겨 간 자리" 표시를 그린다.
- 표 행·열: 넣은 행·열에 `{ kind: 'insert' }`를 표의 행·열 ID로 둔다 (표 레코드 주석). 지우기는 지운 표시를 미루고 `{ kind: 'delete' }`로 둔다. 표 레코드 쪽 주석 키는 `table`·`row`/`col`이다.

## 5. 버전 이력 (G5)

### 5.1 자동 버전과 이름 붙인 버전

- 서버가 방마다 **버전 목록** `<방>/versions.json`을 둔다. 항목은 `{ id, epoch, frontiers, time, authors: [사용자 id], name?, auto }`이다.
- 자동 버전을 남기는 때:
  - 편집이 멈춘 뒤 10분 (조절 가능)
  - 방이 빌 때
  - 새 판 압축 직전
- 이름 붙인 버전은 사용자가 지금 상태에 이름을 단다 (`POST /<방>/versions`).
- 작성자: 서버가 연결마다 Loro 피어 ID → 사용자를 기록한다 (`<방>/peers.json`). 버전의 `authors`는 앞 버전과의 사이에 들어온 변경의 피어들이다 (`doc.getChangeAt`·`travelChangeAncestors`로 구한다).
- 새 판 압축은 이력을 끊는다 (09 §9). 앞 판의 버전은 `epochs/<판>/final.bin` 위에서 그 `frontiers`로 연다. 압축이 버전 목록을 지우지 않는다.

### 5.2 보기

- `GET /<방>/versions/<id>` → 그 시점의 스냅샷 (`doc.forkAt(frontiers).export({ mode: 'snapshot' })`)
- 편집기는 이것으로 **읽기 전용 문서**를 만들어 같은 조판으로 보여 준다 (최종본 보기와 같은 길).

### 5.3 비교

- 두 버전 A → B: Loro `diff(A, B)`가 컨테이너마다 델타를 준다.
  - 텍스트: retain·insert·delete
  - 맵: 키 변경
  - 리스트: 구획 순서
- 텍스트 델타를 B 문서 위의 **비영속 제안 주석**으로 바꾼다. insert는 삽입 표시이고, delete는 A에서 그 글을 가져와 B에 "지워진 글" 표시로 넣는다.
  - 표시는 파생 문서 안에서만 넣는다. 비교 화면은 그 파생 문서를 읽기 전용으로 보여 준다.
- 서식(마크)과 문단 속성 변경은 서식·문단 제안 표시로, 구획 이동은 이동 표시로 바꾼다.
- 원소 ID(Loro) 기준이라 텍스트 diff 추정이 없다. 시험: 무작위 편집 뒤 A에 비교 결과를 "모두 수락"하면 B와 같은 정본이다.

### 5.4 복원

- 같은 판이면 Worker의 Loro에서 `revertTo(frontiers)`를 부른다. 그 결과는 새 변경이 되고, 다른 피어에는 보통 원격 변경으로 간다. 이력은 지우지 않는다.
- 편집기에서는 원격 변경처럼 반영하고, 그 사용자의 실행 취소 기록에 "복원" 한 단계로 넣는다. 되돌리면 복원 직전 frontiers로 다시 `revertTo`한다.
- 앞 판의 버전이면 그 정본을 지금 판 위에 재기반한다 (09 §9의 재기반: 텍스트 차이 → 서식 차이). 표·주석도 옮긴다.

### 5.5 보존

- 05 O-15: 업데이트 로그를 압축하면 그 앞 시점으로는 `forkAt`할 수 없다.
- 4단계 기본: 자동 버전은 30일 동안 그 판의 스냅샷과 frontiers로 보존한다. 이름 붙인 버전은 지우지 않는다. 새 판 압축은 앞 판 파일을 지우지 않는다 (지금과 같음).
- 크기 상한과 정리는 4-6에서 정한다.

## 6. 권한 (G6, 05 O-14)

- 역할은 `edit`·`comment`·`view`다. 4단계에는 계정이 없으므로 방 설정(`<방>/access.json`)에 **토큰 → 역할**을 두고, 연결 URL에 토큰을 싣는다. 토큰이 없으면 `edit`다 (지금과 같음, 개발용).
- 서버는 받은 업데이트를 방 문서에 넣기 전에 **임시 포크**에 넣어 본다. 그리고 바뀐 컨테이너를 확인한다 (`doc.diff(before, after)`의 컨테이너 목록).
  - `view`: 모든 변경을 거부한다.
  - `comment`: `annotations`(댓글 종류만)·`threads`·`msgs:*` 밖의 변경을 거부한다.
- 거부하면 연결에 "읽기 전용" 응답을 보낸다. 클라이언트는 미뤄 둔 로컬 변경을 버리고 서버 상태로 다시 맞춘다 (재접속의 판 맞추기와 같은 길).
- 편집기의 `readOnly`·`commentOnly` 모드: 입력·서식 명령을 막고, 댓글 명령만 연다. 제안 모드는 `edit`가 필요하다 (제안도 본문 변경이므로).
- 비용: 업데이트마다 포크 + diff. 묶음(50 ms)마다 한 번이므로 1,000쪽 문서에서 몇 ms이고, 10만 문단에서 재 본다 (4-7 벤치).

## 7. 프레즌스 확장 (G7)

- 프레즌스 상태에 `story`를 더한다. 셀·머리말·각주 스토리의 커서는 그 스토리 Loro 텍스트의 커서다.
- 편집기는 원격 캐럿을 그 스토리 레이아웃에 그린다. 머리말이면 상대가 편집 중인 쪽에만 그린다 (프레즌스에 쪽 번호도 싣는다).
- 접속자 목록: 이름·색·지금 스토리. 누르면 그 사람 캐럿으로 스크롤한다 (따라가기는 그 사람 캐럿이 움직일 때마다 스크롤하는 것이다).

## 11. 4-1 결과: 주석 레이어

### 구현

- **모델** (`@quire/model` `annotations.ts`, `document.ts`):
  - `Document`가 주석 표를 가진다: `annotate`·`updateAnnotation`·`unannotate`. 연산은 `{ type: 'annotation', id, before, after }`이고 실행 취소 기록에 든다.
  - 위치는 그 스토리 Doc의 `Position`이다. 시작은 첫 글자의 `before`, 끝은 마지막 글자의 `after`이다. 그래서 범위 앞뒤에 입력한 글자는 밖에 있다 (§2.1의 댓글 규칙과 같은 결과).
  - **고아**: 범위 안 글자가 모두 지워져 범위가 접히거나, 원격에서 끝 없이 받은 주석이다. 화면에 그리지 않고 표에는 남는다. 실행 취소로 글자가 돌아오면 범위도 돌아온다.
  - Doc 고리 세 개로 원소 ID가 바뀌는 경우를 따라간다.
    - 꼬리 옮기기로 ¶가 새 ID를 받을 때: `onRemap`
    - 지운 원소가 되살아날 때: `onRevive`
    - 로컬 삭제로 기준 원소가 지워질 때: `onDelete`. 살아 있는 옆 글자로 다시 건다. 실행 취소 연산이라 되돌리면 위치도 돌아온다.
  - `annotationRanges()`: 모든 주석의 화면 범위(스토리별 시작 순)를 문서 판·주석 판마다 캐시한다.
- **동기화** (`@quire/sync` `annotations.ts`):
  - Loro 맵 `annotations`에 키 `<id>|type/story/start/end/data`를 둔다. 커서는 Loro 커서를 인코딩한 바이트열이다 (base64가 아니라 `Uint8Array` 그대로).
    - 시작은 첫 글자 `getCursor(u16, 0)`, 끝은 마지막 글자 `getCursor(lastU16, 1)`이다.
    - 지우기는 `type` 키 삭제로 표시한다.
  - **브리지**: 로컬 주석 변경을 맵에 쓰고, 원격 변경과 텍스트가 지워진 스토리의 주석을 다시 푼다.
  - **Worker** (`core`·`client`):
    - 주석 변경은 정의 맵과 같은 길을 탄다. 로컬 변경이 가는 중이면 그 주석의 원격 값을 미룬다.
    - ack에는 로컬로 바꾼 주석의 적용 뒤 상태가 실린다.
  - 정본은 07의 모양이다: `{ id, type, start: { story, offset }, end: { story, offset }, data }`. 고아는 `story`만 쓴다. 표 셀은 정본 셀 이름으로 쓴다.
  - 새 판 압축(`compactDocument`)은 새 Loro에서 커서를 다시 만든다.
- **O-32 결정 (지워진 기준 글자)**: 피어마다 "있던 자리"를 다르게 풀 수 있어서 다음 세 규칙을 둔다.
  - 로컬 삭제는 그 자리에서 살아 있는 글자로 다시 건다 (`onDelete`).
  - 원격에서 받은 커서가 지워진 글자를 가리키면(`dead`), 받은 피어가 살아 있는 글자로 다시 써서 보낸다 (`rewriteRange`). 모든 피어가 같은 범위를 쓰므로 같은 값으로 모인다.
  - 범위가 접히면 고아다.
- **Worker의 같은 모양 원소**: 메인은 원격 연산을 변환해 적용한다. 같은 글자가 이어질 때 메인과 Loro가 서로 다른 원소를 지우거나 넣을 수 있다. 그러면 원소 ID 기준인 주석 범위가 어긋난다.
  - Worker는 텍스트 변경 자리 근처의 주석을 다시 풀어 원격 항목과 ack에 싣는다 (`annsResync`).
  - 메인은 지금 범위와 비교해 다른 것만 다시 건다.
- **Worker 주석 위치 캐시**: Worker는 주석마다 Loro 위치(u16)를 캐시한다. 로컬·원격 텍스트 변경마다 위치를 옮기고, 바뀐 자리에 닿은 주석만 커서로 다시 푼다.
  - 처음에는 입력마다 모든 주석 커서를 풀었다. 벤치에서 주석 300개에 입력 한 번 270 ms가 나왔다.
- **큰 텍스트 넣기** (`insertChunked`): 새 문서, 새 판 스토리, 큰 붙여넣기는 텍스트를 64K 조각으로 나눠 뒤 조각부터 넣는다.
  - Loro는 한 피어가 이어 넣은 글자를 한 원소로 합치고, 커서↔위치 변환 때 그 원소 안을 앞에서부터 센다. 1.5M자를 한 번에 넣은 문서에서 `getCursor` 1.5 ms, `getCursorPos` 0.6 ms였다.
  - 거꾸로 넣으면 원소가 합쳐지지 않는다. 조각이 작을수록 변환이 빠르지만 스냅샷 압축이 나빠진다. 8K에서는 스냅샷이 30–800% 커졌고, 64K는 +4–8%다.
  - 동기화 벤치(1만 문단)도 빨라졌다.
    - 묶음 내보내기: 1.31 → 0.05 ms
    - 묶음 가져오기 + Doc 적용: 1.44 → 0.14 ms
    - 새 판 만들기: 776 → 281 ms
    - `.quire` 크기는 그대로다.
- **그리기** (`editor.ts`):
  - 줄마다 그 스토리의 주석 범위를 형광펜 다음에 칠한다. 댓글은 노란색, 그 밖은 파란색이고, `focusAnnotation`으로 고른 것은 진하게 칠한다.
  - 겹친 범위는 칠이 겹쳐 진해진다. 문단 끝까지 걸친 범위는 ¶ 자리도 조금 칠한다.
  - 공개 API: `annotate(type, data)`, `unannotate(id)`, `annotationsAtCaret()`, `annotations()`, `focusAnnotation(id)`.
- **플레이그라운드**: 도구 막대에 "주석"(선택 범위에 강조 주석)과 "주석 지우기"(캐럿이 걸친 주석)를 더했다.

  - 플레이그라운드에서 겹친 두 주석이 칠해지고 겹친 곳이 진해진다. 범위 안 입력으로 넓어지고, 실행 취소·다시 실행된다.
  - 협업 데모: 피어 A가 건 댓글 주석이 피어 B에 같은 범위로 칠해진다. B가 범위 안에 입력한 뒤에도 두 피어의 범위가 같다.

### 다음 (남은 것)

- 주석이 수천 개일 때: 화면 범위를 입력마다 모두 다시 풀지 않게 한다. 바뀐 스토리만 다시 풀거나, 오프셋을 변경으로 옮기는 증분 캐시를 둔다 (§2.1의 구간 트리).
- 재기반(오프라인 편집을 새 판으로)은 주석을 옮기지 않는다. 새 판의 주석(서버가 압축한 시점)이 남고, 오프라인에서 바꾼 주석은 잃는다 (§2.3).
- 정본: 덮인 셀(병합으로 주인 셀에 합쳐 저장)에 걸린 주석은 위치를 잃어 쓰지 않는다.
- 오른쪽 여백 표시, 접근성 미러(`<mark>`, `aria-describedby`)는 4-2(댓글 창)와 함께 한다.
- 원격 커서가 아직 받지 못한 글자를 가리키는 경우: Worker 경로는 Loro가 한 곳이라 생기지 않는다. 브리지 경로는 그 주석을 다음 원격 변경 때 다시 푼다.

## 12. 4-2 결과: 댓글

### 구현

- **모델** (`@quire/model` `comments.ts`, `document.ts`):
  - 스레드·메시지는 평평한 키 표다. §3.1은 메시지를 Loro 리스트로 두자고 했지만, 주석(§2.2)처럼 키 하나에 값 하나인 맵으로 바꿨다.
    - 키: `<스레드>|anchor`·`|resolved`·`|deleted`, `<스레드>|m|<메시지>|author`·`|time`·`|text`·`|edited`·`|deleted`
    - 동시 답글은 메시지 ID가 달라 모두 남는다. 차례는 (시각, ID)이므로 모든 피어에서 같다.
    - 고치기와 지우기도 키가 달라서, 같은 때 고치고 지우면 둘 다 남는다 (지운 메시지로 보이고 고친 글은 이력에 남는다).
    - 이렇게 해서 동기화·실행 취소·Worker 경로를 주석과 같은 길로 탄다. 리스트의 중첩 컨테이너 이벤트를 다룰 일이 없다.
  - 연산 `{ type: 'comment', key, before, after }`는 실행 취소 기록에 든다.
  - `addThread`(댓글 주석 + 기준 + 첫 메시지), `addMessage`, `editMessage`, `deleteMessage`, `resolveThread`, `deleteThread`(주석을 지우고 스레드는 지운 표시)
  - `threads()`는 키 표에서 스레드를 만들고 캐시한다. `thread(id)`는 색인으로 찾는다.
- **동기화** (`@quire/sync` `comments.ts`):
  - Loro 맵 `comments`에 키를 그대로 둔다 (값은 JSON, 작성자는 객체).
  - 브리지: 로컬 키를 맵에 쓰고, 원격 맵 변경을 그대로 적용한다.
  - Worker: `LocalChange` `cmt`를 쓰고, ack에는 로컬로 바꾼 키의 적용 뒤 값이 실린다. 원격 항목에는 바뀐 키가 실린다. 그 키의 로컬 변경이 가는 중이면 원격 값을 미룬다.
  - 정본: `threads` 배열 (`{ id, anchor, resolved, deleted, messages: [{ id, author, time, text, edited?, deleted? }] }`). 07의 `annotations`와 함께 쓴다.
  - 새 판 압축은 키를 그대로 옮긴다.
- **편집기** (`editor.ts`):
  - 명령:
    - `addComment(text)`: 선택 범위에 스레드를 만든다. 실행 취소 한 단계.
    - `replyComment`, `editComment`, `deleteComment`(첫 메시지면 스레드 지우기), `resolveThread`: 실행 취소 기록에 넣지 않는다. 댓글 대화는 문서 편집이 아니다 (Google Docs처럼).
    - `deleteThread`: 실행 취소 한 단계. 글을 지운 것처럼 되돌린다.
  - 작성자는 `EditorOptions.user`다. 협업 데모는 피어 이름·색을 넘긴다.
  - 해결했거나 지운 스레드의 범위는 칠하지 않는다.
  - `threads()`: 열린 스레드 목록. 범위 시작의 문서 y 순이고 고아는 뒤에 온다.
    - 본문 밖 스토리의 y는 그 스토리가 걸린 자리다: 표는 표 문단, 각주는 참조 자리, 머리말은 첫 쪽 위, 꼬리말은 첫 쪽 아래.
  - 그 밖: `threadsAtCaret()`, `focusThread`, `revealThread`(범위를 선택하고 스크롤), `selectionY()`, `scrollElement`
- **댓글 창** (플레이그라운드 `comments-pane.ts`):
  - 편집기와 상태 창 사이의 열이다.
  - 열린 스레드 카드는 범위 y − 스크롤에 맞춰 놓는다. 겹치면 고른 카드를 제자리에 두고 위아래로 민다.
  - 해결함·고아 스레드는 아래 접힌 목록에 모은다.
  - 캐럿이 댓글 범위에 들어가면 그 스레드를 고른다. 카드를 누르면 범위로 간다.
  - 새 댓글: "댓글 달기" 또는 Ctrl+Alt+M → 선택 y에 쓰는 카드가 열린다 (Ctrl+Enter 달기, Esc 취소).
  - 카드: 답글, 해결·다시 열기, 메시지 고치기·지우기. 쓰다 만 글은 다시 그려도 남는다.

### 검증

- 댓글 시험 9개 (`packages/sync/src/comments.test.ts`):
  - 모델: 스레드·답글 차례·고치기·지우기·해결, 스레드 지우기와 되돌리기, 만들기 되돌리기, 고아 스레드와 되돌리기
  - 브리지: 동시 답글 둘 다 남고 차례가 같음, 같은 메시지 고치기 ∥ 지우기, 해결, 글이 지워져도 스레드가 남음(늦게 참여한 피어도), 각주 범위
  - Worker 무작위 메시지 타이밍: 답글을 하나도 잃지 않고 메인 문서끼리, Loro와 같다. 시드 3개를 고정했고, 30개까지 돌려 확인했다.
