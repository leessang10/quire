# 09. CRDT 통합

- 상태: 5단계 완료 (텍스트, 구획, 공유 위치, Worker·중계 서버, 저장)
- 근거: ADR-0003, ADR-0004, [V4 결과](../spikes/phase0-crdt.md), 05 §2, 07
- 다음: 주석·댓글·변경 추적·버전 이력·권한은 [14. 협업과 이력](14-collaboration-history.md)

## 1. 목표

편집 모델(`@quire/model`의 `Doc`)과 Loro 문서를 이어, 여러 피어의 편집이 같은 문서로 수렴하게 한다.
키 입력 지연(현재 1만 쪽에서 p50 0.2 ms)을 늘리지 않는다.

## 2. 구조

```
  에디터 ──편집──▶ Doc (화면 상태, 즉시 반영)
                    │ 변경 기록 (UTF-16 위치)        ▲ 원격 델타 적용
                    ▼                                │
               SyncBridge ──── LoroDoc (같은 스레드) ─┘
                    │  50 ms 묶음: 내보내기 / 가져오기
                    ▼
                 전송 (onUpdate / receive)
```

- **Doc이 화면의 원본**이다. 로컬 편집은 Doc에 먼저 반영하고, 같은 변경을 Loro 텍스트에 바로 적용한다 (Loro 로컬 입력 + 커밋은 약 0.03–0.1 ms).
- Loro 비용의 대부분인 **업데이트 내보내기·가져오기**(1만 쪽에서 1회 약 16 ms, V4 결과 3)는 50 ms마다 한 번으로 묶는다.
- 원격 업데이트를 가져오면 Loro가 텍스트 델타(retain / insert / delete)를 이벤트로 준다. 브리지가 이를 Doc에 적용한다. 가져오기 이벤트는 동기로 처리해, 다음 로컬 편집 전에 Doc과 Loro가 같은 상태가 되게 한다.
- **위치 단위**: Loro JS의 텍스트 인덱스와 이벤트 델타는 UTF-16 단위다. Loro의 `convertPos`는 큰 문서에서 임의 위치 변환에 1회 수십 ms가 걸려 쓸 수 없다. Doc이 청크마다 UTF-16 길이를 들고 있어 기존 위치 찾기(O(청크 수))와 같은 비용으로 변환한다.
- **ID**: Doc 원소 ID와 Loro 원소 ID는 따로다. 두 쪽은 "살아 있는 원소 열"(위치)로 맞춘다. Doc ID는 로컬 선택 영역·실행 취소용이고, 피어 사이에서 공유하는 위치(원격 커서, 주석 범위)는 Loro 커서로 표현한다(3단계).
- 같은 스레드에서 시작한다. 1만 쪽 문서에서 50 ms마다 16 ms가 드는 것은 Worker로 옮길 때 해결한다(4단계). Worker로 옮기면 Doc과 Loro 사이에 비동기 지연이 생기므로, 아직 반영되지 않은 로컬 변경 위로 원격 델타를 옮기는 변환이 필요하다.

## 4. 1단계 세부

### Doc 변경 기록

`Doc.observe(fn)`로 등록한 함수가 원소 열이 바뀔 때마다 `RawChange`를 받는다.

```ts
type RawChange =
  | { kind: 'insert'; at: number; text: string }   // at: UTF-16 위치 (구획 표식 포함)
  | { kind: 'delete'; at: number; len: number };   // len: UTF-16 길이
```

- 순서대로 적용하면 Loro 텍스트가 Doc의 살아 있는 원소 열과 같아지도록 보낸다 (여러 구간 삭제는 뒤에서부터, 되살리기는 앞에서부터).
- 원격 델타를 적용하는 동안에는 기록하지 않는다.

### 원격 델타 적용

`Doc.applyDelta(delta)`: UTF-16 위치로 원소를 찾아 새 원소를 넣거나 묘비로 만든다. 문단 목록은 로컬 편집과 같은 증분 갱신을 쓰므로 레이아웃 힌트도 그대로 나온다. 선택 영역은 Doc ID 기준이라 원격 편집 뒤에도 제자리를 지킨다.

### 1단계 한계

- 구획 연산(문단 이동·숨김)은 동기화하지 않는다. 브리지가 붙은 Doc은 구획 연산을 거부한다.
- 실행 취소는 Doc 자체 기록으로 한다. 내가 지운 글자를 되살리면 Loro에는 새 글자로 들어간다(V4 D5와 같은 성질).

## 5. 1단계 결과

### 구현

- `@quire/model`: 청크별 UTF-16 길이, `observe()`(변경 기록), `applyDelta()`(원격 델타), `rawText()`(Loro 텍스트와 비교용), `segmentsEnabled`.
- `@quire/sync`: `SyncBridge.create(text)` / `fromSnapshot(snapshot)`, `receive(update)`, `flush()`, `onUpdate`, `onRemoteChange`, `snapshot()`.
- `@quire/editor`: `doc` 옵션(브리지가 붙은 Doc 편집), `docChanged()`(원격 변경 뒤 다시 배치·그리기).
- 플레이그라운드 `/collab.html`: 두 편집기를 가짜 네트워크(지연, 오프라인)로 잇는 데모.

### 발견한 것

- 여러 업데이트를 `importBatch`로 한꺼번에 가져오면 Loro 이벤트가 `by: 'import'`가 아니라 **`'checkout'`**으로 온다. 처음 구현은 `import`만 처리해 무작위 시험 10개가 모두 어긋났다 → 로컬(`'local'`)이 아닌 이벤트는 모두 적용한다.
- 가져오기 이벤트는 동기로 온다 (Node 빌드, 브라우저 빌드 모두. 브라우저 빌드는 메서드가 끝날 때 대기 중인 이벤트를 처리한다). 시험으로 확인.
- 브라우저: `loro-crdt` 브라우저 빌드는 `.wasm`을 ES 모듈로 가져와 Vite 플러그인이 필요하다. 플레이그라운드는 wasm을 담은 `loro-crdt/base64` 빌드를 별칭으로 쓴다(협업 페이지 묶음 4.9 MB). 제품 배포에서는 wasm을 따로 불러오는 방식으로 바꾼다.

### 검증

- 단위 시험 6개: 전파, 동시 편집과 로컬 캐럿 유지, 이모지(UTF-16), 가져오기 직후 일치, 실행 취소·다시 실행 전파, 구획 연산 거부.
- 무작위 시험 10개: 피어 3개 × 300단계 (입력, 삭제, 실행 취소·다시 실행, 묶음 처리, 일부만 전달). **매 단계 모든 피어의 Doc = Loro 텍스트**, 끝에 전부 전달하면 세 피어 모두 같은 문서, 문단 목록·불변식 일치.
- 브라우저 데모: 양쪽 동시 입력, 지연 300 ms, 한쪽 오프라인 상태에서 같은 문단을 양쪽이 고친 뒤 재연결 → 두 입력 모두 남고 같은 문서로 수렴.

## 6. 2단계 결과: 구획 동기화

### Loro 표현

| 요소 | 표현 |
|---|---|
| 구획 표식 | 텍스트 'body'의 U+E000 글자 + 마크 `seg=<구획 키>` (`expand: none`). 원격 델타에 키가 함께 실려 오므로 ID 대응표가 없다 |
| 구획 순서 | 이동 리스트 'order' (구획 키 + 끝 고정 항목 `$end`). 목록에 없는 구획은 저장 순서상 다음 구획 앞 |
| 숨김·자리표시·사용됨 | 맵 'hidden', 'placeholder', 'used' (키 → true) |
| 처음 문서 | `[사용자 문단들 BRK(t)][¶ BRK(p)][¶ 보초]` — t는 순서 목록에, p는 자리표시 |

구획 키는 피어마다 겹치지 않는다: 로컬에서 나눈 구획은 Doc 원소 ID(`<피어>:<카운터>`, Doc의 피어 이름 = Loro 피어 ID), 처음 문서의 두 구획은 `<피어>.t`, `<피어>.p`.

### 편집 모델 변경

- **보초·자리표시** (V4 후속 4): 동기화 문서(`Doc.fromRaw`)의 마지막 구획은 보이지 않는 보초다. 보이는 내용이 없으면 첫 자리표시를 빈 문단으로 보이고, 입력하면 사용됨으로 표시하고 새 자리표시를 만든다. 동기화 문서는 모든 문단을 숨겨도 된다.
- **가상 ¶**: 동시 편집으로 ¶ 없이 끝난 구획이 생길 수 있다 (A가 문단을 옮기는 동안 B가 그 문단과 다음 문단을 병합). V4 M4는 구획 끝을 문단 끝으로 보는데, 편집 모델은 구획을 이어 붙여 보였기 때문에 그 문단이 엉뚱한 문단과 붙었다 (S24 첫 실행). 동기화 문서에서는 그런 구획 끝에 **화면에만 있는 ¶**를 둔다. 캐럿은 그 구획의 표식 원소 앞에 놓이고, 지우면 기존 꼬리 옮기기가 된다.
- **실행 취소 연산**: 구획 순서 전체를 되돌리면 그사이 다른 피어가 옮긴 문단까지 되돌린다. 연산을 `move`(옮긴 구획들, 넣을 자리, 되돌릴 자리)와 `hidden`(바꾼 구획들)로 바꿨다. 자리는 구획 키가 아니라 **그 자리 문단의 첫 원소**로 기록한다: 다른 피어가 뒤 구획을 나누면 키는 뒷부분에 남기 때문이다 (첫 구현은 되돌린 문단이 엉뚱하게 맨 앞으로 갔다).
- **원격 적용의 예외 경로**: 원격 피어에게는 마지막이 아니던 ¶가 여기서는 화면 마지막 ¶일 수 있고, 원격 피어가 이쪽의 마지막 구획을 통째로 비울 수도 있다. 숨긴 구획·보초·자리표시를 나누는 원격 표식은 화면을 바꾼다. 이런 경우(열림 상태·대체 자리표시·보임 상태가 바뀜, 화면 끝까지 지움, 가상 ¶를 덮는 삭제)는 문단 목록을 처음부터 다시 만든다. 무작위 시험에서 하나씩 찾아 고쳤다.

### 남은 것

- 두 피어가 같은 문단을 같은 자리에서 동시에 나누면(같은 문단을 동시에 옮기거나 숨김) 빈 구획이 생기고 한쪽 연산만 그 문단에 적용된다 (결정적이지만 어느 쪽인지는 Loro의 동시 삽입 순서에 달림). V4에서 별칭 규칙으로 막으려던 경우이며, 별칭 규칙은 더 큰 문제(S31)가 있어 뺐다.
- 꼬리 옮기기와 가상 ¶ 주변의 문단 목록 갱신은 문단 목록 전체를 다시 만든다 (드문 경우지만 1만 쪽 문서에서는 수십 ms).

## 7. 3단계 결과: 공유 위치·프레즌스

### 공유 위치

피어 사이에서 같은 자리를 가리키는 값은 **Loro 커서**(`LoroText.getCursor`, 인코딩하면 12바이트 안팎)다. 커서는 글자 하나(Loro 원소 ID)에 붙고, 받는 쪽은 `getCursorPos`로 자기 문서에서의 현재 자리를 구한다. Doc 원소 ID는 피어마다 달라 공유할 수 없다(§2).

| API | 동작 |
|---|---|
| `Doc.u16OfOffset(offset)` | 화면 오프셋 → 그 자리 원소의 UTF-16 위치 (살아 있는 원소 열 = Loro 텍스트). 가상 ¶ 자리는 그 구획의 표식 원소 |
| `Doc.offsetOfU16(u16)` | UTF-16 위치 → 화면 오프셋. 숨긴 구획·보초 안이면 그 구획이 놓였을 자리, 결과는 0..maxCaret |
| `SyncBridge.cursorAt(offset)` | 화면 오프셋 → 인코딩한 커서. 캐럿 바로 **뒤** 글자에 붙는다: 그 자리에 누가 입력해도 캐럿은 그 글자 앞에 남으므로, 상대가 입력하는 동안 상대 캐럿이 입력한 글자 뒤를 따라간다 |
| `SyncBridge.resolveCursor(bytes)` | 커서 → 현재 화면 오프셋. 아직 받지 못한 연산을 가리키면 `null`. 기준 글자가 지워졌으면 그 글자가 있던 자리 |

주석 범위는 두 커서(시작, 끝)로 표현한다. 시험: 범위 앞과 안쪽 근처에 다른 피어가 입력해도 범위가 같은 글자들을 덮는다. 주석 자체(저장 위치, 표시)는 아직 없다.

Loro 커서의 성질 (탐색 시험, loro-crdt 1.17.1)
- 위치는 UTF-16 단위다 (텍스트 인덱스와 같다).
- `getCursorPos`는 1,200만 글자 문서에서 1회 약 0.06 ms다. `convertPos`(1회 26 ms)와 달리 바로 쓸 수 있다.
- 모르는 연산을 가리키는 커서는 `undefined`를 준다 (예외 아님).

### 프레즌스 (`@quire/sync`의 `Presence`)

- 상태: 이름, 색, 선택 영역의 두 끝(커서). 문서 기록에는 남지 않는다.
- **순서 규칙**: 피어마다 자기 키만 쓰므로, 보내는 피어의 일련번호(시작값 = 시각×1000, 갱신마다 +1)가 큰 쪽이 이긴다. 늦게 도착한 옛 상태는 버린다. 떠날 때는 빈 상태를 보낸다.
  - 처음에는 Loro `EphemeralStore`를 썼다. 그런데 이 저장소는 시각(ms)으로 비교해서, 받는 쪽이 같은 밀리초 안의 두 번째 갱신을 버렸다. 탐색 시험에서 200회 중 199회가 유실됐다. 캐럿은 한 틱에 여러 번 바뀌므로 쓸 수 없었다.
- **보내는 시점**: 캐럿은 방금 입력한 글자 바로 뒤에 붙는 일이 많다. 그 글자가 담긴 문서 업데이트보다 프레즌스가 먼저 도착하면, 받는 쪽은 위치를 풀 수 없다. 그래서 아직 내보내지 않은 로컬 변경이 있으면 프레즌스를 다음 묶음 처리(flush) 직후에 보낸다(`SyncBridge.onFlush`). 같은 연결이면 순서가 지켜진다.
- **풀 수 없을 때**: 다른 경로로 와서 문서 업데이트보다 먼저 도착한 경우 등에는 마지막으로 푼 자리를 Doc 위치로 들고 있다가 그 자리에 그린다. 업데이트가 도착하면 다시 푼다.
- **시간 초과**: 받는 쪽 시계로 30초 동안 소식이 없는 피어는 지운다. 각 피어는 15초마다 자기 상태를 다시 보낸다.
- **풀기 캐시**: `remotes()`는 문서 판과 프레즌스 판이 같으면 이전 결과를 돌려준다. 화면을 다시 그릴 때마다 다시 풀지 않는다.

### 편집기

- `EditorOptions.onSelectionChange(anchor, head)`는 사용자가 선택을 바꿀 때만 호출된다. 원격 편집으로 오프셋만 바뀐 경우는 커서가 알아서 따라가므로 호출하지 않는다.
- `setRemoteCarets(list)`는 상대의 선택 영역(색 22% 투명도), 캐럿(2px), 이름표를 그린다. 이름표 글자색은 배경색과의 대비로 흰색과 검정 중에서 고른다. 화면에 보이는 문단에 있는 캐럿만 그린다.
- 협업 데모(`collab.html`)는 프레즌스를 문서 업데이트와 같은 지연으로 보낸다. 오프라인 동안에는 마지막 상태만 들고 있다가 재연결할 때 문서 업데이트 뒤에 보낸다.

### 사용자별 실행 취소

이미 Doc의 실행 취소가 사용자별이다. 각 편집기의 `History`는 그 사용자가 만든 연산만 기록한다.
- 입력: 넣은 원소 ID들
- 삭제: 지운 원소 ID들
- 이동: 옮긴 구획과 원소 ID로 기록한 자리
- 숨김: 숨긴 구획

되돌리면 그 원소·구획만 바뀌고, 그사이 다른 피어가 한 편집은 그대로 남는다. 시험: A가 입력하고 B가 근처에 입력한 뒤 A가 되돌리면 B의 글자는 남는다. 2단계의 무작위 시험도 실행 취소를 섞어 수렴을 본다. Loro `UndoManager`는 쓰지 않는다. Doc이 원본이고 연산이 이미 ID 기준이기 때문이다.

한계: 삭제를 되돌리면 Doc은 같은 원소를 되살리지만, Loro에는 **새 글자로 입력**된다(1단계). 그래서 지운 글자에 붙어 있던 다른 피어의 커서나 주석 범위는 되살린 글자로 돌아오지 않고, 지운 자리에 남는다. 주석을 구현할 때는 되살린 글자에 범위를 다시 붙이는 규칙이 필요하다.

## 8. 4단계 결과: Worker 이전, 중계 서버, 재접속

### 구조

| 메인 스레드 | Worker | 서버 |
|---|---|---|
| `Doc`(화면의 원본), `SyncClient`: 로컬 변경 기록을 Worker로 보내고, Worker가 보낸 원격 변경을 위치 변환해 Doc에 적용 | `SyncCore`: Loro 문서, 내보내기·가져오기 묶음(50 ms), 프레즌스(커서 만들기·풀기), 네트워크 | `apps/sync-server`: 방마다 Loro 문서를 들고 업데이트를 합쳐 전한다 |

- Worker 파일은 `serveSyncWorker(self)` 한 줄이다. 메인은 `startSyncWorker(worker, config)`로 시작하고, 첫 문서(`init`)를 받으면 `SyncClient`를 얻는다.
- 네트워크 모드는 두 가지다.
  - `relay`: 업데이트를 메인으로 넘긴다. 한 페이지에 피어를 여럿 두는 협업 데모가 이 모드로 지연·오프라인을 흉내 낸다.
  - `ws`: Worker가 직접 WebSocket으로 서버에 붙는다.
- 같은 스레드 `SyncBridge`는 시험과 스파이크(모델 Q)용으로 남겨 둔다. Loro 문서 모양과 로컬 변경 적용은 두 경로가 같은 코드(`shape.ts`)를 쓴다.

### 위치 변환 (`ot.ts`, `protocol.ts`)

Worker로 옮기면 Doc과 Loro 사이에 비동기 지연이 생긴다. 메인은 Worker에 아직 닿지 않은 로컬 변경을 들고 있을 수 있고, Worker는 메인이 아직 받지 못한 원격 변경을 들고 있을 수 있다. 두 쪽 모두 같은 변환 함수로 위치를 맞춘다. 방식은 ot.js의 클라이언트·서버 구조다.

- **Worker의 기록 H**: 메인이 보낸 로컬 묶음(`ack`)과 가져온 원격 변경(`remote`)을 들어온 순서대로 쌓는다. 메인은 받은 H 항목 수(`rev`)를 센다.
- **메인 쪽**:
  - 로컬 묶음은 **한 번에 하나만** 보낸다. ack를 받기 전에 생긴 변경은 대기열에 쌓는다.
  - 원격 항목이 오면 보낸 묶음과 대기열에 대해 변환해 Doc에 적용한다. 보낸 묶음과 대기열도 원격 변경 뒤의 좌표로 바꾼다.
- **Worker 쪽**: 받은 묶음을 그 묶음의 `rev` 뒤에 쌓인 원격 항목들에 대해 변환한 뒤 Loro에 적용한다. 한 번에 하나만 오므로 그 사이 항목은 모두 원격이다.
- **결정성**: 두 쪽은 같은 함수를 같은 입력, 같은 순서로 쓰므로 결과가 같다.
  - 연산 단위는 UTF-16 위치의 삽입·삭제다. 구획 표식도 한 글자로 센다.
  - 삽입 안쪽을 덮는 삭제는 둘로 나뉜다.
  - 같은 자리에 양쪽이 넣으면 원격(Worker에 먼저 있던 것)이 앞이다.
- **구획 상태**: 순서·숨김·자리표시는 Worker가 통째로 보낸다. 메인에 아직 Worker에 닿지 않은 로컬 구획 변경이 있으면, 받은 상태는 그 변경이 빠진 옛것이다. 그래서 적용을 미루고 다음 묶음에 상태를 요청한다(`wantState`). 로컬 구획 변경이 반영된 상태를 ack로 받아 적용한다.
- **목록에 없는 구획**: 순서 목록에 없는 구획 앞으로 옮길 때 Worker에는 Doc이 없다. 그래서 Loro만으로 화면 순서를 계산해 넣을 자리를 정한다(`displayOrderFromLoro`, Doc의 규칙과 같다). 모두 주고받은 뒤에는 Doc의 순서와 같다는 것을 무작위 시험에서 확인한다. 편집 직후에는 잠깐 다를 수 있지만 순서 목록의 자리 보정에만 쓴다.
- **원격 캐럿**: Worker가 커서를 풀어 UTF-16 위치를 보낸다. 메인은 그 위치를 보낸 묶음과 대기열만큼 옮긴 뒤 Doc 위치로 들고 있는다. 풀 수 없으면 이전 자리를 유지한다.

### 중계 서버 (`apps/sync-server/src/server.ts`)

- 실행: `node apps/sync-server/src/server.ts [포트]` (기본 8787). Node 22.18 이상의 TypeScript 타입 제거 실행이다. (5단계부터는 §9의 명령)
- 의존성은 `loro-crdt`와 Node 내장 모듈뿐이다. WebSocket 프레임(RFC 6455)은 직접 처리한다: 마스크 해제, 조각 이어 붙이기, ping/pong, close.
- 방(URL 경로)마다 Loro 문서를 메모리에 둔다. 업데이트는 합친 뒤 다른 클라이언트에게 전한다. 프레즌스는 전하기만 하고, 새로 온 클라이언트에게 각자의 마지막 프레즌스를 보낸다. 연결이 끊기면 그 클라이언트의 캐럿을 지우라고 알린다(`GONE`).
- **맞추기**: 연결될 때마다 클라이언트가 버전 벡터를 보내면(`HELLO`), 서버는 클라이언트에 없는 업데이트와 서버의 버전 벡터를 보낸다(`SYNC`). 클라이언트는 서버에 없는 것을 서버 버전 벡터 기준으로 내보내 보낸다. 그래서 끊긴 동안 보내다 잃은 업데이트나, 서버가 재시작해 방을 잃은 경우도 다시 연결하면 맞춰진다.
- **빈 방**: 서버가 처음 내용을 만들 클라이언트를 하나 정한다. 다른 클라이언트는 내용이 올 때까지 기다린다.
- **재접속**: 0.5초에서 시작해 두 배씩, 최대 5초 간격으로 다시 연결한다. 끊긴 동안에도 편집은 계속되고, 상태 표시줄에 연결 상태가 보인다.

| 문서 | 메인: 글자 입력 p50 | 메인: 원격 묶음 변환 + Doc 적용 p50 | Worker: 원격 가져오기 p50 |

## 9. 5단계 결과: 저장, 정본 JSON, 새 판 압축

### 저장 층 (07 §1)

| 층 | 어디에 | 무엇 |
|---|---|---|
| A. 내부 저장 | 서버 방 디렉터리 (`apps/sync-server/src/store.ts`) | Loro 스냅샷 + 업데이트 로그, 판 기록 |
| B. 문서 파일 | `.quire` (`packages/sync/src/quire-file.ts`) | `document.json`(정본) + `history/crdt.bin` |
| 정본 JSON | `canonical.ts` | QuireDoc v1: 지금 모델이 담는 문단·텍스트 런만 |

### 서버 저장소

방 하나 = 디렉터리 하나 (`--data`, 기본 `.quire-data/`).

```
<방>/snapshot.bin          마지막 체크포인트의 Loro 스냅샷
<방>/log.bin               그 뒤의 업데이트 ([길이 u32][업데이트]…), 받는 즉시 덧붙임
<방>/document.json         방이 빌 때·압축할 때의 정본 JSON
<방>/epochs/<판>/base.bin  그 판의 처음 상태
<방>/epochs/<판>/final.bin 그 판의 마지막 상태 + next (다음 판 ID)
```

- **받은 업데이트는 곧바로 로그에 덧붙인다.** 브로드캐스트보다 먼저다. 서버가 죽어도 받은 것은 남는다.
- **체크포인트**: 업데이트 200개마다(조절 가능) 스냅샷을 쓰고 로그를 비운다. 임시 파일에 쓴 뒤 이름을 바꾸고, 스냅샷을 먼저 바꾼 다음 로그를 비운다. 어느 순간에 죽어도 잃는 것이 없다.
- **잘린 로그**: 덧붙이다 죽어 끝이 잘린 레코드는 읽을 때 버린다 (시험).
- **정본 JSON은 방이 빌 때만 쓴다.** 화면 텍스트 계산(`Doc.fromRaw`)이 10만 문단에서 1.2초 걸려, 편집 중에 쓰면 서버가 멈춘다. HTTP로 요청하면(`GET /<방>.json`) 그때 계산한다.
- **내리기**: 방이 `--idle` ms(기본 10초) 동안 비면 압축하고 메모리에서 내린다. 다음 연결 때 저장소에서 다시 읽는다.
- 메모리 저장소(`memoryStorage`)도 같은 인터페이스다. 시험과 라이브러리 기본값이 이것이다.

### 정본 JSON (`canonical.ts`, 07 §4)

- 문단 하나는 `{ "p": {}, "c": [{ "t": "…" }] }`이다. 빈 문단은 `"c": []`.
- 키를 사전순으로 고정하고 들여쓰기 2칸, 끝 줄바꿈으로 직렬화한다. 같은 문서는 늘 같은 바이트열이다. `stateHash`는 그 바이트열의 SHA-256이다.
- CRDT 원소 ID, 묘비, 구획 표식, 숨긴 구획은 들어가지 않는다. 정본으로 저장했다 다시 열면 구획이 둘(내용 + 자리표시)뿐인 깨끗한 문서가 된다.
- 지금 모델이 담을 수 없는 내용(표, 각주, 필드 같은 텍스트 런 아닌 것)은 열 때 오류로 알린다. 새 스키마(`version` > 1)는 읽기 전용으로 연다.

### `.quire` 파일 (`quire-file.ts`, `zip.ts`)

- ZIP 항목: `mimetype`(첫 항목, 압축 없음), `manifest.json`, `document.json`, `history/crdt.bin`(선택). 나머지는 deflate다.
- ZIP 쓰기·읽기는 직접 구현했다 (표준 `CompressionStream('deflate-raw')`). 시각을 고정해 같은 문서는 같은 파일이 된다.
- **여는 규칙 (07 §3)**: `crdt.bin`을 불러 그 화면 텍스트의 정본 해시를 구하고, `document.json`을 다시 정규화한 해시와 비교한다.
  - 같으면 CRDT로 연다. 이력과 협업 연속성이 유지된다.
  - 다르면 `crdt.bin`을 버리고 JSON에서 새로 만든다. 외부 도구가 JSON만 고친 경우다.
  - manifest의 해시를 믿지 않고 다시 계산하므로, JSON의 공백·키 순서만 바뀐 경우는 이력을 유지한다.
- 서버 HTTP:
  - `GET /<방>.quire`: 지금 문서를 파일로 내려받는다.
  - `PUT /<방>.quire`: 파일로 빈 방을 만든다. 내용이 있는 방이면 409, 새 포맷이면 422.

### 새 판 압축 (`epoch.ts`, V4 후속 3 R3)

편집 중에는 구획 표식·순서 항목·숨긴 구획·묘비를 지울 수 없다. 동시 연산이 가리키는 ID이기 때문이다(후속 3 C1–C3). 그래서 **아무도 없을 때 서버가 판을 바꾼다**.

1. 방이 비면 지금 문서의 화면 텍스트로 새 Loro 문서를 만든다(`compactLoro`). 판 ID는 문서 안 `meta.epoch`에 둔다 (첫 판은 `''`).
2. 옛 판의 마지막 상태(`final.bin`)와 새 판의 처음 상태(`base.bin`)를 남긴다.
3. 클라이언트는 `HELLO`에 자기 판을 넣는다. 판이 다르면 서버는 `SYNC` 대신 `REBASE`를 보낸다: 다음 판 ID, 옛 판 마지막 VV, 옛 판에서 클라이언트에 없는 업데이트, 다음 판 처음 상태.
4. **재기반 (Worker, `rebaseOnto`)**: 옛 판 업데이트를 가져오면 M = 옛 판 마지막 상태 F + 이 클라이언트의 변경이 된다. 새 판 처음 상태는 F의 화면 텍스트로 만들었으므로, 새 판 = 처음 상태 + diff(F → M)이다. 그다음 `HELLO`를 다시 보내 평소처럼 맞춘다.
5. 판이 여러 번 바뀌었으면 한 판씩 거쳐 간다 (판마다 next를 남김). 서버가 모르는 판이면 로컬 변경을 살릴 수 없다. 이때는 지금 문서를 받고 알린다(`lost`).

**메인 스레드 (hold → held → reset)**: 재기반하려면 메인의 Doc과 Worker의 Loro가 같은 순간이 필요하다.
- Worker가 `hold`를 보낸다. 그 전에 받아 둔 원격 변경은 먼저 메인에 넘긴다.
- 메인은 보낸 묶음과 대기열의 문서 변경을 모두 보낸다. 그것이 적용되면 `held`로 답하고, 그때의 화면 텍스트를 기억한다.
- `held` 뒤의 로컬 편집은 보내지 않고 Doc에만 둔다.
- Worker는 재기반한 새 문서를 `reset`으로 보낸다. 메인은 Doc을 새로 만들고, held 뒤의 로컬 편집(텍스트 차이)을 새 문서 좌표로 옮겨(`rebaseHunks`) 다시 적용한다.
- 편집기는 `setDoc`으로 문서를 바꾼다. 캐럿은 같은 화면 오프셋에 두고, 실행 취소 기록은 비운다 (옛 원소 ID를 가리키므로).

**diff (`diffText`)**: 문단 단위는 Myers diff다. 편집 거리 D에 비례하므로 큰 문서에서 몇 군데만 바뀐 경우에 빠르다. 바뀐 문단 구간 안은 글자 LCS로 나눈다. 문서 끝 ¶ 뒤에는 캐럿을 둘 수 없으므로, 끝에 닿는 변경은 같은 결과가 되게 한 칸 앞으로 옮긴다.

**한계**: 재기반은 화면 텍스트 차이로 옮긴다.
- 오프라인 동안의 **문단 이동은 "지우고 다시 넣기"**가 된다. 같은 문단을 다른 피어가 새 판에서 고치고 있었다면 그 수정은 지운 쪽에 남는다.
- 문단 숨김(삭제)도 텍스트 삭제가 된다.
- 판이 바뀌는 일은 방이 빈 뒤에만 생기고, 그 사이 오프라인이던 클라이언트만 재기반하므로 드물다.

| 1,000문단 | 80 → 49 KB | 23 ms | 4 ms | 40 KB · 74 ms · 36 ms | 35 ms |
| 10,000문단 | 205 → 162 KB | 135 ms | 34 ms | 142 KB · 224 ms · 245 ms | 265 ms |

- 구획 표식은 557–798개에서 2개가 된다. 스냅샷 크기는 크게 줄지 않는다 (큰 문서는 내용이 대부분이고, Loro 스냅샷은 이미 압축되어 있다). 압축의 효과는 크기보다 **구획 수와 묘비**다. 구획 수는 화면 순서 계산과 Doc 탐색 비용에 들어간다.

- `.quire`: deflate 전에는 10만 문단에서 43 MB였다 (본문 UTF-8 자체가 약 36 MB).
- `reset`을 받은 메인은 Doc을 새로 만든다. 문서를 처음 여는 것과 같은 비용이다 (10만 문단에서 약 1초).

### Node에서 서버 실행

```
node --experimental-transform-types --import ./apps/sync-server/src/resolve.ts apps/sync-server/src/server.ts 8787 --data=.quire-data --idle=10000
```

서버는 이제 `@quire/sync`(화면 텍스트, 정본 JSON, 새 판)를 쓴다. 워크스페이스 소스의 확장자 없는 상대 import를 풀기 위해 해석 훅(`resolve.ts`)이 필요하다. 생성자 매개변수 속성을 쓰므로 타입 제거만으로는 안 되고 `--experimental-transform-types`가 필요하다. 배포할 때는 묶어서 빌드한다.

### 남은 것

- 인증·권한이 없다.
- 판 기록(`epochs/`)을 지우지 않는다. 오래 오프라인이던 클라이언트를 위해 남기지만, 보존 기간을 정해야 한다.
- 오프라인 문단 이동이 재기반에서 "지우고 다시 넣기"가 된다 (위 한계).
- 정본 JSON은 지금 모델(서식 없는 문단)만 담는다. 서식·표·주석이 생기면 함께 넓힌다. 모르는 속성 보존(07 §4)은 아직 없다 (열 때 버림).
- R2(숨긴 구획 내용 지우기, 후속 3)는 아직 하지 않는다. 새 판 압축이 숨긴 내용을 함께 없앤다.
- 같은 스레드 `SyncBridge`와 relay 모드에는 판이 없다 (서버가 없음).
