# 09. CRDT 통합

- 상태: 2단계 완료 (텍스트 + 구획 동기화)
- 근거: ADR-0003, [V4 결과](../spikes/phase0-crdt.md), 05 §2

## 1. 목표

편집 모델(`@quire/model`의 `Doc`)과 Loro 문서를 이어, 여러 피어의 편집이 같은 문서로 수렴하게 한다.
키 입력 지연(현재 1만 쪽에서 p50 0.2 ms)을 늘리지 않는다.

## 2. 구조

```
  에디터 ──편집──▶ Doc (화면 상태, 즉시 반영)
                    │ 변경 기록 (UTF-16 위치)        ▲ 원격 델타 적용
                    ▼                                │
               SyncBridge ──── LoroDoc (같은 스레드) ─┘
                    │  50 ms 묶음: 내보내기 / 가져오기
                    ▼
                 전송 (onUpdate / receive)
```

- **Doc이 화면의 원본**이다. 로컬 편집은 Doc에 먼저 반영하고, 같은 변경을 Loro 텍스트에 바로 적용한다 (Loro 로컬 입력 + 커밋은 약 0.03–0.1 ms).
- Loro 비용의 대부분인 **업데이트 내보내기·가져오기**(1만 쪽에서 1회 약 16 ms, V4 결과 3)는 50 ms마다 한 번으로 묶는다.
- 원격 업데이트를 가져오면 Loro가 텍스트 델타(retain / insert / delete)를 이벤트로 준다. 브리지가 이를 Doc에 적용한다. 가져오기 이벤트는 동기로 처리해, 다음 로컬 편집 전에 Doc과 Loro가 같은 상태가 되게 한다.
- **위치 단위**: Loro JS의 텍스트 인덱스와 이벤트 델타는 UTF-16 단위다. Loro의 `convertPos`는 큰 문서에서 임의 위치 변환에 1회 수십 ms가 걸려 쓸 수 없다. Doc이 청크마다 UTF-16 길이를 들고 있어 기존 위치 찾기(O(청크 수))와 같은 비용으로 변환한다.
- **ID**: Doc 원소 ID와 Loro 원소 ID는 따로다. 두 쪽은 "살아 있는 원소 열"(위치)로 맞춘다. Doc ID는 로컬 선택 영역·실행 취소용이고, 피어 사이에서 공유하는 위치(원격 커서, 주석 범위)는 Loro 커서로 표현한다(3단계).
- 같은 스레드에서 시작한다. 1만 쪽 문서에서 50 ms마다 16 ms가 드는 것은 Worker로 옮길 때 해결한다(4단계). Worker로 옮기면 Doc과 Loro 사이에 비동기 지연이 생기므로, 아직 반영되지 않은 로컬 변경 위로 원격 델타를 옮기는 변환이 필요하다.

## 3. 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 텍스트 동기화: `@quire/sync` 브리지, UTF-16 위치, 로컬 변경 기록, 원격 델타 적용, 내보내기·가져오기 묶음, 다중 피어 무작위 수렴 시험. 실행 취소는 Doc 자체(되살린 글자는 Loro에 새로 입력) | 완료 (§5) |

| 4 | Worker로 이전 + 대기 중 로컬 변경 위로 원격 델타 변환. 네트워크 공급자(WebSocket), 재접속 | |
| 5 | 저장: Loro 스냅샷 + 정본 JSON(07, ADR-0004), 새 판 압축(V4 후속 3 R3) | |

## 4. 1단계 세부

### Doc 변경 기록

`Doc.observe(fn)`로 등록한 함수가 원소 열이 바뀔 때마다 `RawChange`를 받는다.

```ts
type RawChange =
  | { kind: 'insert'; at: number; text: string }   // at: UTF-16 위치 (구획 표식 포함)
  | { kind: 'delete'; at: number; len: number };   // len: UTF-16 길이
```

- 순서대로 적용하면 Loro 텍스트가 Doc의 살아 있는 원소 열과 같아지도록 보낸다 (여러 구간 삭제는 뒤에서부터, 되살리기는 앞에서부터).
- 원격 델타를 적용하는 동안에는 기록하지 않는다.

### 원격 델타 적용

`Doc.applyDelta(delta)`: UTF-16 위치로 원소를 찾아 새 원소를 넣거나 묘비로 만든다. 문단 목록은 로컬 편집과 같은 증분 갱신을 쓰므로 레이아웃 힌트도 그대로 나온다. 선택 영역은 Doc ID 기준이라 원격 편집 뒤에도 제자리를 지킨다.

### 1단계 한계

- 구획 연산(문단 이동·숨김)은 동기화하지 않는다. 브리지가 붙은 Doc은 구획 연산을 거부한다.
- 실행 취소는 Doc 자체 기록으로 한다. 내가 지운 글자를 되살리면 Loro에는 새 글자로 들어간다(V4 D5와 같은 성질).

## 5. 1단계 결과

### 구현

- `@quire/model`: 청크별 UTF-16 길이, `observe()`(변경 기록), `applyDelta()`(원격 델타), `rawText()`(Loro 텍스트와 비교용), `segmentsEnabled`.
- `@quire/sync`: `SyncBridge.create(text)` / `fromSnapshot(snapshot)`, `receive(update)`, `flush()`, `onUpdate`, `onRemoteChange`, `snapshot()`.
- `@quire/editor`: `doc` 옵션(브리지가 붙은 Doc 편집), `docChanged()`(원격 변경 뒤 다시 배치·그리기).
- 플레이그라운드 `/collab.html`: 두 편집기를 가짜 네트워크(지연, 오프라인)로 잇는 데모.

### 발견한 것

- 여러 업데이트를 `importBatch`로 한꺼번에 가져오면 Loro 이벤트가 `by: 'import'`가 아니라 **`'checkout'`**으로 온다. 처음 구현은 `import`만 처리해 무작위 시험 10개가 모두 어긋났다 → 로컬(`'local'`)이 아닌 이벤트는 모두 적용한다.
- 가져오기 이벤트는 동기로 온다 (Node 빌드, 브라우저 빌드 모두. 브라우저 빌드는 메서드가 끝날 때 대기 중인 이벤트를 처리한다). 시험으로 확인.
- 브라우저: `loro-crdt` 브라우저 빌드는 `.wasm`을 ES 모듈로 가져와 Vite 플러그인이 필요하다. 플레이그라운드는 wasm을 담은 `loro-crdt/base64` 빌드를 별칭으로 쓴다(협업 페이지 묶음 4.9 MB). 제품 배포에서는 wasm을 따로 불러오는 방식으로 바꾼다.

### 검증

- 단위 시험 6개: 전파, 동시 편집과 로컬 캐럿 유지, 이모지(UTF-16), 가져오기 직후 일치, 실행 취소·다시 실행 전파, 구획 연산 거부.
- 무작위 시험 10개: 피어 3개 × 300단계 (입력, 삭제, 실행 취소·다시 실행, 묶음 처리, 일부만 전달). **매 단계 모든 피어의 Doc = Loro 텍스트**, 끝에 전부 전달하면 세 피어 모두 같은 문서, 문단 목록·불변식 일치.
- 브라우저 데모: 양쪽 동시 입력, 지연 300 ms, 한쪽 오프라인 상태에서 같은 문단을 양쪽이 고친 뒤 재연결 → 두 입력 모두 남고 같은 문서로 수렴.

| 문서 | 글자 입력 p50 / p95 (브리지 포함) | 묶음 내보내기 p50 | 묶음 가져오기 + Doc 적용 p50 | 참여(스냅샷) |

### 다음 (2단계)

구획 동기화: Doc의 구획 표식을 Loro 텍스트의 U+E000으로(이미 변경 기록에 포함), 구획 순서·숨김을 Loro 리스트·맵으로, 원격 구획 상태를 `Doc.applySegState`로. 원격 델타 적용을 구획이 있는 문서로 넓히고(raw ↔ 화면 오프셋), 보초·자리표시 구획을 들인다.

## 6. 2단계 결과: 구획 동기화

### Loro 표현

| 요소 | 표현 |
|---|---|
| 구획 표식 | 텍스트 'body'의 U+E000 글자 + 마크 `seg=<구획 키>` (`expand: none`). 원격 델타에 키가 함께 실려 오므로 ID 대응표가 없다 |
| 구획 순서 | 이동 리스트 'order' (구획 키 + 끝 고정 항목 `$end`). 목록에 없는 구획은 저장 순서상 다음 구획 앞 |
| 숨김·자리표시·사용됨 | 맵 'hidden', 'placeholder', 'used' (키 → true) |
| 처음 문서 | `[사용자 문단들 BRK(t)][¶ BRK(p)][¶ 보초]` — t는 순서 목록에, p는 자리표시 |

구획 키는 피어마다 겹치지 않는다: 로컬에서 나눈 구획은 Doc 원소 ID(`<피어>:<카운터>`, Doc의 피어 이름 = Loro 피어 ID), 처음 문서의 두 구획은 `<피어>.t`, `<피어>.p`.

### 편집 모델 변경

- **보초·자리표시** (V4 후속 4): 동기화 문서(`Doc.fromRaw`)의 마지막 구획은 보이지 않는 보초다. 보이는 내용이 없으면 첫 자리표시를 빈 문단으로 보이고, 입력하면 사용됨으로 표시하고 새 자리표시를 만든다. 동기화 문서는 모든 문단을 숨겨도 된다.
- **가상 ¶**: 동시 편집으로 ¶ 없이 끝난 구획이 생길 수 있다 (A가 문단을 옮기는 동안 B가 그 문단과 다음 문단을 병합). V4 M4는 구획 끝을 문단 끝으로 보는데, 편집 모델은 구획을 이어 붙여 보였기 때문에 그 문단이 엉뚱한 문단과 붙었다 (S24 첫 실행). 동기화 문서에서는 그런 구획 끝에 **화면에만 있는 ¶**를 둔다. 캐럿은 그 구획의 표식 원소 앞에 놓이고, 지우면 기존 꼬리 옮기기가 된다.
- **실행 취소 연산**: 구획 순서 전체를 되돌리면 그사이 다른 피어가 옮긴 문단까지 되돌린다. 연산을 `move`(옮긴 구획들, 넣을 자리, 되돌릴 자리)와 `hidden`(바꾼 구획들)로 바꿨다. 자리는 구획 키가 아니라 **그 자리 문단의 첫 원소**로 기록한다: 다른 피어가 뒤 구획을 나누면 키는 뒷부분에 남기 때문이다 (첫 구현은 되돌린 문단이 엉뚱하게 맨 앞으로 갔다).
- **원격 적용의 예외 경로**: 원격 피어에게는 마지막이 아니던 ¶가 여기서는 화면 마지막 ¶일 수 있고, 원격 피어가 이쪽의 마지막 구획을 통째로 비울 수도 있다. 숨긴 구획·보초·자리표시를 나누는 원격 표식은 화면을 바꾼다. 이런 경우(열림 상태·대체 자리표시·보임 상태가 바뀜, 화면 끝까지 지움, 가상 ¶를 덮는 삭제)는 문단 목록을 처음부터 다시 만든다. 무작위 시험에서 하나씩 찾아 고쳤다.

| 시험 | 결과 |

### 남은 것

- 두 피어가 같은 문단을 같은 자리에서 동시에 나누면(같은 문단을 동시에 옮기거나 숨김) 빈 구획이 생기고 한쪽 연산만 그 문단에 적용된다 (결정적이지만 어느 쪽인지는 Loro의 동시 삽입 순서에 달림). V4에서 별칭 규칙으로 막으려던 경우이며, 별칭 규칙은 더 큰 문제(S31)가 있어 뺐다.
- 꼬리 옮기기와 가상 ¶ 주변의 문단 목록 갱신은 문단 목록 전체를 다시 만든다 (드문 경우지만 1만 쪽 문서에서는 수십 ms).

## 7. 3단계 결과: 공유 위치·프레즌스

### 공유 위치

피어 사이에서 같은 자리를 가리키는 값은 **Loro 커서**(`LoroText.getCursor`, 인코딩하면 12바이트 안팎)다. 커서는 글자 하나(Loro 원소 ID)에 붙고, 받는 쪽은 `getCursorPos`로 자기 문서에서의 현재 자리를 구한다. Doc 원소 ID는 피어마다 달라 공유할 수 없다(§2).

| API | 동작 |
|---|---|
| `Doc.u16OfOffset(offset)` | 화면 오프셋 → 그 자리 원소의 UTF-16 위치 (살아 있는 원소 열 = Loro 텍스트). 가상 ¶ 자리는 그 구획의 표식 원소 |
| `Doc.offsetOfU16(u16)` | UTF-16 위치 → 화면 오프셋. 숨긴 구획·보초 안이면 그 구획이 놓였을 자리, 결과는 0..maxCaret |
| `SyncBridge.cursorAt(offset)` | 화면 오프셋 → 인코딩한 커서. 캐럿 바로 **뒤** 글자에 붙는다: 그 자리에 누가 입력해도 캐럿은 그 글자 앞에 남으므로, 상대가 입력하는 동안 상대 캐럿이 입력한 글자 뒤를 따라간다 |
| `SyncBridge.resolveCursor(bytes)` | 커서 → 현재 화면 오프셋. 아직 받지 못한 연산을 가리키면 `null`. 기준 글자가 지워졌으면 그 글자가 있던 자리 |

주석 범위는 두 커서(시작, 끝)로 표현한다. 시험: 범위 앞과 안쪽 근처에 다른 피어가 입력해도 범위가 같은 글자들을 덮는다. 주석 자체(저장 위치, 표시)는 아직 없다.

Loro 커서의 성질 (탐색 시험, loro-crdt 1.17.1)
- 위치는 UTF-16 단위다 (텍스트 인덱스와 같다).
- `getCursorPos`는 1,200만 글자 문서에서 1회 약 0.06 ms다. `convertPos`(1회 26 ms)와 달리 바로 쓸 수 있다.
- 모르는 연산을 가리키는 커서는 `undefined`를 준다 (예외 아님).

### 프레즌스 (`@quire/sync`의 `Presence`)

- 상태: 이름, 색, 선택 영역의 두 끝(커서). 문서 기록에는 남지 않는다.
- **순서 규칙**: 피어마다 자기 키만 쓰므로, 보내는 피어의 일련번호(시작값 = 시각×1000, 갱신마다 +1)가 큰 쪽이 이긴다. 늦게 도착한 옛 상태는 버린다. 떠날 때는 빈 상태를 보낸다.
  - 처음에는 Loro `EphemeralStore`를 썼다. 그런데 이 저장소는 시각(ms)으로 비교해서, 받는 쪽이 같은 밀리초 안의 두 번째 갱신을 버렸다. 탐색 시험에서 200회 중 199회가 유실됐다. 캐럿은 한 틱에 여러 번 바뀌므로 쓸 수 없었다.
- **보내는 시점**: 캐럿은 방금 입력한 글자 바로 뒤에 붙는 일이 많다. 그 글자가 담긴 문서 업데이트보다 프레즌스가 먼저 도착하면, 받는 쪽은 위치를 풀 수 없다. 그래서 아직 내보내지 않은 로컬 변경이 있으면 프레즌스를 다음 묶음 처리(flush) 직후에 보낸다(`SyncBridge.onFlush`). 같은 연결이면 순서가 지켜진다.
- **풀 수 없을 때**: 다른 경로로 와서 문서 업데이트보다 먼저 도착한 경우 등에는 마지막으로 푼 자리를 Doc 위치로 들고 있다가 그 자리에 그린다. 업데이트가 도착하면 다시 푼다.
- **시간 초과**: 받는 쪽 시계로 30초 동안 소식이 없는 피어는 지운다. 각 피어는 15초마다 자기 상태를 다시 보낸다.
- **풀기 캐시**: `remotes()`는 문서 판과 프레즌스 판이 같으면 이전 결과를 돌려준다. 화면을 다시 그릴 때마다 다시 풀지 않는다.

### 편집기

- `EditorOptions.onSelectionChange(anchor, head)`는 사용자가 선택을 바꿀 때만 호출된다. 원격 편집으로 오프셋만 바뀐 경우는 커서가 알아서 따라가므로 호출하지 않는다.
- `setRemoteCarets(list)`는 상대의 선택 영역(색 22% 투명도), 캐럿(2px), 이름표를 그린다. 이름표 글자색은 배경색과의 대비로 흰색과 검정 중에서 고른다. 화면에 보이는 문단에 있는 캐럿만 그린다.
- 협업 데모(`collab.html`)는 프레즌스를 문서 업데이트와 같은 지연으로 보낸다. 오프라인 동안에는 마지막 상태만 들고 있다가 재연결할 때 문서 업데이트 뒤에 보낸다.

### 사용자별 실행 취소

이미 Doc의 실행 취소가 사용자별이다. 각 편집기의 `History`는 그 사용자가 만든 연산만 기록한다.
- 입력: 넣은 원소 ID들
- 삭제: 지운 원소 ID들
- 이동: 옮긴 구획과 원소 ID로 기록한 자리
- 숨김: 숨긴 구획

되돌리면 그 원소·구획만 바뀌고, 그사이 다른 피어가 한 편집은 그대로 남는다. 시험: A가 입력하고 B가 근처에 입력한 뒤 A가 되돌리면 B의 글자는 남는다. 2단계의 무작위 시험도 실행 취소를 섞어 수렴을 본다. Loro `UndoManager`는 쓰지 않는다. Doc이 원본이고 연산이 이미 ID 기준이기 때문이다.

한계: 삭제를 되돌리면 Doc은 같은 원소를 되살리지만, Loro에는 **새 글자로 입력**된다(1단계). 그래서 지운 글자에 붙어 있던 다른 피어의 커서나 주석 범위는 되살린 글자로 돌아오지 않고, 지운 자리에 남는다. 주석을 구현할 때는 되살린 글자에 범위를 다시 붙이는 규칙이 필요하다.

### 검증

| 시험 | 결과 |
|---|---|
| 왕복 (모든 캐럿 자리, 이모지·숨긴 문단·옮긴 문단 포함) | `resolveCursor(cursorAt(o)) = o`, 다른 피어에서 풀어도 같은 자리 |
| 동시 편집·이동 | 같은 자리에 입력해도 커서는 기준 글자 앞, 문단을 옮겨도 그 글자를 따라감. 지운 글자 → 그 자리, 숨긴 문단 → 그 문단이 있던 자리 |
| `@quire/sync` 무작위 시험 30개 | 매 단계 모든 피어에서 임의 캐럿의 왕복이 제자리. 25단계마다 만든 커서를 끝에서 세 피어가 같은 자리로 푼다 |
| 프레즌스 | 같은 밀리초 연속 갱신 → 마지막 것, 늦게 온 옛 상태 무시, flush 전 보류, 풀 수 없을 때 마지막 자리, 하트비트·시간 초과, 떠남 |
| 브라우저 데모 | A의 선택이 B 화면에 파란 이름표와 함께 보임. B가 입력하면 A 화면의 B 캐럿이 입력한 글자 뒤를 따라감. A가 문단을 옮겨도 양쪽의 상대 캐럿·선택이 같은 글자에 남음 |
