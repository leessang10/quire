# 02. 레이아웃 엔진

- 상태: 설계 (1–6단계에서 구현함. 구현하며 바뀐 점과 결과는 09–16의 결과 절에 있다)
- 해결 대상: L1, L2, L5, L9

## 1. 요구사항

- R1. 결정성: 같은 문서, 같은 글꼴 파일, 같은 엔진 버전이면 모든 기기에서 **같은 쪽 나눔**과 같은 줄바꿈 결과를 낸다.
- R2. 쪽 조판: 용지·여백, 머리말·꼬리말, 쪽 하단 각주, 다단, 표 행 분할과 제목 행 반복, 쪽 나눔 제어(다음 문단과 함께, 문단 나누지 않음, 과부·고아 줄).
- R3. 어울림 배치: 떠 있는 개체 주위로 텍스트가 흐른다 (사각형, 양쪽/한쪽, 자리 차지).
- R4. 한글 조판: 어절 단위 줄바꿈 옵션, 금칙 처리, 양쪽 정렬 시 자간·어간 조정, 장평·자간 속성.
- R5. 증분성: 입력 1회에 다시 계산하는 양이 문서 크기와 무관하다 (변경 지점 주변 + 수렴까지).
- R6. DOM 비의존: Web Worker, Node에서 실행 가능. PDF 내보내기가 같은 결과를 재사용한다.

## 2. 단위와 좌표

- 내부 길이 단위: **정수 1/1000pt** (`Unit`). 부동소수점 누적 오차가 기기별 결과 차이를 만드는 것을 막는다.
- 글리프 진행폭: 글꼴 단위(unitsPerEm) 값을 `Unit`으로 반올림하는 규칙을 고정한다.
- 화면 좌표 변환(줌, devicePixelRatio)은 렌더러에서만 한다.

### 1단계의 결정성 규칙 (2026-11-17)

정수 단위로 바꾸기 전, 지금 레이아웃(px, 부동소수점)이 기기마다 같은 결과를 내는 조건을 정해 둔다.

- 글리프 진행폭은 HarfBuzz가 낸 **글꼴 단위 정수**에서 시작한다. px = 정수 × 글자 크기 ÷ upem.
- 그 뒤의 계산은 더하기·곱하기·나누기와 비교만 쓴다. JavaScript는 이 연산을 IEEE 754 배정밀도로 하도록 정해져 있어 어느 엔진에서나 같은 비트가 나온다. 엔진마다 다를 수 있는 함수(`Math.sin`, `Math.pow` 등)와 `toFixed` 같은 문자열 왕복을 레이아웃 계산에 쓰지 않는다.
- 문단 안 x 위치는 float32(`Float32Array`)에 둔다. 더하는 순서(코드포인트 순)가 고정이라 반올림도 같다.
- 엔진이 불러온 글꼴만 쓴다. 대체 측정기(시스템 글꼴)로 잰 글자는 이 보장 밖이다.
- **회귀 시험** (`packages/shaping/src/determinism.test.ts`): 저장소 글꼴로 고정 말뭉치를 세 가지 줄 폭에 조판해 줄 나눔과 줄 폭(float32 비트)의 지문을 고정한다. 지문은 Node와 브라우저(Chromium)에서 같았다 (`5a769681`). 글꼴·harfbuzzjs·셰이퍼·레이아웃을 바꿔 지문이 달라지면 쪽 나눔이 바뀌는 변경이므로 일부러 고친다.
- 정수 단위(1/1000pt) 전환은 PDF 내보내기와 함께 한다: 내보내기에서 같은 위치를 정확히 재사용하고, 아주 긴 문단의 float32 누적 오차(0.02 px 수준)를 없애기 위해서다.

## 3. 파이프라인

```
문서 모델
  │  (dirty 문단 집합)
  ▼
① 아이템화 (Itemize)      문단 텍스트 → 스크립트·글꼴·서식이 같은 런(run) 단위로 분할
  ▼                       글꼴 대체(fallback) 결정
② 셰이핑 (Shape)          런 → 글리프 열 (HarfBuzz). 결과 캐시
  ▼
③ 줄바꿈 기회 계산         UAX #14 + 한글·금칙 규칙 → 끊을 수 있는 위치와 비용
  ▼
④ 문단 레이아웃            주어진 줄 폭 함수 width(y) 로 줄 나누기, 정렬, 양쪽 정렬
  ▼                       결과: 줄 목록 (높이, 기준선, 글리프 위치)
⑤ 쪽 조립 (Compose)       구역 설정에 따라 쪽·단 영역을 만들고 문단 줄을 흘려 넣음
  ▼                       각주, 떠 있는 개체, 표 분할, 쪽 나눔 제어 처리
레이아웃 트리
```

①~③은 문단 내용에만 의존하므로 **폭과 무관하게 캐시**한다. ④는 줄 폭이 바뀌면(어울림 배치 등) 다시 한다.

## 4. 텍스트 처리 (①~③)

### 글꼴

- 글꼴은 엔진이 직접 로드한다 (woff2 → ArrayBuffer). 시스템 글꼴에 의존하지 않아야 R1이 성립한다.
- 문서는 사용하는 글꼴 목록을 가진다. 없는 글꼴은 지정된 대체 글꼴로 조판하고, 사용자에게 표시한다.
- 한글 글꼴은 용량이 크므로 **부분 로드**(유니코드 범위별 분할 파일)와 로딩 중 임시 메트릭 사용 후 재조판을 지원한다.

### 셰이핑

- HarfBuzz(WASM)로 글리프 ID, 진행폭, 오프셋, 클러스터 매핑을 얻는다 (ADR-0002).
- 셰이핑 캐시 키: `(글꼴, 크기, OpenType 기능, 텍스트)`. 같은 단어가 반복되는 한글 문서에서 적중률이 높다.
- 클러스터 매핑은 캐럿 위치 계산(03)에 쓰인다. 한글 음절, 결합 문자, 이모지 ZWJ 시퀀스는 하나의 캐럿 단위다 (`Intl.Segmenter` grapheme).

### 1단계 구현 (`@quire/shaping`, ADR-0002)

- **셰이퍼 = 레이아웃의 Measurer + `advances`·`fontsOf`**. 레이아웃은 공백·탭으로 나뉜 조각(어절)마다 셰이퍼에 코드포인트별 진행폭을 받아 x 위치를 채운다. 셰이퍼가 없으면 0단계처럼 grapheme별 폭을 합한다(시험용 고정 폭, 시스템 글꼴 캔버스).
- **`HbShaper`** (harfbuzzjs)
  - 조각을 grapheme으로 나누고, grapheme마다 글꼴을 고른다: 글꼴 목록에서 그 글자(ZWJ·이형 선택자 제외)를 모두 가진 첫 글꼴 → 첫 글자를 가진 첫 글꼴 → 대체 측정기(엔진이 불러오지 않은 시스템 글꼴, 글꼴 번호 255).
  - 같은 글꼴·같은 스크립트(한글, 한자, 가나, 라틴, 기타 문자; 문장부호·숫자는 앞 런에 붙음)를 한 런으로 셰이핑한다. 커닝·합자 켬.
  - 글리프 진행폭을 클러스터별로 모아 grapheme 첫 코드포인트에 둔다. 합자처럼 클러스터 하나에 grapheme이 여럿이면 똑같이 나눠 캐럿이 설 자리를 만든다.
  - **옛 kern 표**: harfbuzzjs는 HB_TINY 빌드라 GPOS가 아닌 옛 `kern` 표를 쓰지 않는다. 맑은 고딕은 GPOS 없이 kern 표만 있어, 그대로 두면 라틴 폭이 브라우저와 달랐다("r," 9.16 vs 7.82 px). GPOS에 kern 기능이 없으면 kern 표(형식 0)를 직접 적용한다 (HarfBuzz와 같은 규칙).
  - 조각 문자열로 캐시한다 (상한 10만 개).
- **편집기**: `fonts` 옵션으로 글꼴 파일(TTF·OTF; HarfBuzz가 woff2를 못 읽음)을 받는다. 불러오는 동안은 시스템 글꼴로 재고, 다 불러오면 셰이퍼로 바꿔 다시 조판한다. 그리기는 같은 파일을 `FontFace`로 등록해, 어절·글꼴 단위로 셰이핑 위치에 `fillText`(커닝 켬). 레이아웃이 어절마다 셰이핑하므로 같은 단위로 그려야 어절 경계 커닝 차이가 없다.
- 결과 (앱 내장 Chromium, 맑은 고딕 + Calibri): 1,000쪽 문서 31만 어절 모두 캔버스 폭 = 셰이핑 폭 (차이 0 px), 968쪽으로 같다. 입력 p50 3.6 / p95 5.4 ms (같은 측정에서 시스템 글꼴 3.2 / 10.4 ms). 전체 조판(Node) 1만 문단 236 ms, 10만 문단 2.9 s (배경 조판).
- **기본 글꼴과 부분 로드** (`fonts/README.md`): 기본 본문 Pretendard, 대체 Noto Sans KR (둘 다 OFL, 저장소에 OTF). `scripts/build-fonts.mjs`가 HarfBuzz 부분 집합(hb-subset WASM, 레이아웃 기능 모두 유지)으로 유니코드 범위별 조각(120–490 KB)과 `manifest.json`(조각별 글자 범위를 줄인 문자열, 6 KB gzip)을 만든다.
  - 글꼴 목록의 자리 = 조각. 셰이퍼는 불러오기 전에도 어느 조각이 그 글자를 가졌는지 안다(manifest). 아직 없는 조각의 글자는 대체 측정기로 재고 **캐시하지 않으며** 불러오기를 요청한다.
  - 편집기는 처음에 문서에 나온 글자가 든 조각을 미리 받아 한 번만 조판한다. 편집 중 새 글자가 다른 조각에 있으면 모아서 받은 뒤 다시 조판한다.
  - 결과 (앱 내장 Chromium): 예제 문서는 `base` 하나(0.46 MB)로 열린다. 1,000쪽 문서 31만 어절 차이 0 px(970쪽), 입력 p50 4.2 / p95 5.9 ms. 한자 4글자 입력 → 그동안 시스템 글꼴로 재고, 한자 조각 3개(1.2 MB)를 받아 다시 조판.
  - 시험: 조각으로 셰이핑 = 원본으로 셰이핑 (한글, 커닝, 합자, 한자, 옛한글), 대체 글꼴 조각에는 Pretendard에 없는 글자만, 불러오기 전 대체 측정·요청은 자리마다 한 번, 조각 600 KB 미만. 저장소의 OFL 글꼴만 써서 CI에서도 돈다.
- 남은 것: 한자 조각을 빈도순으로 (지금은 코드 순이라 흔한 한자 몇 자에 여러 조각), 문서별 글꼴 목록과 대체 글꼴 지정, 합자 캐럿(GDEF), 내부 단위(1/1000pt) 정수 좌표, 실제 문서의 캐시 적중률.

### 줄바꿈 규칙

- 기본: UAX #14.
- 한글 모드 (문단 속성 `koreanBreak`):
  - `word`: 어절(공백) 단위로만 끊음 — 한국어 문서 기본값
  - `char`: 음절 단위로 끊음 — 한글 프로그램의 "글자 단위" 옵션
- 금칙: 줄 앞에 올 수 없는 문자(닫는 괄호, 마침표, 쉼표 …), 줄 끝에 올 수 없는 문자(여는 괄호 …) 목록. 문서 설정으로 바꿀 수 있다.
- 영문 하이픈 넣기: 후순위 (패턴 사전 필요).

### 양쪽 정렬

- 1차: 줄 단위 탐욕(greedy) 줄바꿈 + 어간(공백) 확장, 부족하면 자간 확장 상한까지.
- 2차 후보: 문단 단위 최적 줄바꿈(Knuth–Plass 계열). 비용이 커서 문단 길이·성능 기준을 두고 선택 적용.

## 5. 문단 레이아웃 (④)

입력: 줄바꿈 기회가 계산된 글리프 열, 문단 속성, 그리고 **줄 폭 함수**.

```ts
interface LineSpace {
  // y 위치에서 높이 h인 줄을 놓을 수 있는 가로 구간들 (어울림 배치로 여러 개일 수 있음)
  slotsAt(y: Unit, h: Unit): Array<{ x: Unit; width: Unit }>;
}
```

- 떠 있는 개체가 없으면 slot은 항상 `[0, 단 폭]` 하나다. 이 경우 결과를 단 폭 기준으로 캐시할 수 있다.
- 출력: `Line { startOffset, endOffset, height, ascent, descent, runs: PositionedRun[] }`

## 6. 쪽 조립 (⑤)

### 영역 모델

```
Page
├─ header region
├─ body region
│   └─ column[] (다단)
├─ footnote region (본문 아래, 필요한 만큼 위로 자람)
└─ footer region
```

### 조립 알고리즘 개요

1. 구역 설정으로 쪽과 단을 만든다.
2. 본문 문단을 순서대로 꺼내 현재 단에 줄 단위로 채운다.
3. 줄 안에 각주 참조가 있으면 해당 각주 높이만큼 같은 쪽의 각주 영역을 늘리고 본문 영역을 줄인다. 공간이 부족하면 줄을 다음 쪽으로 넘기거나 각주를 분할해 이어 쓴다.
4. 앵커가 있는 떠 있는 개체를 위치시키고, 겹치는 영역에 배제 구간을 등록한다. 이미 배치된 줄과 겹치면 해당 문단을 다시 레이아웃한다.
5. 쪽 나눔 제어 규칙(다음 문단과 함께, 문단 나누지 않음, 과부·고아 줄)을 적용한다. 위반 시 되돌아가서 다시 놓는다(제한된 백트래킹).
6. 표는 행 단위로 놓고, 행이 쪽을 넘으면 행 분할 허용 여부에 따라 행을 쪼개거나 통째로 넘긴다. 제목 행 반복을 넣는다.
7. 머리말·꼬리말은 쪽마다 조판한다 (쪽 번호 필드가 쪽마다 다름).

### 순환 의존과 수렴

- 각주와 어울림 배치는 "줄 위치 → 영역 크기 → 줄 위치"의 순환을 만든다. 쪽 단위로 **최대 N회 반복** 후 고정하고, 고정된 경우를 진단 로그로 남긴다.
- 쪽 번호 필드(총 쪽수 포함)는 조립 후 확정되는 값이다. 필드 폭이 바뀌면 영향받는 쪽만 다시 조립한다.

## 7. 증분 레이아웃 (R5, L5)

- 문단 수준 캐시: `(문단 ID, 문단 버전, 줄 폭 키) → 줄 목록`
- 쪽 조립 체크포인트: 각 쪽 시작 시점의 상태(구역, 다음 문단·줄 위치, 열려 있는 각주, 떠 있는 개체)를 저장한다.
- 편집 시 첫 dirty 문단이 속한 쪽의 체크포인트부터 다시 조립한다. 새로 조립한 쪽의 끝 상태가 이전 결과의 같은 쪽 끝 상태와 **같아지면(수렴) 멈추고** 이후 쪽은 재사용한다 (쪽 번호만 이동).
- 조립은 시간 예산 단위로 나눠 실행한다. 화면에 보이는 쪽을 먼저 확정하고, 나머지 쪽(전체 쪽수 등)은 유휴 시간에 계산한다.
- 셰이핑·문단 레이아웃은 Worker 풀에서 병렬 실행할 수 있다. 쪽 조립은 순차.

## 8. 레이아웃 트리 (출력)

```
LayoutDocument
└─ Page[]            { index, size, sectionId }
   └─ Region[]       { kind: header|body|column|footnote|footer|frame, rect }
      └─ Block[]     { kind: paragraph|tableRow|cell|object, paragraphId, rect }
         └─ Line[]   { baseline, rect, offsetRange }
            └─ Run[] { glyphs, font, size, color, x[] , clusterMap }
```

렌더러(04), hit-test·캐럿 계산(03), 접근성 미러(04), PDF 내보내기가 모두 이 트리만 읽는다.
