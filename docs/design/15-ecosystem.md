## 1. 목표

캔버스 편집기는 `contenteditable`이 공짜로 주던 기능(찾기, 맞춤법, 인쇄)을 직접 되찾아야 한다 (00 원칙 5). 또 다른 프로그램과 문서를 주고받아야 쓸 수 있다. 5단계는 이 둘과, 앱이 기능을 덧붙일 수 있는 플러그인 API다.

| # | 목표 | 끝났다는 기준 |
|---|---|---|
| G1 | 찾기·바꾸기: 모든 스토리(본문·셀·머리말·꼬리말·각주), 대소문자·낱말 단위·정규식, 바꾸기·모두 바꾸기 | 1,000쪽 문서에서 모두 찾기 200 ms 안(Worker 밖에서도), 찾은 상태로 입력 p95 16 ms 그대로, 모두 바꾸기가 실행 취소 한 번 |
| G2 | 맞춤법 검사: 검사기 인터페이스, 문단 단위 증분 검사, 물결 밑줄, 고칠 말 메뉴, 무시·사전에 더하기 | 입력 중 보이는 문단만 검사하고 입력 p95 16 ms 그대로, 한 문단 고치면 그 문단만 다시 검사 |

| G5 | 교환 포맷: Markdown·HTML 문서 단위 가져오기·내보내기, DOCX·HWPX 가져오기·내보내기 ("주요 요소 보존", 00 §2) | 기준 문서 세트 왕복(내보내기 → 가져오기)에서 주요 요소 표(§6.1)의 요소가 모두 남음, 내보낸 파일을 Word·한글이 연다 (사람 확인) |

React 래퍼와 서버 패키지(08)는 5단계 끝에 공개 API를 정리하면서 함께 한다 (§8).

## 2. 장식: 비영속 범위 (G1·G2·G6의 바탕)

찾기 결과와 맞춤법 오류는 문서가 아니다. 저장·동기화·실행 취소에 들어가면 안 되고, 피어마다 다르다. 04 §4·§5는 이것을 "비영속 주석"이라 했다. 14의 주석 레이어와 겉모양(범위, 그리기)은 같지만 데이터 경로는 따로 둔다.

```ts
interface Decoration {
  story: StoryId | null;
  from: number; // 그 스토리의 화면 오프셋
  to: number;
  kind: string; // 'find' | 'find-current' | 'spell' | 플러그인 종류
  data?: unknown;
}

interface DecorationSource {
  /** 보이는 문단 범위의 장식. 그리기마다 부른다 */
  decorationsIn(story: StoryId | null, from: number, to: number): readonly Decoration[];
  /** 문서가 바뀌면 바뀐 범위를 받아 자기 장식을 옮기거나 다시 계산한다 */
  onChange?(change: DocChange): void;
}
```

- 장식은 **오프셋**으로 둔다 (원소 ID가 아니다). 값이 짧게 살고, 바뀌면 다시 계산하는 편이 싸다.
- 편집기는 `commit`마다 바뀐 범위(스토리, 문단 범위, 오프셋 차이)를 장식 소스에 알린다. 소스는 바뀐 문단의 장식을 버리고 그 뒤 장식을 오프셋 차이만큼 옮긴 다음, 바뀐 문단만 다시 계산한다.
- 그리기는 14 §2.4의 주석 그리기 경로를 같이 쓴다: 오버레이에 종류별 그리기 함수(바탕색, 물결 밑줄, 테두리).
- 보기 모드(14 §4.3)의 최종본·원본은 파생 문서다. 장식은 그 파생 문서의 오프셋으로 계산한다 (찾기는 보이는 글자를 찾는다).

## 3. 찾기·바꾸기 (G1)

### 3.1 검색

- Ctrl+F(macOS ⌘F)를 가로채 찾기 막대를 연다. Ctrl+H는 바꾸기 줄까지 연다. 막대 UI는 플레이그라운드가 만들고 편집기는 API만 낸다 (08 R3):

```ts
editor.find(query: FindQuery): FindResult;       // 모두 찾기, 현재 = 캐럿 뒤 첫 결과
editor.findNext(); editor.findPrev();
editor.replace(text: string): boolean;           // 현재 결과를 바꾸고 다음으로
editor.replaceAll(text: string): number;         // 한 트랜잭션
editor.clearFind();
interface FindQuery { text: string; caseSensitive?: boolean; wholeWord?: boolean; regex?: boolean; stories?: 'all' | 'body' }
```

- 찾는 대상은 스토리마다의 문단 텍스트다 (`Doc.paragraphs()`의 `text`). 개체 글자(표·각주 참조·이미지)는 U+FFFC라 낱말 경계가 된다. 표는 셀 스토리를 문서 순서(행, 열)로 찾는다.
- 문단을 넘는 결과는 찾지 않는다 (정규식의 `\n`도 문단 안 줄바꿈만). Word와 같다.
- 낱말 단위: 앞뒤 글자가 글자·숫자가 아니면 낱말이다 (`\p{L}\p{N}`). 한글은 조사가 붙어 낱말 단위가 잘 맞지 않으므로 기본은 끈다.
- 대소문자 무시는 `toLocaleLowerCase` 후 길이가 바뀌지 않는 글자에만 쓴다 (길이가 바뀌는 글자는 그대로 비교). 결과 오프셋이 원문과 어긋나지 않게 한다.
- 비용: 1,000쪽 ≈ 문단 2만 개, 글자 200만 자. 문단별 `indexOf`면 수십 ms다. Worker는 두지 않고 메인에서 하되 문단 결과를 캐시해 입력 때 바뀐 문단만 다시 찾는다. 결과 수는 상한(1만)을 두고 넘으면 "1만+"로 보인다. 200 ms를 넘으면 문단 묶음을 나눠 유휴 시간에 찾는다.

### 3.2 보이기

- 모든 결과는 `find` 장식(연한 노랑), 현재 결과는 `find-current`(진한 주황)다.
- 현재 결과로 스크롤한다: 스토리 위치에서 화면 좌표를 구하는 기존 경로(`revealRemote`가 쓰는 `storyLayoutFor`)를 쓴다. 머리말 결과는 그 머리말을 쓰는 첫 쪽에 보인다.
- 스크롤 막대 옆에 결과 위치 눈금을 그린다 (쪽 비율).

### 3.3 바꾸기

- 바꾸기는 그 범위를 지우고 넣는 편집이다. 제안 모드면 제안으로 기록된다 (14 §4: `recordSuggestions`가 그대로 받는다). 읽기 전용(보기 모드·보기 권한)이면 바꾸기를 막는다.
- 바꿀 글자의 서식은 결과 첫 글자의 서식을 따른다 (Word와 같다).
- 정규식 바꾸기는 `$1`·`$&`를 쓴다 (`String.prototype.replace` 규칙).
- 모두 바꾸기는 뒤에서 앞으로 바꿔 오프셋이 밀리지 않게 하고, 연산을 한 트랜잭션으로 묶는다 → 실행 취소 한 번. 동기화에는 한 번에 간다.
- 협업: 찾은 뒤 원격 변경이 오면 장식이 옮겨진다 (§2). 바꾸기 직전에 결과 범위의 글자가 아직 검색어와 맞는지 다시 확인하고, 아니면 건너뛴다.

## 4. 맞춤법 검사 (G2)

### 4.1 검사기 인터페이스

한국어 맞춤법은 사전 단어 목록으로 잘 되지 않는다 (조사·어미 활용, 띄어쓰기). 좋은 검사기는 대개 서버 서비스이고 라이선스가 따로다. 그래서 편집기는 **검사기를 끼우는 자리**만 정하고, 검사기는 앱이 준다.

```ts
interface SpellChecker {
  /** 문단 하나. 같은 글자에는 같은 결과 (캐시 키 = 언어 + 텍스트) */
  check(text: string, lang: string, signal: AbortSignal): Promise<SpellIssue[]>;
  /** 사용자 사전 (선택) */
  addWord?(word: string): void;
}
interface SpellIssue { from: number; to: number; kind: 'spelling' | 'spacing' | 'grammar'; message?: string; suggestions: string[] }
```

- 내장 검사기는 둘이다.
  - `WordListChecker`: 단어 목록 사전 (영어 등, 시험용). 낱말을 잘라 목록에 없으면 오류다.
  - `HttpChecker`: 문단 묶음을 서버로 보내는 어댑터 (요청 모양만 정하고 서비스는 앱이 고른다).
- 한국어 기본 검사기는 정하지 않는다 (O-36).

### 4.2 일정

- 검사 대상: 보이는 문단 ± 여유분, 그다음 유휴 시간에 나머지 문단. 캐럿이 있는 문단은 입력이 멈춘 뒤(500 ms) 검사한다. 입력 중인 낱말은 오류로 보이지 않는다.
- 결과 캐시: (언어, 문단 텍스트) → 결과. 문단을 옮기거나 되돌려도 다시 검사하지 않는다. 캐시는 LRU로 크기를 제한한다.
- 비동기 결과가 왔을 때 문단 텍스트가 이미 바뀌었으면 버린다. 진행 중 검사는 `AbortSignal`로 그만둔다.
- 언어: 문단의 언어 속성이 없으므로 처음에는 문서 기본 언어 하나다 (`ko`). 문자 종류(한글·라틴)로 검사기를 고르는 것은 검사기가 한다.

### 4.3 보이기와 고치기

- `spell` 장식: 빨간 물결 밑줄(띄어쓰기·문법은 파랑).
- 오른쪽 클릭 → 고칠 말 목록, "모두 무시", "사전에 더하기". 고칠 말을 고르면 그 범위를 바꾼다 (보통 편집, 제안 모드면 제안).
- 무시 목록은 문서마다(로컬 상태, 저장하지 않음), 사전에 더하기는 검사기의 `addWord`(앱이 저장)다.
- 미러(04 §3)에는 `aria-invalid="spelling"`을 붙인 `span`으로 알린다.

## 5. 쪽 그리기 분리와 PDF (G3·G4)

### 5.1 그리기기 분리

지금 쪽 그리기는 `Editor` 안에 있다 (`render`, `drawLines`, `drawFloat`, `drawPageHF`, `drawPageNotes`, 표 그리기). 편집기 상태(캐럿, 선택, 활성 스토리, 원격 캐럿, 화면 스크롤)와 섞여 있고 `CanvasRenderingContext2D`에 직접 그린다. PDF와 서버 실행(08 §6)을 위해 둘로 나눈다.

```ts
/** 그리기 대상: Canvas 2D의 부분집합 */
interface PaintTarget {
  save(): void; restore(): void;
  translate(x: number, y: number): void;
  fillRect(x: number, y: number, w: number, h: number, color: string): void;
  line(x1: number, y1: number, x2: number, y2: number, width: number, color: string, dash?: number[]): void;
  /** 셰이핑한 글리프 열. 화면은 fillText로, PDF는 글리프 ID로 그린다 */
  glyphs(run: GlyphRun, x: number, y: number, color: string): void;
  image(id: string, x: number, y: number, w: number, h: number): void;
  clip(x: number, y: number, w: number, h: number): void;
  link?(x: number, y: number, w: number, h: number, href: string): void;
}

class PagePainter {
  constructor(layout: PagedLayout, document: Document, fmt: Formatter, images: ImageSource);
  /** 쪽 하나의 내용: 본문 줄·표·떠 있는 개체·머리말·꼬리말·각주. 편집기 오버레이는 없다 */
  paintPage(page: number, target: PaintTarget): void;
}
```

- `GlyphRun`은 같은 글꼴 슬롯의 글자 조각과 레이아웃이 정한 코드포인트별 x 위치다 (`Measurer.advances`·`fontsOf`의 결과). 레이아웃은 글리프 ID를 두지 않는다. 화면 대상은 지금처럼 `fillText(text)`로 그리고(같은 글꼴 파일이라 같은 모양, O-12 해소), PDF 대상은 같은 셰이퍼(`HbShaper`, 결정적)로 그 조각을 다시 셰이핑해 글리프 ID를 얻는다 (조각 캐시).
- 편집기의 `render`는 보이는 쪽마다 `paintPage`를 부르고, 그 위에 편집기만의 것(선택, 주석·제안·장식, 캐럿, 원격 캐럿, 활성 스토리 흐리기, 개체 핸들)을 그린다.
- 레이아웃이 아직 준비되지 않은 쪽(백그라운드 조판)은 편집기가 자리표시를 그린다. 그리기기는 준비된 쪽만 받는다.
- 시험: 기록 대상(`RecordingTarget`)으로 그리기 명령을 모아 지문(해시)을 비교한다. Node와 Chromium에서 같은 지문이면 서버 PDF가 화면과 같다.

이 분리는 `editor.ts`(5,200줄)의 가장 큰 리팩터링이다. 단계 5-3이 이것만 한다. 화면 결과가 바뀌지 않음을 기준 문서 세트의 그리기 지문으로 확인하면서 옮긴다.

### 5.2 PDF 작성기

외부 라이브러리 없이 쓴다 (`@quire/pdf`, DOM 없음, Node·브라우저·Worker).

- **글꼴**: 글꼴 슬롯(Pretendard 조각들, Noto Sans KR)은 OpenType CFF(`.otf`)다. 쓰인 글리프만 남긴 부분 글꼴을 만들어 `FontFile3`(`/Subtype /OpenType`)로 넣고, `Type0` + `CIDFontType0` + `Identity-H`로 글리프 ID를 그대로 CID로 쓴다. 부분 글꼴 만들기(CFF 부분화)가 어려우면 첫 단계는 조각 파일을 통째로 넣는다 (조각 하나 250–460 KB, O-37).
- **글자 복사**: 글꼴마다 `ToUnicode` CMap (글리프 ID → 원문 글자). 합자처럼 글리프 하나가 여러 글자면 그 글자열로 매핑한다. 한 글자가 여러 글리프면 첫 글리프에 매핑한다.
- **좌표**: 레이아웃 단위는 정수 1/1000pt (02 §2)라 PDF 사용자 단위(pt)로 나누기만 한다. y축은 뒤집는다.
- **글리프 위치**: `TJ` 연산자에 진행 폭 보정값을 넣어 셰이핑한 진행 폭과 같게 한다 (양쪽 정렬 늘림 포함).
- **이미지**: JPEG는 그대로(`DCTDecode`), PNG는 픽셀을 풀어 `FlateDecode`로 (알파는 `SMask`). 압축은 `CompressionStream('deflate')`(브라우저)와 `zlib`(Node)을 같은 인터페이스로 감싼다.
- **나머지**: 표 선·밑줄·취소선은 선, 배경색은 사각형, 링크는 `Link` 주석, 제목 문단은 개요(책갈피) 트리.
- **크기**: 쪽 내용 스트림은 쪽마다 압축한다. 1,000쪽 10초 목표는 조판(이미 Worker) + 그리기 + 압축이다. 쪽을 하나씩 만들어 스트림으로 내보내 메모리를 쪽 수와 무관하게 둔다.

### 5.3 인쇄

- 브라우저 인쇄(Ctrl+P)를 가로채 PDF를 만들어 새 창에서 연다. 쪽 나눔이 화면과 같다 (04 §7).
- PDF 없이 바로 인쇄하는 경로(쪽마다 고해상도 캔버스를 인쇄 전용 DOM에 넣기)는 두지 않는다. 인쇄 품질(벡터 글자)과 결과가 PDF와 같아야 해서다.

### 5.4 서버 실행 (08 §6)

`PagePainter`와 PDF 작성기가 DOM에 의존하지 않으므로, 동기화 서버(또는 `@quire/server`)가 정본 JSON → 조판 → PDF를 낼 수 있다. 글꼴은 서버가 같은 파일을 읽는다. 첫 쪽 PNG 썸네일은 5단계 밖이다 (래스터라이저가 필요하다).

## 6. 교환 포맷 (G5)

### 6.1 주요 요소 표

"주요 요소 보존"(00 §2)을 시험할 수 있게 정한다. 아래 요소가 왕복 뒤 남아야 한다.

| 요소 | Markdown | HTML | DOCX | HWPX |
|---|---|---|---|---|
| 문단 텍스트, 제목 1–6 | ○ | ○ | ○ | ○ |
| 굵게·기울임·밑줄·취소선 | ○ (밑줄 빼고) | ○ | ○ | ○ |
| 글꼴 크기·색·형광펜 | - | ○ | ○ | ○ |
| 정렬·들여쓰기·줄 간격 | - | ○ | ○ | ○ |
| 목록 (번호·글머리, 수준) | ○ | ○ | ○ | ○ |
| 링크 | ○ | ○ | ○ | ○ |
| 인라인 이미지 | ○ (자산 경로) | ○ (data URL) | ○ | ○ |
| 표 (병합 셀, 열 너비) | ○ (병합·너비 빼고) | ○ | ○ | ○ |
| 구역·용지·여백·방향 | - | - | ○ | ○ |
| 머리말·꼬리말·쪽 번호 | - | - | ○ | ○ |
| 각주 | ○ (GFM 각주) | ○ (끝에 목록) | ○ | ○ |
| 다단 | - | - | ○ | ○ |
| 떠 있는 이미지·어울림 | - | - | ○ | ○ |
| 댓글 | - | - | ○ | ○ (메모) |
| 변경 추적(제안) | - | - | ○ (`w:ins`·`w:del`) | 내보낼 때 최종본 |

"-"인 요소는 내보낼 때 버리거나(쪽 설정) 가까운 것으로 바꾼다(밑줄 → `<u>`). 가져올 때 모르는 요소는 버리고, 버린 요소 수를 결과에 알린다 (`ImportReport`).

### 6.2 구조

- 모든 변환은 **정본 JSON(07 §4)** 을 거친다: 내보내기는 정본 → 포맷, 가져오기는 포맷 → 정본 → `documentFromQuire`. 내보내기의 시작은 `quireFromDocument`다. 편집 모델·Loro를 직접 다루지 않는다.
- 클립보드의 HTML 변환(`fragmentToHtml`·`htmlToFragment`, 04 §6)은 문서 조각용이다. 문서 단위 HTML은 이것을 넓혀 같이 쓴다 (정제 규칙 하나).
- 패키지 `@quire/convert` (DOM 없음). HTML 파싱은 이미 자체 파서(`parseHtml`)가 있어 Node에서도 된다. DOCX·HWPX는 zip + XML이다: zip은 `sync/zip.ts`를 옮겨 같이 쓰고, XML은 작은 자체 파서를 둔다 (네임스페이스, 엔티티, CDATA만).
- 단위: DOCX는 twip(1/20 pt)·EMU, HWPX는 HWPUNIT(1/7200 인치 = 1/100 pt). 정본은 1/1000 pt라 정수 변환이다.

### 6.3 DOCX

- 내보내기: `document.xml`(본문, 표, 구역 `w:sectPr`), `styles.xml`(문단 스타일 → `w:style`), `numbering.xml`(목록), `footnotes.xml`, `header*.xml`·`footer*.xml`, `comments.xml`, `media/`. 제안은 `w:ins`·`w:del`(글자), `w:rPrChange`(서식)로 낸다.
- 가져오기: 같은 부분을 읽는다. 스타일 상속(`w:basedOn`)과 문서 기본값을 풀어 정본의 스타일·직접 서식으로 둔다.
- 글꼴은 이름만 옮긴다. 우리 글꼴 목록에 없으면 기본 글꼴로 조판한다 (쪽 나눔이 Word와 다를 수 있다, 02 O-7).

### 6.4 HWPX

- HWPX(OWPML, KS X 6101)는 zip 안의 `Contents/section*.xml`, `Contents/header.xml`(글꼴·글자 모양·문단 모양 표), `BinData/`다. 글자·문단 모양을 ID로 참조하므로 내보낼 때 서식 조합을 모아 표를 만든다.
- 이전 형식 HWP(바이너리)는 하지 않는다.
- 기준 문서 세트의 "서식 문서"를 HWPX로 내보내 한글에서 열어 쪽 나눔을 비교한다 (02 O-7, 사람 확인).

### 6.5 Markdown

- GFM: 제목, 강조, 목록(중첩), 링크, 이미지, 표, 각주, 코드(코드 스타일 문단 → 펜스). 가져오기 파서는 직접 쓴다 (블록 → 인라인 두 단계, GFM 명세의 일부).

## 7. 플러그인 API (G6)

00 §4의 맨 위 층이다. 편집기 코어를 고치지 않고 기능을 덧붙이는 자리다.

```ts
interface QuirePlugin {
  name: string;
  /** 명령 (editor.run(name, ...args)) */
  commands?: Record<string, (ctx: PluginContext, ...args: unknown[]) => boolean>;
  /** 단축키 → 명령 이름 */
  keymap?: Record<string, string>;
  /** 장식 소스 (§2) */
  decorations?: (ctx: PluginContext) => DecorationSource;
  /** 장식·주석 종류 그리기 (오버레이) */
  painters?: Record<string, OverlayPainter>;
  /** 오른쪽 클릭 메뉴 항목 */
  contextMenu?: (ctx: PluginContext, at: StoryPos) => MenuItem[];
  /** 내보내기 형식 (§6) */
  exporters?: Record<string, Exporter>;
  /** 문서 확장 데이터: 정본 객체의 `x.<name>` (07 §4) */
  data?: { schemaVersion: number; migrate?(old: unknown, from: number): unknown };
  init?(ctx: PluginContext): void | (() => void);
}
```

- `PluginContext`는 편집기의 좁은 면만 준다: 문서 읽기, 트랜잭션 만들기(`ctx.transact(ops)` → 실행 취소·동기화·제안 기록을 그대로 탄다), 선택, 좌표(`caretRect`·`rangeRects`), 장식 다시 그리기 요청.
- 플러그인이 직접 문서 상태를 바꾸는 길은 트랜잭션 하나뿐이다. 그래서 권한(읽기 전용)·제안 모드가 플러그인에도 적용된다.
- 찾기(§3)와 맞춤법(§4)을 내장 플러그인으로 다시 짠다. 그래도 동작이 같으면 API가 충분하다는 증거다 (G6 기준).
- 예제 플러그인: 글자 수 세기(상태 표시, 장식 없음), 강조 낱말(정해진 낱말에 장식 + 명령).
- 플러그인 데이터의 동기화: `x` 데이터는 정본·`.quire`에 남는다. 실시간 동기화는 문서 수준 키 맵(구역 설정과 같은 모양, 12 §3.2)에 `x|<name>|<key>`로 둔다 (5-8에서 필요하면).

## 8. 공개 API 정리 (08)

- 지금 편집기 생성자(`new Editor(opts)`)를 08 §3의 `createEditor`로 감싸고, 플러그인 옵션을 받는다.
- `@quire/react`: `useQuire`, `QuireEditor`, `useEditorState` (08 §4). 입력 한 번이 리렌더를 일으키지 않음을 시험한다 (렌더 횟수 세기).
- 이것은 5단계 끝(5-8)에 플러그인 API와 같이 한다.

## 12. 5-1 결과: 찾기·바꾸기

### 구현

- **찾기 엔진** (`@quire/model` `find.ts`, DOM 없음):
  - `compileFind(query)`: 조건을 정규식 하나로 만든다. 보통 글자는 이스케이프한다. 낱말 단위는 앞뒤 `(?<![\p{L}\p{N}_])`·`(?![…])`이다. 대소문자 무시는 `i` 플래그라 원문 위에서 맞추고, 길이가 바뀌는 글자 문제가 없다. 틀린 정규식·빈 글자는 `error`다.
  - 결과는 코드포인트 오프셋이다 (보조 평면 글자가 있는 문단만 UTF-16 → 코드포인트 표를 만든다). 빈 결과와 개체 글자(U+FFFC)를 덮는 결과는 버린다.
  - `FindCache`: 문단 텍스트 → 결과. 바뀌지 않은 문단은 같은 문자열 객체라 조회가 싸다.
  - `findInDocument`: 본문(표 문단 자리에 그 표의 셀들, `normalizeTable`의 행·열 순, 덮인 칸 빼고), 각주(참조 순), 머리말·꼬리말(구역 순). 상한(기본 1만)에 닿으면 `truncated`.
  - `replaceMatches`: 스토리마다 뒤에서 앞으로 바꾼다. 결과가 아직 맞는지는 바꾸기 전에 모두 본다 (같은 문단을 다시 찾아 같은 범위가 있는지). 바꾼 글자는 결과 첫 글자의 서식이다. 제안 모드면 `recordSuggestions`로 제안이 된다. 스토리 연산은 `Document.tag`로 감싼다.
  - 정규식 바꾸기는 `$1`·`$&`이다 (`replacementFor`).
  - `Document.contentKey()`: 스토리 판들 + 표 판 (표 레코드가 바뀔 때 올린다). 같으면 찾기 결과가 그대로다.
- **편집기** (`Editor`):
  - `find(query)`, `findNext(dir)`, `findStatus()`, `replace(text)`, `replaceAll(text)`, `clearFind()`, `selectedText()`, 옵션 `onFindRequest(replace)`.
  - 결과는 글자 판이 바뀌면(입력, 원격 변경, 실행 취소) 그리기·상태 조회 때 다시 구한다. 지금 결과는 같은 자리 다음 것으로 옮긴다.
  - 그리기: 스토리별 결과 목록(시작 순)을 줄마다 이분 탐색해 칠한다. 모든 결과는 노랑, 지금 결과는 주황이다. 셀·각주·머리말 레이아웃도 같은 경로(`drawLines`)라 그대로 칠해진다.
  - 결과로 가기: 그 스토리로 들어가(셀 `enterCell`, 각주 `enterNote`, 머리말은 그 스토리를 쓰는 첫 쪽에서 `enterHF`) 범위를 고르고, 화면 위 1/3쯤으로 스크롤한다.
  - 바꾸기는 지금 결과가 선택돼 있을 때만 바꾸고, 아니면 먼저 그리로 간다 (Word와 같다). 모두 바꾸기는 한 트랜잭션이다. 읽기 전용(보기 모드·보기·댓글 역할)이면 바꾸지 않는다.
  - 단축키: Ctrl+F·Ctrl+H는 `onFindRequest`가 있을 때만 가로챈다. F3·Shift+F3은 다음·앞.
- **플레이그라운드**: 찾기 막대 (`find-bar.ts`): 찾을 글·바꿀 글, Aa·낱말·.* 토글, "지금 / 전체", ↑↓, 바꾸기·모두 바꾸기. Enter 다음, Shift+Enter 앞, Esc 닫기.
- 설계(§2)와 다른 점: 결과를 오프셋 차이만큼 옮기는 대신 문단 텍스트 캐시로 다시 구한다. 바뀐 문단만 실제로 다시 찾으므로 결과가 같고 더 단순하다. 장식 레이어를 소스 인터페이스로 일반화하는 것은 맞춤법(5-2)에서 두 번째 사용처가 생길 때 한다.

  - 겉모양은 종류마다 `DecorationStyle {fill, wave, underline}`이다. 바탕은 글자 아래(선택 영역 전), 물결·밑줄은 글자 위(제안 표시 다음)에 그린다. `setDecorationStyle`로 바꾸거나 더한다.

  - `onChange`로 오프셋을 옮기는 부분(§2)은 두지 않았다. 두 소스 모두 문단 텍스트로 다시 구하는 편이 단순하고 싸다 (§12와 같은 결론).
- **검사기** (`spell.ts`, DOM 없음):

  - `HttpChecker`: 한 틱에 들어온 문단을 언어마다 50개씩 한 요청으로 묶는다 (`POST {lang, texts}` → `{results}`). 그만둔 문단은 빼고, 모두 그만두면 요청을 그만둔다.
- **일정** (`SpellSession`, §4.2):
  - 결과 캐시는 텍스트 → 오류이고 LRU 5만 문단이다 (1,000쪽 문서의 문단이 다 들어간다. 작으면 유휴 검사가 앞 문단을 밀어내 편집마다 다시 검사한다).
  - `want(texts)`: 그리기가 끝날 때 보인 문단들을 넘긴다. 캐시에 없는 것을 큐 앞에 넣고, 더 원하지 않는 진행 중 검사는 그만둔다 (`AbortSignal`). 늦게 온 그만둔 결과는 버린다.
  - `wantLater(texts)`: 유휴 시간(`requestIdleCallback`)에 본문 문단을 50개씩 큐 뒤에 넣는다. 이것은 화면에서 벗어나도 그만두지 않는다. 문서가 바뀌면 처음부터 다시 훑는다 (캐시에 있는 문단은 건너뛴다).
  - 동시 검사 4개다. 실패한 문단은 빈 결과로 캐시한다 (계속 다시 보내지 않는다).
  - 결과가 오면 그 문단이 지난 그리기에 보였을 때만 다시 그린다. 보이지 않는 문단의 결과는 다음 유휴 검사만 잇는다.
  - 캐럿 문단은 글자가 바뀐 뒤 500 ms 동안 검사하지 않는다. 그동안 그 문단은 지난 결과를 새 글자로 옮겨(`carryIssues`: 공통 앞부분 안은 그대로, 공통 뒷부분 안은 길이 차이만큼, 바뀐 곳에 닿은 낱말은 버림) 보인다. 그래서 입력 중인 낱말은 오류로 보이지 않고, 다른 밑줄은 깜박이지 않는다.
  - 무시 목록은 세션(문서)마다 낱말 단위이고 저장하지 않는다. 사전에 더하기는 검사기의 `addWord`를 부르고 바로 무시한다.
- **편집기**:

## 14. 5-3 결과: 쪽 그리기 분리

### 구현

- **그리기 대상** (`paint.ts`, DOM 없음):

## 15. 5-4 결과: PDF 내보내기와 인쇄

### 구현

- **패키지 `@quire/pdf`** (DOM 없음, 외부 라이브러리는 이미 쓰던 `harfbuzzjs`뿐):

  - `sfnt.ts`: 표 위치, head의 글꼴 상자, OS/2 대문자 높이, CFF charset. 저장소 글꼴은 Pretendard 조각·Noto Sans KR 모두 **CID 방식 CFF**(ROS)라 내용 스트림에는 글리프 ID가 아니라 charset의 CID를 쓴다 (§5.2의 "글리프 ID를 그대로 CID로"는 틀렸다). 부분화해도 CID가 그대로임을 확인했다.
  - `fonts.ts`: 자리·굵기마다 얼굴 하나. 굵은 얼굴이 없으면 보통 굵기를 합성 굵게(`2 Tr`, 선 굵기 0.03 em). 부분화 뒤 `Type0` + `CIDFontType0`(CFF, `FontFile3 /OpenType`) 또는 `CIDFontType2`(TrueType, `FontFile2`, `CIDToGIDMap /Identity`), `Identity-H`, `W`(1000/em 반올림, 이어진 CID 묶음), `ToUnicode`(클러스터 글자열을 첫 글리프에).

  - `images.ts`: JPEG는 그대로(`DCTDecode`, CMYK는 `Decode` 뒤집기). PNG는 IDAT를 풀지 않고 `FlateDecode` + `Predictor 15`로 넣는다 (팔레트는 `Indexed`, 완전히 투명한 색인 하나면 색 키 `Mask`). 알파(색 유형 4·6)는 픽셀을 풀어 색과 `SMask`로 나눈다. 비월·16비트 알파는 다루지 않는다 (자리표시로 그린다).
  - `export.ts` `exportPdf({env, fonts, asset, subsetter, title})`: ① 이미지 자산만 모으는 대상으로 미리 그린다 ② 자산을 받아 XObject로 쓴다 (못 쓰면 그 자산은 `'error'` → 자리표시) ③ 쪽마다 `PagePainter.paintPage` ④ 쓴 얼굴을 부분화해 쓴다 ⑤ 내용 스트림(글리프 → CID)과 쪽. 자원 사전은 모든 쪽이 함께 쓴다. 제목 문단(h1–h3)으로 책갈피 나무(`/XYZ`, `PageMode /UseOutlines`), `Lang (ko)`, 문서 정보 제목.
- **글자 위치**: 그리기 대상이 `wantsPositions`면 그리기기가 `TextRun.positions`(조각 시작 기준 코드포인트별 레이아웃 x)를 채운다. PDF 대상은 조각을 그 얼굴로 다시 셰이핑하고(커닝·합자, 옛 kern 표: 레이아웃 셰이퍼와 같게), 글리프마다 바라는 x = 클러스터 첫 코드포인트의 레이아웃 x + 클러스터 안 앞 글리프 진행폭으로 둔다. `W` 진행폭과의 차이를 `TJ` 조정값으로 넣는다. 그래서 양쪽 맞춤·커닝·글자 단위 늘림이 레이아웃과 같다. 위치가 없는 조각(목록 기호, 필드, 자리표시 글)은 셰이핑 진행폭으로 놓는다.
- **링크**: `DrawStyle.link`(링크 표시의 주소)를 더했다. 그리기 대상에 `link?`가 있으면 그리기기가 서식 조각마다 글자 높이 사각형을 넘긴다 → `Link` 주석(`URI`, ASCII 밖 글자는 퍼센트 인코딩, 테두리 없음). 화면 대상은 `link`가 없어 그대로다.
- **편집기** `printSource()`: 그리기 환경, 글꼴 자리별 파일(불러온 보통·굵은 조각 바이트를 `loadFonts`가 자리마다 들고 있는다), 자산 바이트, 첫 문단 제목. 엔진 글꼴을 쓰지 않으면(`?fonts=off`) 글꼴이 없어 글자를 그리지 못한다.
- **플레이그라운드**: `PDF` 단추와 Ctrl+P(브라우저 인쇄를 가로챈다). 누르는 즉시 새 창을 열고 다 만들면 PDF로 옮긴다 (팝업이 막히면 내려받기). PDF 모듈과 hb-subset WASM은 처음 내보낼 때 불러온다.

- **브라우저**: 예제·서식·표·각주·구역·다단 예제 6종을 HTML과 Markdown으로 내보냈다 가져와 §6.1 투영을 비교했다. 12번 모두 같고 버린 것이 없다. 한 번에 3–18 ms다 (서식 예제 HTML 254 KB는 이미지 data URL). 내보낸 HTML을 브라우저로 열어 제목·목록 번호(가, 나)·인용·글자 서식·이미지가 보이는 것을 확인했다.
- 타입 검사 통과, 편집기·변환 시험 76개 통과 (붙여넣기 시험 16개 그대로).

### 한계

- §6.1에서 "-"인 요소는 왕복에서 빠진다:
  - HTML: 구역·용지, 머리말·꼬리말, 다단, 떠 있는 이미지(글 안 그림이 된다), 댓글, 제안.
  - Markdown: 그 밖에 밑줄, 크기·색·형광펜·글꼴·첨자, 문단 배치, 병합·너비.
- 떠 있는 이미지가 글 안 그림이 되면 쪽 나눔이 달라진다 (서식 예제의 어울림 그림).
- 정본의 기본이 아닌 스타일 정의(색을 바꾼 제목 1 등)와 목록 정의의 모양(기호·들여쓰기)은 HTML·Markdown에 남지 않는다. 가져오면 기본 정의다.
- Markdown 파서는 GFM의 일부다: 참조식 링크(`[a][1]`), HTML 블록, 목록 안 여러 문단, 느슨한 목록 구분은 하지 않는다.

  - 각주: `hp:footNote`(첫 문단 앞 `autoNum FOOTNOTE`). 링크: `HYPERLINK` 필드(`Path`, 탈출한 `Command`).
  - 댓글: 메시지마다 메모(`MEMO` 필드, 같은 범위, 작성자, FILETIME 시각). 제안: 삽입·삭제 표지(문단을 넘으면 문단 끝에서 닫고 다음 문단에서 다시 연다).
  - 같은 문서는 같은 바이트다.
  - 설계(§6.1)는 "제안은 내보낼 때 최종본"이었지만, 한글이 변경 추적을 그대로 읽으므로 제안으로 낸다.
- **가져오기** (`importHwpx`):
  - `container.xml` → `content.hpf`의 목록·순서로 구역 파일을 찾는다.
  - 글꼴·채우기·글자 모양·문단 모양·번호·글머리표·스타일·변경 추적 표를 푼다. 직접 서식 = 런 모양 − 문단 스타일 모양이고, 문단 속성도 같다. 바탕글이 우리 기본(12pt, Pretendard)과 다르면 본문 스타일로 둔다.
  - 스타일: 이름·영문 이름으로 우리 스타일(바탕글·제목 N·heading N·인용·코드…)에 맞추고, 나머지는 바탕글과의 차이로 새 스타일을 만든다.
  - 번호 문단: 번호 글에 `^`가 없으면 글머리표다. 여백이 목록 정의에서 나온 것이면 들여쓰기를 뺀다.
  - `hp:t` 안: 탭, 줄 바꿈(문단을 나눈다), 고정 폭·묶음 빈칸, 하이픈, 형광펜(`markpenBegin`), 변경 추적.
  - 표는 문단에서 떼어 블록으로 둔다 (한글은 표 뒤 글을 같은 문단에 둔다).
  - 쪽 번호 매기기(`hp:pageNum`)는 머리말·꼬리말이 없으면 그 자리의 쪽 번호 필드로 바꾼다.
  - 문단 중간의 단 정의는 이어지는 구역으로 되살린다.
  - 메모: 같은 범위에 이어진 메모는 답글로 묶는다. 시각은 FILETIME을 먼저 본다.
  - 버리고 보고하는 것: 도형, 묶음 개체, 수식, OLE, 글맵시, 차트, 동영상, 덧말, 양식 개체, 표 안의 표.
- **시험 틀**: `SUPPORT.hwpx`. 단위는 10(1/100pt)이다. 댓글 해결 표시와 이어지는 구역의 용지·여백·쪽 번호는 비교하지 않는다 (HWPX에 없다).
- **플레이그라운드**: `HWPX 저장`, `가져오기`가 `.hwpx`도 받는다.

### 한계

- 메모에 해결 표시가 없다. 이어지는 구역은 앞 구역의 용지·여백·쪽 번호·머리말을 따른다. 날짜 필드와 구역 쪽 수는 내보내지 않는다 (구역 쪽 수는 전체 쪽 수로).
- 첫 쪽 머리말 따로는 첫 쪽 숨김으로만 옮긴다. 줄 간격 %는 글자 크기 기준이라, 글자 크기가 섞인 문단은 한글과 줄 높이가 조금 다를 수 있다.
- 링크 글은 한글에서 파란 밑줄이 아니다 (서식이 아니라 그리기 표시라 내보내지 않는다).
- 글꼴은 이름만 옮긴다 (한글에 Pretendard가 없으면 한글이 바꾼다). 도형·수식·글상자 등은 버린다 (보고).
- 이전 형식 HWP(바이너리)는 하지 않는다.

## 19. 5-8 결과: 플러그인 API, createEditor, React 래퍼

### 구현

- **플러그인 API** (`plugins.ts`, §7):
  - `QuirePlugin`에는 `name`, `commands`, `keymap`, `decorations`, `decorationStyles`, `contextMenu`, `exporters`, `data`(schemaVersion·migrate), `init`(정리 함수)이 있다.
  - §7의 `painters`(겉그리기 갈고리) 대신 `decorationStyles`(바탕·물결·밑줄)를 두었다. 찾기·맞춤법·예제에 충분했다.
  - **`PluginContext`**(좁은 면):
    - 읽기: `document()`, `story()`, `doc()`, `selection()`
    - 선택: `select()`, `reveal(story, from, to)`(셀·각주·머리말로 들어가 고르고 스크롤)
    - 트랜잭션: `edit(fn)`은 편집 중인 스토리 Doc 연산으로 실행 취소·동기화·제안 기록을 탄다. `editDocument(fn)`은 여러 스토리에 걸친 연산이고 실행 취소 한 단계다. 둘 다 `canEdit()`이 아니면 fn을 부르지 않는다.
    - 좌표: `caretRect()`, `rangeRects()`(뷰포트), `hitTest()`
    - 기타: `redraw()`, `on('change' | 'selection' | 'beforeRender' | 'afterRender')`, `run()`, `getData()`·`setData()`
  - 단축키: `'Mod+F'` 꼴을 정규화한다. 한글 자판에서도 `code`로 글자를 맞춘다 (`ㄹ` → F).
- **편집기**:
  - `use(plugin)`·`unuse(name)`·`pluginNames()`·`run('플러그인.명령')`·`commandNames()`·`exporters()`·`exportWith(id)`. 옵션 `plugins`.
  - 키 처리에서 플러그인 단축키를 먼저 본다. 명령이 true면 기본 동작을 막는다.
  - 오른쪽 클릭은 `onContextMenu(e, spell, items)`로 플러그인 메뉴 항목을 함께 넘긴다.
  - 그리기 앞뒤로 `beforeRender`·`afterRender`를 알린다.
  - `undo`·`redo`를 공개했다.
- **찾기·맞춤법을 내장 플러그인으로** (G6):
  - `find-plugin.ts`, `spell-plugin.ts`는 `PluginContext`만 쓴다. 편집기 본체의 찾기 상태·맞춤법 세션·일정 코드(약 400줄)를 옮겼다.
  - 편집기의 `find`·`findNext`·`replace`·`replaceAll`·`clearFind`·`setSpellChecker`·`spellSession`·`spellAt`은 이 플러그인에 맡긴다 (공개 API 그대로).
  - Ctrl+F·Ctrl+H·F3도 찾기 플러그인의 단축키다.
  - 맞춤법의 "보인 문단 알리기·유휴 검사"는 `afterRender` 이벤트로, 캐럿 문단 입력 멈춤은 `selection()`과 자체 타이머로 한다.
  - 미러(스크린리더용 aria-invalid)만 편집기가 내장 맞춤법 플러그인의 세션을 읽는다.
- **예제 플러그인** (`example-plugins.ts`):
  - 글자 수 세기: change 이벤트(묶어서), 명령, 내보내기 형식(통계 글), 장식 없음.
  - 강조 낱말: 장식 소스·겉모양, 명령(더하기·빼기·선택 더하기·다음), 단축키(Ctrl+Alt+K·J), 오른쪽 클릭 항목, 문서 데이터(낱말 목록, 판 1 쉼표 글 → 판 2 옮기기).
- **문서 데이터** (07 §4): `Document.ext`(이름 → `{v, data}`). 정본 `x`로 저장·복원한다 (`quireFromDocument`·`documentFromQuire`). 실시간 동기화는 하지 않는다.
- **`@quire/sdk`** `createEditor({host, doc: QuireDoc, plugins, …})` (08 §3):
  - `run`: 내장 명령은 점 없는 이름(toggleBold·undo·setStyle·bulletList·insertTable…, 플러그인 `core`), 플러그인 명령은 '이름.명령'.
  - `getState`: 불변 스냅샷 — 선택, 캐럿 서식, 문단 스타일, 실행 취소 가능, 제안 모드, 찾기, 플러그인. 값이 같으면 같은 객체다.
  - `subscribe`: 그리기가 끝날 때 알린다. 그 밖에 `caretRect`·`rangeRects`·`toJSON`·`use`·`destroy`.
- **`@quire/react`** (08 §4, JSX 없이 `createElement`):
  - `useQuire(options)`: 처음 옵션으로 제어기 하나.
  - `QuireEditor`: div에 붙인다. 떼면 문서를 정본으로 들고 있다가 다시 붙일 때 이어 쓴다 (StrictMode 이중 마운트).
  - `useEditorState(editor, selector, isEqual)`: `useSyncExternalStore` 기반이고, 고른 값이 같으면 같은 값을 돌려줘 다시 그리지 않는다.
  - `createController`는 React 밖에서 쓴다. react·react-dom 19.1.0은 피어 의존성이고, 시험은 happy-dom 21.0.4(15판의 심각한 취약점 때문에 올렸다)로 한다.
- **플레이그라운드**: 예제 플러그인 둘을 붙였다. 상태 칸에 플러그인 글자 수와 플러그인 목록을 보이고, 오른쪽 클릭 메뉴가 플러그인 항목도 보인다.

### 한계

- 겉그리기 갈고리(`painters`)는 두지 않았다 (장식 겉모양 셋으로 충분했다). 플러그인 데이터는 실시간 동기화하지 않는다 (정본·`.quire`로 남는다).
- 플러그인 명령 이름이 겹치면 나중 것이 이긴다. 권한(읽기 전용·역할)은 트랜잭션에서 막지만, 플러그인이 받은 Document 객체를 직접 바꾸는 것까지 막지는 않는다 (읽기 전용 프록시는 하지 않았다).
- `createEditor`의 `assets`(wasmUrl·workerUrl·fontBaseUrl, 08 §3)는 편집기 옵션(`fonts`, `assets` 저장소)으로 대신한다.
