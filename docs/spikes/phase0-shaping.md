# 0단계 셰이핑 검증 (ADR-0002)

- 날짜: 2026-11-17
- 질문: 1단계부터 글자 폭 측정을 캔버스 `measureText`에서 HarfBuzz(WASM)로 바꿀 것인가. 바꾸면 무엇이 필요한가.
- 코드: `spikes/shaping/` (셰이핑 도우미 `hb.ts`, 말뭉치 `corpus.ts`, Node 시험 `shaping.test.ts`), `scripts/bench-shaping.test.ts`, 브라우저 실험 `apps/playground/shaping.html`
- 도구: harfbuzzjs 1.6.4 (HarfBuzz 15.0.0, `HB_TINY` 빌드)
- 글꼴: Windows의 맑은 고딕(`malgun.ttf`, 13.5 MB, 한글)과 Calibri(`calibri.ttf`, 커닝·합자 있음). 저장소에 넣지 않는다. 브라우저 실험은 `node spikes/shaping/prepare-fonts.mjs`로 `apps/playground/public/spike-fonts/`(gitignore)에 복사해 쓴다.
- 브라우저: 앱 내장 Chromium. 캔버스에는 **같은 글꼴 파일**을 `FontFace`로 넣어 비교했다 (시스템 글꼴 이름이 아님).

## 1. 결정성

`shaping.test.ts`가 말뭉치 9종(아래)을 셰이핑해 지문을 만들고, `shaping.html`이 같은 코드를 브라우저 WASM으로 돌려 비교한다.

| 표본 | 내용 |
|---|---|
| ko-sentence | 현대 한글 음절 + 공백·문장부호 |
| ko-old | 옛한글 첫가끝 조합 (GSUB ljmo/vjmo/tjmo) |
| ko-hanja | 한자 |
| ko-punct | 전각·약물·숫자 |
| ko-mixed | 한글 글꼴로 라틴 섞어 쓰기 |
| latin-liga | Calibri 합자 (fi, ffi, …) |
| latin-kern | 커닝 쌍 |
| latin-marks | 결합 문자 (분해형) |
| emoji | 이모지 (맑은 고딕에 없음) |

- Node 지문 = 브라우저 지문 = `8845f937`. 같은 WASM과 같은 글꼴 파일이면 실행 환경이 달라도 같은 정수를 낸다.
- 화면 px·내부 단위(1/1000pt)로 바꾸는 반올림을 정수 연산 하나로 고정했다 (`toUnit`: 글꼴 단위 × 크기 ÷ upem, 절반은 0에서 먼 쪽). 02 R1(같은 글꼴·같은 엔진이면 같은 쪽 나눔)의 바탕이 된다.
- 기기마다 달라지는 것은 HarfBuzz가 아니라 **글꼴 파일**과 **대체 글꼴**이다 (아래 4).

## 2. 클러스터와 grapheme

| 표본 | grapheme | 글리프 | 클러스터 | 클러스터 안의 grapheme 경계 | 빈 글리프 (.notdef) |
|---|---|---|---|---|---|
| ko-sentence | 129 | 129 | 129 | 0 | 0 |
| ko-old | 7 | 13 | 7 | 0 | 0 |
| ko-hanja | 11 | 11 | 11 | 0 | 0 |
| ko-punct | 30 | 30 | 30 | 0 | 0 |
| ko-mixed | 41 | 41 | 41 | 0 | 0 |
| latin-liga | 37 | 26 | 26 | **11** | 0 |
| latin-kern | 28 | 28 | 28 | 0 | 0 |
| latin-marks | 19 | 19 | 19 | 0 | 0 |
| emoji | 9 | 13 | 9 | 0 | **6** |

- 한글은 옛한글까지 클러스터 = grapheme이다. 옛한글은 자모 여러 글리프가 클러스터 하나로 묶인다. 캐럿 단위(03 §5)와 그대로 맞는다.
- **합자(latin-liga)**: fi·ffi가 글리프 하나라 grapheme 경계 11개가 클러스터 안에 있다. 캐럿을 합자 안에 두려면 GDEF 합자 캐럿(`getLigatureCarets`)이나 균등 분할이 필요하다.
- HarfBuzz가 grapheme을 쪼개는 경우(클러스터 시작이 grapheme 안)는 없었다.
- 이모지는 맑은 고딕에 없어 .notdef가 된다 → **대체 글꼴을 고르는 아이템화(02 ①)가 셰이핑 앞에 있어야 한다.**

## 3. 캔버스 `measureText`와의 차이 (브라우저, 16px)

글자별 (B2): 0.01 px 넘게 다른 글자 수와 최대 차이

| 표본 | grapheme | 다른 글자 | 최대 차이 |
|---|---|---|---|
| ko-*, latin-* (8종) | 293 | 0 | 0.000 px |
| emoji | 9 | 3 | 5.98 px |

런 폭 (B3, px)

| 표본 | HB 글자별 합 | 캔버스 글자별 합 | 캔버스 통째 (커닝 끔) | 캔버스 통째 (커닝 켬) | HB 런 (커닝·합자) |
|---|---|---|---|---|---|
| ko-sentence | 1700.63 | 1700.63 | 1700.63 | 1700.63 | 1700.63 |
| ko-mixed | 388.91 | 388.91 | 388.91 | **388.15** | 388.91 |
| latin-liga | 197.60 | 197.60 | **194.98** | 194.73 | 194.73 |
| latin-kern | 197.79 | 197.79 | 197.79 | 186.00 | 186.00 |
| latin-marks | 116.80 | 116.80 | 116.80 | 116.09 | 116.09 |
| emoji | 128.48 | 124.03 | 124.03 | 124.03 | 128.48 |

- **같은 글꼴 파일이면 캔버스와 HarfBuzz가 같은 폭을 낸다.** 글자별로도, 커닝·합자를 켠 런으로도 같다. 04 O-12(fillText와 HarfBuzz 결과의 불일치)는 같은 파일을 쓰는 한 생기지 않는다.
- **지금 렌더링의 숨은 문제 (latin-liga)**: 지금 편집기는 커닝을 끄고 글자별 폭으로 위치를 계산한 뒤, 줄(탭 사이 구간)을 `fillText` 한 번으로 그린다. 커닝은 껐지만 **캔버스는 합자를 끄지 못한다**. 합자가 있는 글꼴에서는 그린 줄(194.98)이 계산한 위치(197.60)보다 짧아지고, 캐럿·선택이 글자와 어긋난다. 한글 글꼴(맑은 고딕)에서는 차이가 없다.
- **ko-mixed (캔버스 커닝 켬 −0.77 px)**: 한글·라틴이 섞인 줄을 HarfBuzz가 한 런(스크립트 = 한글)으로 셰이핑하면 라틴 구간의 커닝이 빠진다. 브라우저는 스크립트별로 나눠 셰이핑한다. **스크립트별 아이템화**가 필요하다.
- emoji: 캔버스는 시스템 이모지 글꼴로 대체하고, HarfBuzz는 맑은 고딕의 .notdef를 쓴다.

## 4. 줄바꿈 비교 (B4, 맑은 고딕 16px, 본문 폭 602px)

| | 캔버스 측정기 | HarfBuzz 측정기 |
|---|---|---|
| 같은 줄 나눔 / 다른 문단 (209개) | 208 / 1 | |
| 1만 문단 전체 조판 (브라우저) | 371 ms, 968쪽 | 304 ms, 968쪽 |
| 1만 문단 (Node, 고정 폭 측정기 96 ms) | – | 123 ms |

- 다른 1개는 latin-marks 문단이다. 맑은 고딕에 없는 결합 문자를 캔버스는 대체 글꼴로 그리고, HarfBuzz는 폭 0으로 낸다. 역시 대체 글꼴 문제다.
- 0단계 결과 보고서의 "1,000쪽 생성 (968쪽)"과 같은 쪽 수다. 지금 편집기는 같은 맑은 고딕을 시스템에서 쓰고 있었다.

## 5. 속도 (1만 문단 = 130만 글자, 10만 문단 = 1,360만 글자)

| 방식 | Node 1만 | Node 10만 | 브라우저 1만 |
|---|---|---|---|
| 글자별 측정 + 캐시 (지금 레이아웃 방식, 서로 다른 글자 74개) | 전체 조판 123 ms | 1,238 ms | 304 ms |
| 문단 통째 셰이핑 | 1,224 ms (122 µs/문단) | 14,398 ms | 1,397 ms |
| 어절 단위 셰이핑 + 캐시 | 101 ms | 888 ms | 111 ms |
| (참고) 캔버스 `measureText` 문단 통째 | – | – | 약 1,540 ms |

- 문단 통째 셰이핑은 캔버스 문단 측정과 비슷하게 비싸다. 큰 문서의 처음 조판을 문단 통째 셰이핑으로 하면 10만 문단에서 14초다.
- 어절 단위 + 캐시(02 §4의 셰이핑 캐시)는 10배 빠르다. 다만 이 측정 문서는 같은 문단을 반복해 적중률이 96.8%로 높다. 실제 문서의 적중률은 기준 문서 세트로 다시 재야 한다. 어절 사이(공백 경계)의 커닝은 잃는다 (한글 본문에는 영향 없음, 라틴은 공백과 이웃 글자 사이 커닝만).
- 글꼴 불러오기: 맑은 고딕 13.5 MB의 Face·Font 생성 + 첫 셰이핑 6.5 ms (Node). 비용은 셰이핑이 아니라 **내려받기**다.

## 6. 결론 (→ ADR-0002)

1. **HarfBuzz를 채택한다.** 1단계에서 레이아웃의 측정기(`Measurer`)를 셰이퍼 인터페이스로 바꾸고, HarfBuzz 구현을 넣는다. 결정성(Node = 브라우저)과 클러스터 정보(합자 캐럿, 옛한글)가 캔버스로는 얻을 수 없는 것이다.
2. **렌더링은 `fillText`를 유지한다** (04 O-12 해소). 같은 글꼴 파일을 `FontFace`로 넣으면 캔버스와 HarfBuzz의 폭이 같다. 조건:
   - 렌더러는 **엔진이 불러온 글꼴만** 쓴다 (시스템 글꼴 이름 금지).
   - 줄을 `fillText` 한 번으로 그릴 때는 레이아웃도 **같은 런을 커닝·합자를 켠 채 셰이핑한 위치**를 써야 한다. 지금처럼 글자별 폭 합으로 위치를 정하면 합자 글꼴에서 어긋난다 (위 3).
3. **셰이핑 앞에 아이템화가 필요하다**: 스크립트별 런 나누기, 글꼴에 없는 글자(이모지, 결합 문자)의 대체 글꼴. 대체 글꼴도 엔진이 불러온 것이어야 결정성이 유지된다.
4. **셰이핑 단위는 어절 + 캐시**에서 시작한다. 문단 통째는 큰 문서에서 너무 느리다. 한글 본문은 어절 경계에서 잃는 것이 없다.
5. **글꼴 배포가 가장 큰 비용**이다. 한글 글꼴 하나가 수 MB–십수 MB다. 유니코드 범위별로 나눈 부분 글꼴과 로딩 중 임시 메트릭(02 §4)이 필요하다. `harfbuzz.wasm`(gzip 180 KB)은 그에 비하면 작다.

## 남은 것

- 실제 문서(기준 문서 세트, 02 O-7)로 어절 캐시 적중률과 처음 조판 시간 측정.
- 합자 안 캐럿: GDEF 합자 캐럿이 없는 글꼴은 균등 분할.
- 다른 기기(macOS, 모바일)에서 같은 지문이 나오는지: `shaping.html`을 열면 바로 확인된다 (같은 글꼴 파일을 쓰는 조건).
- 세로쓰기·양방향(아랍어·히브리어)은 범위 밖이다.

## 후속: 1단계 적용 (`@quire/shaping`)

레이아웃에 셰이퍼를 넣었다 (02 §4 "1단계 구현"). 검증에서 못 본 것 하나가 나왔다.
- **맑은 고딕의 라틴 커닝이 브라우저와 달랐다.** 맑은 고딕은 GPOS 없이 옛 `kern` 표만 있는데, harfbuzzjs(HB_TINY)는 옛 표를 적용하지 않는다. 브라우저(전체 HarfBuzz)는 적용한다. 검증의 B3 "ko-mixed −0.77 px"도 이것이었다 (스크립트 문제로 봤던 것). 셰이퍼가 GPOS kern이 없는 글꼴에 kern 표를 직접 적용하도록 고쳤고, 1,000쪽 문서 31만 어절 모두 차이 0 px.
