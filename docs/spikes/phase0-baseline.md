### 성능 (V5) — 미달
문서 중간에서 한 글자 입력 → 화면 반영까지의 시간 (Chromium, 개발 서버).

| 문서 | 쪽 | 첫 레이아웃 | 입력 p50 | 입력 p95 |
|---|---|---|---|---|
| 예제 | 1 | 1 ms | 1.9 ms | 2.9 ms |
| 100쪽 생성 | 97 | 88 ms | 48 ms | 57 ms |
| 1,000쪽 생성 | 968 | 1,032 ms | 498 ms | 570 ms |

목표(1,000쪽에서 16 ms) 대비 약 30배 느리다. 쪽 수에 선형으로 늘어난다 (쪽당 약 0.5 ms).

원인 (모두 문서 크기에 비례하는 O(n) 작업):
1. 모델의 오프셋 ↔ 배열 인덱스 변환이 선형 탐색이며, 렌더링 한 번에 여러 번 호출된다 (`resolve`, `positionAt`).
2. `paragraphs()`가 매 변경마다 문서 전체 문자열을 다시 만든다.
3. 쪽 조립을 매번 처음부터 다시 한다 (문단 레이아웃은 캐시 적중).

해결 방향 (1단계 첫 작업):
- 모델: 원소 열을 **청크 + 순위 트리**(각 노드에 보이는 원소 수, `¶` 수 보관)로 바꿔 오프셋 질의를 O(log n)으로.
- 문단 목록: 문단 단위 증분 갱신 (변경된 `¶` 구간만).
- 쪽 조립: 02 §7의 체크포인트 + 수렴 방식.

### 성능 개선 1차 (같은 날)

변경 사항:
1. **모델**: 원소 열을 typed array 청크(청크당 최대 1,024개)로 저장. 원소별 객체·ID 문자열 없음. 카운터 → 청크 표로 ID 해석. 오프셋 질의 O(청크 수 + 청크 크기).
2. **문단 목록 증분 갱신**: 변경 구간의 문단만 다시 만들고 뒤 문단은 오프셋만 이동. 바뀌지 않은 문단은 같은 문자열 객체 유지.
3. **증분 레이아웃**: 문단 ID로 이전 배치를 찾아, 텍스트·시작 상태가 같으면 그대로 재사용(O(1)), 텍스트만 같으면 줄 나눔 재사용 후 위치만 다시 배치, 텍스트가 바뀐 문단만 줄을 다시 나눔.
4. 검증: 무작위 편집 2,000회(시드 5개 × 400)마다 증분 문단 목록 = 처음부터 계산한 결과, 청크 불변식, 위치 왕복을 확인. 증분 레이아웃 = 처음부터 한 레이아웃 확인.

#### 엔진 벤치마크 (Node, DOM 없음, `npm run bench`)
편집 → 문단 목록 → 증분 레이아웃 → 캐럿 계산. 글자 폭은 고정값이라 브라우저의 `measureText`·그리기 비용은 제외.

| 문서 | 캐럿 | 글자 입력 p50 / p95 | Enter p50 / p95 | Backspace p50 / p95 |
|---|---|---|---|---|
| 1,000문단 / 126쪽 | 중간 | 0.27 / 0.57 ms | 0.23 / 0.60 ms | 0.16 / 0.20 ms |
| 10,000문단 / 1,251쪽 | 중간 | 1.5 / 3.4 ms | 2.4 / 5.0 ms | 2.1 / 3.0 ms |
| 10,000문단 / 1,251쪽 | 맨 앞 | 3.3 / 6.7 ms | 6.6 / 10.3 ms | 4.2 / 8.8 ms |
| 100,000문단 / 12,501쪽 | 중간 | 40 / 62 ms | 80 / 134 ms | 59 / 118 ms |

#### 브라우저 (Chromium, 968쪽, 문서 중간)
| 단계 | 글자 입력 p50 | 힙 |
|---|---|---|
| 기초 프로토타입 | 498 ms | - |
| 1차 개선 (청크 + 증분, 원소별 객체) | 12 ms | 217 MB |
| 1차 개선 + typed array 청크 | 측정 불안정 (아래) | 97 MB |

마지막 줄은 브라우저 창이 백그라운드 상태여서 측정값이 흔들렸다 (100쪽 문서에서도 최대 300 ms). 화면에 보이는 상태에서 다시 측정해야 한다. 원소별 객체 방식에서 보였던 100 ms 이상의 간헐적 지연은 GC로 판단했고, typed array 전환으로 힙이 217 → 97 MB로 줄었다.

#### 판단
- **1,000쪽 규모는 엔진 기준 목표(16 ms) 달성**. 쪽 수에 비례하는 비용은 남아 있지만(뒤 문단 오프셋 이동, 재배치) 상수가 작다.
- **10만 문단(V5 기준)은 미달**. 키 입력당 40–80 ms, 힙 1.5 GB. 힙의 대부분은 레이아웃 데이터(문단마다 `cps` 문자열 배열, `xs` 숫자 배열)다.

#### 다음 개선 후보
1. 레이아웃 데이터 압축: `cps` 배열 제거(표시 문자열 + 인덱스), `xs`를 `Float32Array`, `stops`를 `Uint8Array`로
2. 지연 쪽 조립 (02 §7): 화면 근처만 즉시 배치하고 나머지는 유휴 시간에. 앞쪽 편집이 뒤쪽 수천 쪽 재배치를 기다리지 않게
3. 문단 오프셋을 상대값(순위 트리)으로 저장해 뒤 문단 오프셋 이동을 없앰
4. 첫 레이아웃(1,000쪽 0.7–1.5초)을 Worker로 옮기고 보이는 쪽부터 표시

### 성능 개선 2차: 레이아웃 압축 + 지연 쪽 조립

변경 사항:
1. **문단 레이아웃 압축**: 글자별 문자열 배열(`cps`)을 없애고 표시 문자열 1개 + `Float32Array`(x 위치) + `Uint8Array`(캐럿 경계) + 서로게이트가 있을 때만 `Uint32Array`(UTF-16 매핑)로 보관.
2. **`PagedLayout` (02 §7 구현)**: 상태를 가진 증분 레이아웃.
   - 이전 결과와 새 문단 목록을 앞뒤에서 객체 동일성으로 비교해 바뀐 구간만 다시 배치
   - 바뀌지 않은 문단의 시작 상태(쪽, y)가 이전과 같으면 수렴으로 보고 나머지를 그대로 사용
   - 수렴하지 않으면 화면 아래 두 화면까지만 즉시 배치하고 나머지는 8 ms 조각으로 유휴 시간에 처리
   - 위치 질의(캐럿, hit-test, 줄 이동)는 필요한 구간이 아직이면 그 구간까지 먼저 배치
3. **에디터**: 백그라운드 쪽 조립 스케줄링, 쪽 수는 조립 중 추정값(≈) 표시. 캐럿 깜박임 재시작을 Web Animations API로 바꿔 강제 리플로 제거.
4. **플레이그라운드**: 입력 이벤트 로그를 프레임당 한 번만 DOM에 반영 (이전에는 키 입력마다 로그 DOM 갱신 + 강제 리플로로 키 입력당 수 ms~수십 ms가 더해졌음).

검증 중 발견해 고친 버그 (무작위 테스트가 찾음):
- 배치 도중(pending) 편집이 들어오면, pending 앞(직전 문서 기준으로 정확)과 뒤(더 오래된 레이아웃)를 하나의 일관된 결과로 착각해 잘못 수렴하던 문제
- 수렴으로 건너뛴 뒤 수렴 판단 범위를 무제한으로 되돌려, 오래된 레이아웃 결과에서 다시 잘못 수렴하던 문제
- 화면 맨 아래 줄 다음 문단이 아직 배치되지 않았을 때 렌더링이 그 문단을 읽던 문제 (브라우저 확인 중 발견)

테스트: 무작위 편집·조합 문자열·부분 배치·백그라운드 진행·질의를 섞은 시나리오에서 증분 결과 = 처음부터 한 결과를 확인. 기본 4개 시드 × 150단계, 별도로 300개 시드 × 400단계 스트레스 실행 통과.

#### 남은 문제
- **문서 열기**: 10,000쪽 1.3초. 대부분 `Doc.fromText`(1,300만 글자를 코드포인트 배열로 변환 후 청크 생성). 스트리밍 생성 또는 Worker로 옮길 수 있다.
- **메모리**: 모델이 글자당 약 13바이트(코드포인트 4 + 카운터 4 + 삭제 1 + 카운터→청크 표 4). 문단 텍스트 문자열을 모델과 레이아웃이 따로 갖는다.
- **키 입력당 O(문단 수) 작업**: 모델의 뒤 문단 오프셋 이동, 레이아웃의 앞뒤 비교. 10만 문단에서 약 2 ms로 아직 문제는 아니다.
- 스크롤바를 끌어 문서 끝으로 바로 가면, 그 위치까지 남은 쪽 조립을 한 번에 동기적으로 한다 (12,501쪽에서 최대 수 초 멈춤 가능).

### 성능 개선 3차: 열기·GC·그리기·스크롤 이동

변경 사항:
1. **문서 열기**: `Doc.fromText`가 중간 배열 없이 문자열에서 청크를 바로 채우고, 문단 텍스트는 원문을 `split`해서 얻는다. 처음 불러올 때 청크를 거의 채운다(960/1024). 카운터 → 청크 표를 JS 배열에서 `Int32Array`(청크 id)로 바꿨다. 이 표 하나가 열기 시간의 가장 큰 부분(1,370만 항목에 319 ms)이었고 GC 추적 대상이었다.
2. **줄 위치 지연 계산**: `PlacedPara`가 시작·끝 상태 숫자만 들고, 줄별 위치는 읽을 때 계산해 캐시한다. 앞 문단 높이 변화로 뒤가 전부 밀려도 다시 배치할 때 할당이 없다(숫자 4개만 바꿈).
3. **빠른 grapheme 경로**: 결합 문자·서로게이트·ZWJ가 없는 문단(한글 음절, ASCII, Latin-1, CJK, 전각 등)은 `Intl.Segmenter`를 건너뛴다. 처음 전체 조판 비용의 대부분이 이것이었다.
4. **모델 변경 힌트**: 모델이 문단 목록에서 바뀐 구간(앞에서 몇 개, 뒤에서 몇 개가 그대로인지)을 기록해 레이아웃에 넘긴다. 레이아웃이 매 입력마다 문단 목록 전체를 앞뒤로 비교하던 일(브라우저에서 10만 문단에 약 4 ms)이 없어졌다. 힌트가 없으면 예전처럼 비교한다.
5. **줄 단위 그리기**: 캔버스 `fontKerning = 'none'`이면 문자열 폭 = 글자 폭의 합(실측 오차 0 px, 커닝을 켜면 최대 10.6 px 차이)이므로, 글자마다 하던 `fillText`를 줄(탭 사이 구간)마다 한 번으로 줄였다. 지원하지 않는 브라우저는 글자 단위로 그린다.
6. **스크롤바 이동**: 렌더링이 쪽 조립에 프레임당 10 ms까지만 쓰고, 못 끝낸 영역은 "쪽 조립 중… N%" 자리표시로 그린 뒤 다음 프레임에 이어서 한다. 그 영역의 클릭은 무시한다.

간헐 지연의 원인: 3차 전 브라우저에서 보이던 100 ms 안팎의 최대값은 GC가 아니었다. 에디터 코드 없이 같은 캔버스에 `fillText`만 반복해도 똑같이 나타났다(약 17프레임마다 25 ms, 50프레임마다 100–150 ms). 이 환경(숨겨진 창)에서 캔버스 명령 버퍼가 비워질 때 생기는 멈춤으로 보이며, 그리기 호출 수를 줄이자 사라졌다(같은 화면 300회 렌더링 최대 0.5 ms).

### 입력 경로 A (EditContext)

- 지원하는 브라우저(Chromium 계열)에서 기본으로 쓴다. 숨긴 textarea(경로 B)와 같은 입력 의도를 내므로 편집기 쪽 변경은 입력 층 선택뿐이다.
- 단위 시험 8개: 가짜 EditContext가 Chromium 순서로 이벤트를 낸다. 영문 입력, 한글 연속 음절 조합(음절 사이 버퍼 유지), Enter와 조합 중 Enter(Process/229), 조합 중 키 무시, 클릭으로 조합 강제 확정, 후보 창 경계, 선택 위 조합.
- 브라우저(앱 내장 Chromium, 실제 EditContext): 입력·Enter·Backspace·방향키, EditContext 객체에 조합 이벤트를 보내 조합 중 문서 불변 → 확정 때 한 번 들어감·버퍼 비움, `?input=textarea`로 경로 B, 협업 데모(편집기 둘 = EditContext 둘)에서 입력·동기화.
- 실제 IME(한국어 IME의 조합 중 Enter 순서, 후보 창 위치)는 확인하지 않았다 → V1·V2에서 경로 A·B 모두 확인한다.
