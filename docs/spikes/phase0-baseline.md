### 성능 (V5) — 미달
문서 중간에서 한 글자 입력 → 화면 반영까지의 시간 (Chromium, 개발 서버).

| 문서 | 쪽 | 첫 레이아웃 | 입력 p50 | 입력 p95 |
|---|---|---|---|---|
| 예제 | 1 | 1 ms | 1.9 ms | 2.9 ms |
| 100쪽 생성 | 97 | 88 ms | 48 ms | 57 ms |
| 1,000쪽 생성 | 968 | 1,032 ms | 498 ms | 570 ms |

목표(1,000쪽에서 16 ms) 대비 약 30배 느리다. 쪽 수에 선형으로 늘어난다 (쪽당 약 0.5 ms).

원인 (모두 문서 크기에 비례하는 O(n) 작업):
1. 모델의 오프셋 ↔ 배열 인덱스 변환이 선형 탐색이며, 렌더링 한 번에 여러 번 호출된다 (`resolve`, `positionAt`).
2. `paragraphs()`가 매 변경마다 문서 전체 문자열을 다시 만든다.
3. 쪽 조립을 매번 처음부터 다시 한다 (문단 레이아웃은 캐시 적중).

해결 방향 (1단계 첫 작업):
- 모델: 원소 열을 **청크 + 순위 트리**(각 노드에 보이는 원소 수, `¶` 수 보관)로 바꿔 오프셋 질의를 O(log n)으로.
- 문단 목록: 문단 단위 증분 갱신 (변경된 `¶` 구간만).
- 쪽 조립: 02 §7의 체크포인트 + 수렴 방식.

### 성능 개선 1차 (같은 날)

변경 사항:
1. **모델**: 원소 열을 typed array 청크(청크당 최대 1,024개)로 저장. 원소별 객체·ID 문자열 없음. 카운터 → 청크 표로 ID 해석. 오프셋 질의 O(청크 수 + 청크 크기).
2. **문단 목록 증분 갱신**: 변경 구간의 문단만 다시 만들고 뒤 문단은 오프셋만 이동. 바뀌지 않은 문단은 같은 문자열 객체 유지.
3. **증분 레이아웃**: 문단 ID로 이전 배치를 찾아, 텍스트·시작 상태가 같으면 그대로 재사용(O(1)), 텍스트만 같으면 줄 나눔 재사용 후 위치만 다시 배치, 텍스트가 바뀐 문단만 줄을 다시 나눔.
4. 검증: 무작위 편집 2,000회(시드 5개 × 400)마다 증분 문단 목록 = 처음부터 계산한 결과, 청크 불변식, 위치 왕복을 확인. 증분 레이아웃 = 처음부터 한 레이아웃 확인.

#### 엔진 벤치마크 (Node, DOM 없음, `npm run bench`)
편집 → 문단 목록 → 증분 레이아웃 → 캐럿 계산. 글자 폭은 고정값이라 브라우저의 `measureText`·그리기 비용은 제외.

| 문서 | 캐럿 | 글자 입력 p50 / p95 | Enter p50 / p95 | Backspace p50 / p95 |
|---|---|---|---|---|
| 1,000문단 / 126쪽 | 중간 | 0.27 / 0.57 ms | 0.23 / 0.60 ms | 0.16 / 0.20 ms |
| 10,000문단 / 1,251쪽 | 중간 | 1.5 / 3.4 ms | 2.4 / 5.0 ms | 2.1 / 3.0 ms |
| 10,000문단 / 1,251쪽 | 맨 앞 | 3.3 / 6.7 ms | 6.6 / 10.3 ms | 4.2 / 8.8 ms |
| 100,000문단 / 12,501쪽 | 중간 | 40 / 62 ms | 80 / 134 ms | 59 / 118 ms |

#### 브라우저 (Chromium, 968쪽, 문서 중간)
| 단계 | 글자 입력 p50 | 힙 |
|---|---|---|
| 기초 프로토타입 | 498 ms | - |
| 1차 개선 (청크 + 증분, 원소별 객체) | 12 ms | 217 MB |
| 1차 개선 + typed array 청크 | 측정 불안정 (아래) | 97 MB |

마지막 줄은 브라우저 창이 백그라운드 상태여서 측정값이 흔들렸다 (100쪽 문서에서도 최대 300 ms). 화면에 보이는 상태에서 다시 측정해야 한다. 원소별 객체 방식에서 보였던 100 ms 이상의 간헐적 지연은 GC로 판단했고, typed array 전환으로 힙이 217 → 97 MB로 줄었다.

#### 판단
- **1,000쪽 규모는 엔진 기준 목표(16 ms) 달성**. 쪽 수에 비례하는 비용은 남아 있지만(뒤 문단 오프셋 이동, 재배치) 상수가 작다.
- **10만 문단(V5 기준)은 미달**. 키 입력당 40–80 ms, 힙 1.5 GB. 힙의 대부분은 레이아웃 데이터(문단마다 `cps` 문자열 배열, `xs` 숫자 배열)다.

#### 다음 개선 후보
1. 레이아웃 데이터 압축: `cps` 배열 제거(표시 문자열 + 인덱스), `xs`를 `Float32Array`, `stops`를 `Uint8Array`로
2. 지연 쪽 조립 (02 §7): 화면 근처만 즉시 배치하고 나머지는 유휴 시간에. 앞쪽 편집이 뒤쪽 수천 쪽 재배치를 기다리지 않게
3. 문단 오프셋을 상대값(순위 트리)으로 저장해 뒤 문단 오프셋 이동을 없앰
4. 첫 레이아웃(1,000쪽 0.7–1.5초)을 Worker로 옮기고 보이는 쪽부터 표시
