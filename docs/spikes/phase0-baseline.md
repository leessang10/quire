## 검증 결과

### 자동 테스트
`npm test` — 모델 13개, 레이아웃 10개 통과.

### 입력 (V1) — 부분 검증
아래는 **합성 이벤트**로 브라우저별 순서를 흉내 낸 결과다. 실제 IME로 한 검증은 아니다.

| 시나리오 | 결과 |
|---|---|
| 조합 중 글자는 문서에 들어가지 않고 표시만 됨 | 통과 |
| 음절마다 조합 종료·시작 ("한" → "글") | 통과: `한글` |
| 조합 중 Enter, `beforeinput`이 `compositionend`보다 먼저 옴 | 통과: 확정 후 문단 분할 |
| 조합 중 클릭, `compositionend`가 오지 않는 경우 | 통과: preedit 확정 후 이동 |
| 연속 입력 실행 취소가 한 단위로 묶임, 다시 실행 | 통과 |

**남은 일**: 06 §2의 실제 환경 표(Windows·macOS·iOS·Android, 각 입력기)에서 직접 입력해 확인. 플레이그라운드의 입력 이벤트 로그가 이 용도다.

### 성능 (V5) — 미달
문서 중간에서 한 글자 입력 → 화면 반영까지의 시간 (Chromium, 개발 서버).

| 문서 | 쪽 | 첫 레이아웃 | 입력 p50 | 입력 p95 |
|---|---|---|---|---|
| 예제 | 1 | 1 ms | 1.9 ms | 2.9 ms |
| 100쪽 생성 | 97 | 88 ms | 48 ms | 57 ms |
| 1,000쪽 생성 | 968 | 1,032 ms | 498 ms | 570 ms |

목표(1,000쪽에서 16 ms) 대비 약 30배 느리다. 쪽 수에 선형으로 늘어난다 (쪽당 약 0.5 ms).

원인 (모두 문서 크기에 비례하는 O(n) 작업):
1. 모델의 오프셋 ↔ 배열 인덱스 변환이 선형 탐색이며, 렌더링 한 번에 여러 번 호출된다 (`resolve`, `positionAt`).
2. `paragraphs()`가 매 변경마다 문서 전체 문자열을 다시 만든다.
3. 쪽 조립을 매번 처음부터 다시 한다 (문단 레이아웃은 캐시 적중).

해결 방향 (1단계 첫 작업):
- 모델: 원소 열을 **청크 + 순위 트리**(각 노드에 보이는 원소 수, `¶` 수 보관)로 바꿔 오프셋 질의를 O(log n)으로.
- 문단 목록: 문단 단위 증분 갱신 (변경된 `¶` 구간만).
- 쪽 조립: 02 §7의 체크포인트 + 수렴 방식.

### 미검증
- V2 IME 후보 창 위치: textarea를 캐럿 위치로 옮기도록 구현했으나 실제 IME로 확인하지 않음
- V3 접근성: 미러 DOM만 있고 스크린리더로 확인하지 않음
- V4 동기화 의도 보존 (M1/M2 비교): 시작하지 않음

## 알려진 한계 (의도된 단순화)
- 서식, 표, 이미지 없음. 왼쪽 정렬만

- 드래그 선택 중 자동 스크롤 없음 (03 O-10)
- 경로 A(EditContext) 미구현
