# 0단계 V4: 동기화 의도 보존 비교

- 날짜: 2026-11-16
- 관련: [05 협업과 이력 §3](../design/05-collaboration-and-history.md), [ADR-0003](../adr/0003-crdt-choice.md), [06 로드맵 §2 V4](../design/06-roadmap.md)
- 코드: [`spikes/crdt`](../../spikes/crdt) (Loro `loro-crdt` 1.17.1)

## 질문

문서 모델을 CRDT 위에 둘 때, 문단 분할·병합·이동이 동시 편집과 겹쳐도 사용자의 의도가 지켜지는가?
05 §3의 두 후보를 Loro로 구현해 같은 시나리오로 비교했다.

| 모델 | 표현 | 분할 | 병합 | 이동 |
|---|---|---|---|---|
| **M1 평평한 텍스트** | 스토리 = `LoroText` 하나, 문단 끝마다 `\n`(¶) | ¶ 삽입 | ¶ 삭제 | 문단 텍스트 삭제 후 다른 곳에 다시 삽입 (잘라내기+붙여넣기) |
| **M2 문단 리스트** | `LoroMovableList`의 원소마다 `LoroText` | 뒷부분을 잘라 새 문단 컨테이너에 넣음 | 뒤 문단 텍스트를 앞 문단에 붙이고 뒤 문단 삭제 | 리스트 `move` |

M1은 이동을 위한 포워딩(05 §3의 M1안)을 아직 구현하지 않은 기본형이다.

### 해석

- **M1은 글자를 잃지 않는다.** 실패는 모두 문단 이동·통째 삭제(S7–S11, S16)이고, 결과는 "글자가 원래 자리에 남는다"(위치 어긋남)이다. 이동 ∥ 이동만 문단이 복제된다(S8). 이것은 이동을 잘라내기+붙여넣기로 처리하는 편집기(Google Docs의 끌어서 옮기기 등)와 같은 동작이다.
- **M2는 가장 흔한 동시 편집에서 글자를 잃거나 복제한다.** 분할·병합이 "텍스트를 다른 컨테이너로 복사하고 원본을 지움"이기 때문에, 그 사이 원본에 들어온 편집은 지워진 컨테이너에 남아 사라지거나(S4, S6, S17), 복사본과 원본에 모두 남는다(S3, S13, S13b). 이동은 완벽하다.
- 문단 분할·병합·입력은 이동보다 훨씬 자주 일어난다. M2의 실패가 더 치명적이다.

### 발견해 고친 것

M1 첫 구현은 무작위 테스트 200회 중 136회에서 스토리 끝 표식(마지막 ¶) 뒤에 글자가 남는 구조 위반을 냈다. 마지막 문단을 옮기거나 지울 때 마지막 ¶까지 지웠기 때문이다. 문서 모델 규칙(01 §6 "마지막 ¶는 지울 수 없다")대로 마지막 문단은 "앞 문단의 ¶ + 내용"을 지우도록 바꾸자 0회가 되었다. 이 규칙은 실제 동기화 계층에서도 반드시 지켜야 한다.

### M1의 동기화 비용

M1에서 입력 자체(`insert` + `commit`)는 0.03 ms 정도다. 비용은 **업데이트를 내보내거나 받아들일 때마다 드는 고정 비용**이고, 텍스트 길이에 비례한다.

| 문서 | 내보내기(커밋 시 push) | 원격 적용 1회 | 키 입력 100회를 묶어서 적용 |
|---|---|---|---|
| 1만 문단 (140만 자) | 1.3 ms | 1.3 ms | 1.3 ms |
| 3만 문단 (410만 자) | 8.1 ms | 8.1 ms | 8.4 ms |
| 10만 문단 (1,370만 자) | 16 ms | 16 ms | 18.5 ms |

연산 수가 아니라 **호출 횟수**에 비례하므로 묶으면 해결된다. 문서를 문단 단위로 나눠 만들어도, 스냅샷에서 불러와 편집해도 같은 경향이었다.

대응:
1. 동기화 계층(`@quiredoc/sync`)을 **Worker**에서 돌린다. 편집기는 자체 모델(`@quiredoc/model`)로 편집하고 연산만 Worker에 넘기므로(00 §4, 05 §2) 이 비용이 입력 지연에 들어가지 않는다.
2. 내보내기·원격 적용을 **50–100 ms 단위로 묶는다.** 1만 쪽에서도 초당 10–20회 × 16 ms 수준.
3. Loro 쪽 원인(큰 텍스트 컨테이너의 업데이트 인코딩·적용 고정 비용)은 업스트림에 확인한다.

1,000쪽 규모(1.3 ms)에서는 문제가 되지 않는다.

## 결론

1. **CRDT는 Loro, 문서 표현은 M1(평평한 텍스트 + ¶)을 채택한다.** 01 §2의 설계와 같다.
   - 글자 유실이 없고, 분할·병합·입력·실행 취소의 동시 편집이 모두 의도대로 동작한다.
   - 문단 경계를 넘는 범위(댓글, 변경 추적, L7)가 텍스트 범위 하나로 자연스럽게 표현된다. M2에서는 컨테이너를 넘는 범위를 별도로 만들어야 한다.
   - 스냅샷이 M2보다 약 9배 작고, 1만 쪽 문서를 만들고 내보내는 데 M2는 1분 이상 걸린다.
2. **문단 이동은 당분간 잘라내기+붙여넣기 의미론으로 둔다.** 동시 편집 시 글자는 잃지 않고 원래 자리에 남는다. 이동 ∥ 이동은 복제된다.
3. **이동을 1급으로 만드는 일(L8)은 별도 연구 과제로 남긴다.** 후보:
   - M1 + 이동 포워딩: 이동 기록을 남기고, 원래 자리에 남은 동시 편집을 옮겨진 자리로 보낸다. 여러 피어가 같은 보정을 동시에 하면 복제되므로 "누가 보정하는가" 규칙이 필요하다.
   - M1 + 문단 순서 덧씌우기: 내용은 평평한 텍스트에 두고, 표시 순서만 별도의 이동 가능한 리스트로 관리한다. 두 정보 사이의 정규화 규칙이 결정적이어야 한다.
   - 이동을 지원하는 자체 시퀀스 CRDT (05 §3 M3).
4. 동기화 계층은 Worker + 묶음 전송을 전제로 설계한다.

## 후속: 문단 이동 의미론 (M3)

M1의 실패는 모두 같은 원인이었다: 이동이 **글자를 실제로 옮기기**(삭제 후 다시 삽입) 때문에, 동시에 들어온 편집이 원래 자리에 남는다.
M3는 M1의 평평한 텍스트를 그대로 두되 **글자를 옮기지 않는** 이동을 시험했다.

### M3 구조: 평평한 텍스트 + 구획 순서

| 요소 | 표현 |
|---|---|
| 내용 | M1과 같은 `LoroText` 하나, 문단 끝은 ¶ |
| 구획 | 보이지 않는 구획 표식(BRK, U+E000)으로 텍스트를 나눈 조각. ID = BRK 문자의 CRDT ID (`text.getCursor(pos).pos()`), 첫 구획은 `root` |
| 화면 순서 | 구획 ID의 `LoroMovableList` (`order`). 끝에 고정 항목 END |
| 숨김 | 구획 ID → true 맵 (`hidden`) |
| 이동 표시 | 이동 명령으로 옮긴 구획 ID 맵 (`moved`) |

| 편집 | 동작 |
|---|---|
| 입력·분할·병합 | M1과 같은 텍스트 연산 |
| 이동 | 문단 앞뒤에 BRK를 넣어 그 문단만의 구획을 만들고, `order`에서 **구획 ID만** 옮긴다. 텍스트는 제자리에 있으므로 동시 편집이 함께 움직인다 |
| 문단 삭제 | 문단을 구획으로 떼어 내 숨긴다. 동시 편집도 함께 숨겨진다(삭제 우선). 단, 문서 마지막 ¶를 가진 문단은 텍스트를 지운다(보이는 문단이 항상 남도록) |
| 떨어진 문단 병합 | 화면에서는 이웃이지만 텍스트상 떨어진 경우(이동 후): 뒤 문단 내용을 복사해 붙이고 뒤 문단을 숨긴다 |

표시 규칙 (모든 피어가 같은 상태에서 같은 결과를 내는 결정적 규칙):
1. `order`에 있는 구획을 그 순서대로
2. `order`에 없는 구획(동시에 생긴 구획)은 텍스트 순서상 바로 앞 구획 뒤에
3. **연달아 붙은 BRK는 한 구획의 별칭**으로 본다 (두 피어가 같은 자리를 동시에 나누면 생김). 위치는 별칭 중 이동 명령으로 옮겨진 것을 우선, 그 안에서 가장 앞선 것
4. 숨긴 구획은 표시하지 않음, 구획 끝에 ¶ 없이 남은 텍스트는 한 문단

| 동시에 서로 다른 문단을 옮기면 한쪽 의도가 사라짐 (S18 1차) | 별칭 중 "나머지 부분"의 위치가 "옮긴 문단"의 위치를 이김 | 이동 명령으로 옮긴 별칭 우선 (`moved`) |
| 무작위 시험에서 보이는 문단이 0개 (200회 중 1회) | 두 피어가 짧은 문서의 남은 문단을 동시에 숨김 | 마지막 ¶를 가진 문단은 숨기지 않음 |

### 남은 문제

- **S18 (서로 다른 문단을 동시에 "맨 뒤로")**: "맨 뒤로"가 리스트에서 "그때의 마지막 항목 다음"으로 기록되는데, 다른 피어가 같은 구간에 동시에 추가한 항목들 사이에서 CRDT가 한 피어의 항목을 통째로 앞에 놓는다. 끝 고정 항목(END)을 두어도 해결되지 않았다. 리스트 위치 대신 **"구획 X 다음에 온다"는 기준(anchor) 방식**으로 순서를 표현해야 할 것으로 보인다(RGA 방식의 작은 순서 CRDT, 또는 순환을 막는 트리 이동).
- **S25**: 이동 목적지가 문서의 마지막 문단이고 동시에 삭제되면 빈 문단 하나가 남는다.
- **구획 정리**: 이동할 때마다 BRK와 구획이 늘어난다. 내용이 빈 구획, 화면에서도 텍스트상에서도 이웃인 구획을 합치는 정리 규칙이 필요하다(정리 자체도 동시 편집에 안전해야 함).
- **비용**: 시험 구현은 연산마다 화면 순서를 처음부터 다시 계산한다(O(문서 크기)). 실제 구현은 구획 단위로 증분 계산해야 한다. CRDT 데이터는 M1에 BRK 몇 글자와 작은 리스트·맵이 더해지는 수준이라 크기·속도는 M1과 같다고 보며, 측정하지는 않았다.

### 결론 (갱신)

- 문서 표현은 **M3(평평한 텍스트 + 구획 순서)를 목표로 한다.** 분할·병합·입력은 M1과 같으므로 M1의 장점(유실 없음, 문단 경계를 넘는 범위)을 그대로 가지면서, 문단 이동을 1급 연산으로 만든다.
- 편집 모델(`@quiredoc/model`)에 **구획 표식 원소**와 **구획 순서**를 추가해야 한다 (01 §2 갱신).
- 순서 표현을 기준(anchor) 방식으로 바꾸는 일, 구획 정리 규칙은 4단계(협업) 설계 과제로 남긴다.

## 후속 2: 기준(anchor) 방식 검토와 M4 (끝 표식 구획)

### 기준 방식을 그대로 쓰지 않은 이유

"구획 X 다음에 온다"를 각 구획이 기록하는 기준 트리(RGA처럼)는 S18을 풀 것처럼 보이지만, 이동에 맞지 않는다.

- 구획 B가 A를 기준으로 삼고 있을 때 A를 옮기면 **B도 A를 따라간다.** 문단 하나를 옮겼는데 뒤 문단들이 끌려간다.
  이를 막으려면 이동할 때마다 뒤따르던 구획들의 기준을 다시 써야 하고, 그 재기록끼리 동시 편집에서 다시 충돌한다.
- 각 항목이 "제 자리(slot)"를 가지고 자리만 옮기는 것은 이미 `LoroMovableList`가 제공한다.
  문제는 순서 표현이 아니라 **어떤 구획이 원래 자리를 유지하느냐**였다.

### S18의 실제 원인

M3에서 구획 ID = 구획을 **시작하는** BRK.
문단 p를 떼어 내려면 p 앞뒤에 BRK를 넣는데, 그러면 **p 뒤의 나머지 부분이 새 ID**를 받는다.
S18에서 A는 1문단을, B는 2문단을 떼어 내므로 두 피어가 같은 원래 구획에서 서로 다른 "나머지" 구획을 새로 만든다.
이 새 구획들은 각자 order에 추가되는데, 동시에 추가된 항목끼리의 순서를 CRDT가 피어 단위로 정하므로 한쪽의 이동이 덮인다.

### M4: 구획 ID = 구획을 끝내는 BRK

- 구획 = 다음 BRK 묶음까지. ID = 그 BRK들(연달아 붙은 BRK는 별칭), 마지막 구획은 `tail`.
- 문단 p 뒤에 BRK를 넣으면 [앞부분 + p]가 새 BRK를 ID로 받고, **나머지 부분은 원래 ID와 order 자리를 그대로 유지**한다. p 앞에도 BRK를 넣으면 앞부분만 새 ID를 받는다. 새 ID는 모두 원래 구획 바로 앞에 놓는다.
- order에 없는 구획(동시에 생긴 구획)은 텍스트 순서상 **다음** 구획 바로 앞에 둔다.
- 그 밖의 규칙(숨김, 이동 표시, 별칭 우선순위, 마지막 ¶ 보호)은 M3와 같다. (이후 별칭 규칙은 M4에서 뺐다: [후속 5](#후속-5-빈-구획과-별칭-규칙))

이렇게 하면 떼어 낸 문단만 새 ID를 받으므로, 두 피어가 같은 구획에서 서로 다른 문단을 떼어 내도 나머지 구획의 자리가 겹치지 않는다.

- 순서 표현을 기준 트리로 바꾸는 일은 하지 않는다. 이동 리스트의 자리 개념을 그대로 쓰고, 구획 ID를 끝 표식으로 정한다.

## 후속 3: 구획 정리 규칙

M4는 이동·삭제할 때마다 BRK와 order 항목이 늘고, 문단 삭제는 숨김이라 지운 문단의 글자가 텍스트에 계속 남는다.
무엇을 정리할 수 있는지, 동시 편집에 안전한지를 시험했다 (`spikes/crdt/src/cleanup.test.ts`, 결과 `spikes/crdt/results/cleanup.md`).

| 규칙 | 내용 | 상태를 바꾸는가 |
|---|---|---|
| R1 화면 계산에서 합쳐 보기 | 숨긴 구획(과 빈 구획)을 건너뛰고, 텍스트상으로도 화면상으로도 이웃한 보이는 구획(앞 구획이 ¶로 끝남)을 한 조각으로 다룬다 | 아니오 (계산 규칙) |
| R2 숨긴 내용 지우기 | 문단 삭제로 숨긴 구획의 내용을 지운다. BRK·숨김 표시와 마지막 ¶ 하나는 남긴다 | 예 (글자 삭제) |

### R3: 편집 중 물리 삭제는 안전하지 않다

첫 문단을 맨 뒤로 보냈다가 되돌려 하나로 볼 수 있는 구획 둘을 만든 뒤, A가 정리하는 동안 B가 편집했다.

| # | B의 동시 편집 | 정리 안 함 | A가 정리 |
|---|---|---|---|
| C1 | 첫 문단 삭제 | ✅ | ❌ 지운 문단이 되살아남 (숨김 표시가 가리키던 BRK가 사라짐) |
| C2 | 첫 문단을 맨 뒤로 | ✅ | ⚠️ 이동이 사라짐 (옮긴 order 항목이 지워짐) |
| C3 | 마지막 문단을 첫 문단 다음으로 | ✅ | ⚠️ 엉뚱한 자리로 감 (목적지 구획이 사라짐) |

BRK는 동시 편집이 "이 구획"을 가리키는 유일한 ID다. 지우는 순간 그 ID를 쓰는 동시 연산(숨김, 이동, 목적지)의 의도가 깨진다. 다른 피어의 연산이 아직 오고 있을 수 있는 동안에는 지울 수 없다.

### R2: 숨긴 내용 지우기

| # | 시나리오 | M4 | M5 (M4 + R2) |
|---|---|---|---|
| D1 | 삭제 ∥ 같은 문단에 입력 | ✅ | ✅ (동시 입력도 숨긴 구획에 들어가 숨겨짐) |
| D2 | 삭제 후 실행 취소 | ✅ | ✅ |
| D3 | 삭제 ∥ 같은 문단 이동 | ✅ | ✅ |
| D4 | 삭제 ∥ 앞 문단과 병합 | ✅ | ✅ |
| D5 | 삭제 ∥ 같은 문단에 입력, 그 뒤 삭제 실행 취소 | ✅ | ⚠️ 동시 입력 X가 문단 끝으로 감 |

- 첫 구현은 내용을 모두 지웠다가 D3·D4에서 **앞 문단이 사라졌다.** 구획이 비면 앞뒤 BRK가 맞붙어 별칭 규칙에 따라 앞 구획과 한 구획이 되고, 숨김 표시가 그 구획 전체에 걸린다. 마지막 ¶ 하나를 남겨 해결했다.
  → (후속 5에서 해결: 원인은 별칭 규칙이었고, M4에서 빼자 구획이 비어도 안전해져 내용을 모두 지운다.) 당시 결론: **어떤 연산도 구획을 완전히 비우면 안 된다**는 조건이 생긴다 (병합으로 빈 문단 하나뿐인 구획의 ¶가 지워지는 경우도 같은 위험. 후속 확인 필요).
- D5: Loro 실행 취소는 지운 글자를 새 글자로 다시 넣으므로, 그사이 들어온 동시 입력과의 원래 순서를 잃는다. **R2를 그 삭제가 실행 취소 기록에서 빠질 때 실행하면** D5는 생기지 않는다 (되돌릴 수 없으면 되살릴 일도 없음).

### 결론: 채택하는 정리 규칙

1. **R1 채택**: 화면 순서 계산(증분 인덱스)은 숨긴 구획을 건너뛴 조각 단위로 한다. 상태를 바꾸지 않으므로 동시 편집과 무관하게 안전하다.
2. **R2 채택, 시점 제한**: 숨긴 구획의 내용은 그 삭제가 실행 취소 기록에서 빠질 때(또는 세션이 끝날 때) 지운다. BRK와 숨김 표시는 남긴다 (후속 5 이후 ¶도 남기지 않음).
3. **R3 기각 (편집 중)**: BRK와 order 항목은 온라인으로 지우지 않는다. 남는 양은 이동·삭제 1회당 BRK 3개 이하라 작다. 완전히 비우는 일은 **정본 JSON으로 저장 후 다시 열 때**(ADR-0004: 정본에는 ID·묘비가 없음) 또는 아무도 편집하지 않을 때 서버가 하는 **새 판(epoch) 압축**으로 한다.

## 후속 4: S25와 보초 구획

### 원인

S25: A가 1문단을 4문단(마지막 문단) 앞으로 옮기는 동안 B가 4문단을 지운다.

- A는 이동 목적지를 표시하려고 4문단 바로 앞에 BRK를 넣는다.
- 4문단은 문서의 마지막 ¶를 가지므로 숨길 수 없고, B는 예외 규칙대로 **"앞 문단의 ¶ + 이 문단 내용"**을 지운다.
- 합치면 3문단의 ¶와 4문단 내용 사이에 A의 BRK가 끼어, 3문단은 ¶ 없는 문단이 되고 4문단의 ¶만 빈 문단으로 남는다.

예외 규칙은 "텍스트상 이웃한 두 문단은 같은 구획에 있다"고 가정하는데, 동시 편집에서는 그 사이에 구획 경계가 생길 수 있다. 이 예외는 M1에서 구조 위반을 막으려고 생겼고, M3에서 "보이는 문단 0개"를 막는 데도 쓰였다.

### 해결: 보초 구획 (M4에 적용)

- 텍스트 끝은 늘 `[BRK ¶]`이다. 마지막 구획(`tail`)은 그 ¶ 하나뿐인 **보초**로, 화면에 나오지 않는다. 스토리가 ¶로 끝난다는 조건은 보초가 지킨다.
- 사용자 문단은 모두 BRK로 끝나는 보통 구획에 있으므로, **문단 삭제는 예외 없이 숨김**이다.
- 보이는 문단이 0개면 **빈 문단 하나를 보여 준다** (가상 문단). 여기에 입력하거나 나누면 그때 보초 바로 앞에 `[¶ BRK]`를 넣어 실제 빈 문단 구획을 만든다.
- 정리 규칙 R1·R3에서 보초 앞 BRK는 합치지 않는다 (사용자 문단이 표시하지 않는 보초에 합쳐짐).

### S29: 자리표시 문단

보초만 넣은 상태에서는, 보이는 문단이 0개일 때 입력하면 그 순간 `[¶ BRK]`를 새로 넣어 빈 문단을 만들었다.
두 피어가 동시에 그렇게 하면 삽입이 두 번 일어나 문단이 둘(`["X","Y"]`)이 된다.
텍스트 삽입은 멱등이 아니므로, **두 피어가 같은 기존 구획을 고르게** 해야 한다.

- 문서에 **미리 만들어 둔 빈 문단 구획**(자리표시, `placeholder` 맵에 표시)을 늘 하나 이상 둔다. 기준 문서는 `[문단들 BRK][¶ BRK][¶ 보초]`로 시작한다.
- 쓰지 않은 자리표시는 보이지 않는다. 보이는 문단이 하나도 없을 때만 **텍스트 순서상 첫 자리표시**가 빈 문단으로 보인다.
- 그 빈 문단에 입력하거나 나누면 `used` 맵에 표시하고(맵 설정이라 두 피어가 동시에 해도 결과는 하나) 그 구획에 입력한다. 그리고 다음에 쓸 자리표시를 보초 앞에 새로 만든다. 두 피어가 동시에 새 자리표시를 만들어도 쓰지 않은 것은 보이지 않으므로 해가 없다.
- 자리표시로 보이는 빈 문단의 삭제는 아무것도 하지 않는다. 정리 규칙(R1·R3)은 쓰지 않은 자리표시를 합치지 않는다.

## 후속 5: 빈 구획과 별칭 규칙

### 위험

M3에서 들인 **별칭 규칙**(연달아 붙은 BRK = 한 구획)은 두 피어가 같은 자리를 동시에 나눌 때 생기는 빈 구획을 처리하려던 것이다.
그런데 구획 내용이 모두 지워져도 앞뒤 BRK가 맞붙는다. 그러면 비어 버린 구획이 **이웃 구획과 한 구획**이 되고, 빈 구획에 걸린 숨김·이동이 이웃 구획에 번진다.

재현 (S31): 1문단(가나다라)을 맨 뒤로 옮겨 `[가나다라¶](b1)[마바사아¶자차카타¶하하하하¶]` 구조를 만든 뒤
- A: 마바사아와 자차카타를 합치고(¶ 삭제) 마바사아 글자를 지움
- B: 마바사아 문단 삭제 → 마바사아 뒤에 BRK를 넣어 떼어 내고 숨김

합치면 마바사아 글자와 ¶가 모두 지워져 b1과 B의 BRK가 맞붙고, B의 숨김 표시가 b1 구획(가나다라)까지 숨긴다. **가나다라가 사라진다** (M4·M5 유실).
병합(¶ 삭제)과 문단 떼어 내기(BRK 삽입)가 동시에 일어나면 ¶ 없는 구획 조각이 생기고, 그 조각의 글자가 지워지면 구획이 빈다. 드물지만 일반 편집만으로 생긴다.

### 해결: M4에서 별칭 규칙을 뺀다

끝 표식 구획(M4)에서는 별칭 규칙이 필요 없었다. 같은 문단을 두 피어가 동시에 떼어 내면 BRK 두 개가 맞붙어 빈 구획이 생기는데, 문단은 텍스트상 첫 BRK의 구획에 들어가고 빈 구획은 아무것도 표시하지 않는다. 한쪽 이동이 이기는 결정적 결과다 (S8 통과).

| | 별칭 규칙 있음 (기존 M4) | 별칭 규칙 없음 (M4) |
|---|---|---|
| 시나리오 36개 | 35 통과, 유실 1 (S31) | **36 통과**, 유실·중복 0 |
| S8 같은 문단을 동시에 다른 곳으로 | ✅ | ✅ |
| S31 병합 후 글자 삭제 ∥ 앞 문단 삭제 | ❌ 가나다라 유실 | ✅ |
| S32 병합 후 글자 삭제 ∥ 앞 문단 이동 | ✅ | ✅ |

- R2(숨긴 내용 지우기)도 이제 내용을 **모두** 지운다. 후속 3에서 ¶ 하나를 남겨 피했던 유실(D3·D4)의 원인이 같은 별칭 규칙이었다. 내용을 모두 지워도 D1–D4 통과, D5는 이전과 같은 한계(실행 취소가 지운 글자를 새로 넣어 동시 입력 위치가 바뀜).
- 편집 모델(`@quiredoc/model`)에는 처음부터 별칭 개념이 없다. 빈 구획은 길이 0으로 건너뛴다.

무작위 동시 편집 (피어 3개 × 150 편집 × 200회, 별칭 규칙을 뺀 뒤 다시 실행): M4 일반 200/200, M4 이동 35% 200/200, M5 일반 200/200 수렴, 구조 위반 0, 오류 0.

빈 구획은 별칭으로 묶이지 않으므로 구획 수는 조금 늘지만(크기 표), 화면에 아무것도 내지 않아 R1 조각 수에는 영향이 없다.

### 발견

1. **Loro 마크 키에는 `:`를 쓸 수 없다** (패닉). 문단 속성 키는 `p_<이름>`으로 한다.
2. **expand 규칙은 로컬 입력에만 확실하다.** 다른 피어가 동시에 구간 경계에 입력한 글자가 서식을 받을지는 Loro 내부 순서(피어 번호)로 정해진다. 규칙과 반대가 될 수도 있다. 수렴은 한다.
3. **문단 속성 마크는 동시에 ¶ 옆에 들어온 글자로 번진다.** 확장 없음(`none`)이어도 그렇다. 그래서 **문단 속성은 ¶ 글자의 것만 읽는다**. 번진 글자가 ¶ 자체(동시에 누른 Enter)이면 그 새 문단도 속성을 받는데, Enter의 속성 복사와 같은 결과라 받아들인다.
4. **동시 나누기와 속성 변경 (F5)**: 나누는 쪽이 모르는 속성은 새 앞 문단에 복사되지 않는다. 고칠 방법(받는 쪽이 나중에 복사)은 피어마다 다른 결정을 낳아 수렴을 깬다. 받아들인다.
5. **가상 ¶ 문단에는 속성을 걸 수 없다**: 속성을 걸 때 그 구획 끝에 실제 ¶를 먼저 넣는다. 그러면 화면은 그대로이고, 구획은 보통 모양(¶ + 표식)이 된다.

### 결론

10 §3의 표현을 유지한다. 2-6(동기화)에 위 3·5를 넣고, 2·4는 알려진 한계로 둔다.

- 무작위 동시 편집 (3피어 × 200단계 × 40시드, 연산 8,000개): 셀 입력, 행·열 추가·삭제·되돌리기·이동, 열 너비, 병합·나누기, 개체 크기·이동, 부분 동기화를 섞었다.
  - 모두 수렴했고 셀 글 유실은 0이다.
  - 병합할 때 덮인 셀의 글을 왼쪽 위 셀로 **옮기면** 글 44개가 둘이 되었다 (40시드 중 22개). **옮기지 않으면** 0이다.

### 발견

1. **Loro 루트 컨테이너 이름에는 `/`(와 `\0`)를 쓸 수 없다.** 표 레코드는 `<표>.rows`처럼 점으로 잇는다.
2. **MovableList에서 동시 이동 ∥ 삭제는 이동이 이긴다.** 지운 행이 되살아난다 (T8 처음 결과). 그래서 행·열 삭제는 목록에서 빼지 않고 지운 표시 맵(`<표>.gone`)에 둔다. 표시는 이동과 무관하게 남는다. 되돌리기는 표시만 지우면 되고, 행이 제자리로 돌아온다.
3. **셀 스토리 ID를 (표, 행, 열)에서 정한다.** 동시에 행과 열을 넣어 생긴 교차 칸에 두 피어가 처음 입력해도 같은 컨테이너라 합쳐진다. 셀 맵에 스토리 ID를 두면 LWW라 한쪽 글이 보이지 않게 된다. 이렇게 하면 셀 맵 자체가 필요 없고, 병합·셀 속성만 맵에 둔다.
4. **병합은 덮인 셀의 글을 옮기지 않는다.** 옮기기(지우고 넣기)는 동시 병합에서 같은 글을 두 번 넣는다. 덮인 셀의 글은 제자리에 두고, 레이아웃이 왼쪽 위 셀 뒤에 이어 그린다. 나누면 원래 셀에 그대로 있다.
5. **병합 범위는 덮는 행·열 ID 목록으로 둔다.** 칸 수로 두면 가운데 행·열을 지울 때 병합이 다음 행·열까지 늘어난다. ID 목록이면 남은 것 중 가장 먼 것까지로 줄어든다.
6. **개체 속성 마크도 동시에 옆에 들어온 글자로 번진다** (후속 6 발견 3과 같음). 개체 글자의 것만 읽는다.

### 결론

11 §3의 표현을 유지하되 2–5를 반영한다. 셀마다 텍스트(O-24)를 그대로 쓴다. 다만 셀 스토리를 지금 본문 모양(구획 순서 목록, 보초·자리표시)으로 만들면 셀마다 컨테이너가 서넛 더 생기고 내용도 늘어난다. 2-10에서 셀 스토리는 구획 표식 없이 가볍게 시작하고, 처음 문단을 옮길 때 구획을 만든다.
